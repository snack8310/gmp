# 运营演示容器化设计

## 意图与边界

用户希望先把运营演示做成可构建、可启动的容器交付物，以便考虑部署。现有演示由 Node 页面及同源代理、Go 管理 API 共同运行；活动和流程边存在 API 进程内，受众、实验及活动流程实验草稿存在当前浏览器。容器化不改变这些数据边界，也不接生产依赖。

本轮交付 Docker 构建、双服务编排、启动配置和运行说明。只在本机验证，不进行远端部署或公开互联网开放。默认仅将页面端口映射到宿主机回环地址；API 只允许编排网络中的前端访问。若以后向外部人员开放，部署方须先提供访问控制与 TLS。

## 方案选择

| 方案 | 取舍 | 结论 |
|---|---|---|
| 一个多阶段 Dockerfile 分别构建 Go API 与 Node 前端目标，由 Compose 编排 | 各容器只运行一个主进程，前端可通过内部服务名代理 API；增加一份 Compose 配置。 | 用户于 2026-11-06 确认采用。 |
| 一个容器同时运行 Go 与 Node | 单条 `docker run` 即可启动，但必须管理子进程退出、信号和重启。 | 不采用。 |
| 只封装静态页面 | 构建最少，但页面依赖的活动 API 不可用。 | 不采用。 |

## 运行设计

- Dockerfile 的管理目标用与 `management/go.mod` 兼容的 Go 工具链编译二进制；运行容器不包含源码。前端目标用 Node 运行现有 `serve.mjs` 和演示资源。
- Compose 分别启动 `api` 与 `frontend`；API 监听容器网络，前端监听容器网络并通过 `api` 服务名访问 API。Compose 只映射前端端口，宿主机默认地址为 `127.0.0.1`。
- 前端入口保留现有端口参数和本机默认回环地址；新增显式环境变量控制监听主机与 API 主机，空值启动失败。已有本机命令无需修改。
- API 可用性由现有只读活动列表接口检查；前端在上游连接失败时维持可判别的 JSON 502 响应。容器日志继续使用现有结构化 JSON，避免记录请求体、凭据和个人敏感信息。
- 构建上下文排除 Git 元数据、临时产物及无关源码。文档提供构建、启动、停止、访问和重启后的数据边界说明。

## 验收与回滚

构建与启动后，从宿主机请求页面和同源 `/api/v1/campaigns`，确认 API 只在容器网络内；再验证本机原命令及前端与管理 API 回归。通过回退本分支的容器配置、前端入口配置和运行文档恢复原状；本轮无持久化迁移或生产变更。
