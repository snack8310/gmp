# 领域设计文档

本目录是本项目**领域模型的规格真源**，供所有 repo 引用。

根 `AGENTS.md`「项目高风险清单」中「当条目措辞与领域设计文档冲突时，以设计文档为准」所指的「领域设计文档」，即本目录下的文档。

## 定位

- 本目录描述**领域语义与边界决策**：概念、标识、不变量、状态机、职责归属、依赖方向。
- 本目录**不描述实现**。「实现」的判定边界见下方「三类文档」——**该处是本目录唯一的规则出处**，此节不另立禁令。
- 各 repo 的实现必须符合本目录的语义；实现细节写在各自 repo 内，不写回本目录。

| 文档 | 关系 |

## 三类文档

本目录放三类文档。**一份文档只能属于一类**——不设复合分类。

| 类型 | 写什么 | 禁止出现 |
|---|---|---|
| **需求整理** | 只有用户故事、场景、原话。写「运营想干什么」 | 任何设计——字段、状态机、接口、存储、不变量 |
| **决策记录** | 已确认事实、能力清单、职责归属、依赖方向、被推翻的判断，以及支撑它们的用户故事 | 见下方「可判定的边界」 |
| **设计文档** | 领域模型。每个决策都能追溯到某条故事或某条已确认事实 | 同「可判定的边界」的禁止侧 |

**当前四份文档全部归「决策记录」**——判据是：**每份文档要么标记自己的已确认项，要么逐条引用别处的已确认条目**。`business-scenarios.md` 的五个场景本身待业务确认，但它逐个标注了每个场景踩到哪些已确认决策，主体仍是决策。目录下暂无纯「需求整理」文档。

该判据由 `test/docs/consistency_check.py` 校验，不靠人工核对。

> 曾允许一份文档同时属于「需求整理 + 决策记录」。评估器指出：**复合分类下没有规则说明某句话归哪一半，需求整理的禁止列因此恒为空**；而实施方正是用这个漏洞给 `business-scenarios.md` 改标签而非改内容通过了判定。复合分类据此取消。

### 可判定的边界

决策记录能不能写某句话，按**它约束的是谁**来判，不按它含不含技术词汇：

| 允许 —— 约束**职责与依赖** | 禁止 —— 约束**怎么做出来** |
|---|---|
| 接口的**职责形状**：收什么、给什么。例「实验服务只收 `(分流键, 一次分流的定义)`，只给份号」 | 接口用什么**协议**、什么序列化格式 |
| **依赖方向与分层**。例「`experimentation` 不得依赖另外两个」 | 某个包**内部**的文件与模块如何摆放 |
| 某物**归谁**——哪个 repo、哪个包、哪个变更单元。例「场景测试归 `gmp-core/scenarios/`」 | 该能力用什么**算法、数据结构**实现。例：不写哈希表达式 |
| **技术选型的倾向与其后果**。例「倾向 Go，其接口隐式实现，故需契约测试」 | 框架用法、部署形态、配置项 |

判据一句话：**写「谁负责什么、谁能依赖谁」是允许的；写「它内部长什么样」不允许。**

> 本目录曾只分「需求整理 / 设计文档」两类，并在「定位」节禁止出现任何技术词汇。评估器指出该规则**对本目录一份文档也不成立**。第一次修订只改了细则段、没改定位段，**把矛盾从产物侧搬进了规则内部**，被第二轮再次判为阻断。本次同时改掉定位段、给出可判定的边界，并对四份文档逐份重判（结果见变更证据）。

尚无设计文档。**先有用户故事，再有设计**——曾经有过一份直接从业务主线推导出的设计文档，因为跳过了需求这一步而被整份删除（见 `docs/history/changes/`，原文可在 git 历史中查看）。

## 设计文档的写法约定

以下要求只适用于**设计文档**，不适用于需求整理。每份设计文档必须包含以下章节，缺一不可：

1. **状态**：草稿 / 已定稿；最后修订对应的 issue 或 PR。
2. **名词表**：本文档定义的每个概念，中文名 + 英文名 + 一句话定义。英文名是跨 repo 命名的依据。
3. **概念与关系**：概念本身、概念之间的引用方向。
4. **不变量**：必须恒真的性质。每条写成可证伪的断言，不写成愿望。
5. **状态机**：有生命周期的概念必须给出状态与合法流转，并明确非法流转。
6. **边界与非目标**：显式写出哪些职责**不**属于本模型，以及属于谁。
7. **决策记录**：本文档做出的硬决策，每条含备选方案与否决理由。**只记录选了什么和为什么，不记录讨论过程。**
8. **待澄清问题清单**：想不清楚的、当前没人在看的开放项。**不允许因为想不清楚而省略。**

### 编制纪律

- 从来源文本（业务主线、高风险清单、需求原文）编制内容时，以**来源侧**为遍历基准逐项承接，禁止复合词压缩。见 [`source-enumeration-fidelity`](../history/memory/source-enumeration-fidelity.md)。
- 承接情况必须落成**产物形态**（分项承接表），不得只写「已逐项核对」。
- 仓库内无法证明的字段名、默认值、配置不得臆造；信息不足时列入待澄清问题清单。
