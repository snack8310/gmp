# 名单视角的用户故事

## 这份文档是什么

站在**运营**的视角，列出跟「名单」有关的事情。本文档属**决策记录**，适用 [`README.md`](README.md) 的「可判定的边界」——该处是本目录唯一的规则出处，此处不另立禁令。

每条标注三态之一：

- `已确认`：本次讨论中用户明确说过，可以找到原话。
- `待确认`：我推测运营会需要，等用户判断。**这是默认值。**
- `明确不做`：用户明确说过不在范围内。

`待确认` 不代表我认为该做，只代表「这件事该不该有，得你来定」。可以直接回「不要」「没想过」「运营不会这么干」。

> **注意**：后来发现**活动才是上游**——本文档的开放问题曾有一半卡在活动上（Q1、Q3、Q5、Q9、Q10）。活动侧定清后已回补，**Q1–Q10 现已全部关闭**（见下方结论表）。活动侧的讨论在 [`campaign-user-stories.md`](campaign-user-stories.md)。

## 已确认的名词

只记运营和研发都认、且已经拍板的词。**这里不是设计，只是约定大家说同一个词指同一件事。**

| 词 | 英文 | 指什么 |
|---|---|---|
| **受众服务** | `Audience Service` | 这个系统本身。**不叫 CDP**——CDP 的核心是身份拼接与统一档案，而「uid 背后是什么」「账号合并」已明确排除在外（见第七节）。叫 CDP 会招来「统一档案在哪」「跨端身份怎么打通」的错误期待。它做的是 CDP 里**分群那一层** |
| 人群来源，简称**来源** | `AudienceSource` | 一个能吐出 uid 的地方。**由研发预先接好，运营只能从列表里挑，不能自己新接。** 分两类：**外部来源**（订单系统、CRM、某个消息流）和**平台自身**（本平台的执行结果回流——发了、打开了、领了券）。后者是条件分流成立的前提，见活动文档 |
| **人群配置** | `AudienceConfig`（**建议名**；代码层现为 `audience.Definition`，旧文档亦称 `AudienceDefinition`） | **来源 + 筛选条件**。筛人是配置的一部分，不是与来源并列的另一套东西。有枚举与判定两种求值用法。**勿再以「人群定义」当主名**——易与「来源」混淆（事实 8、26） |
| **人群组** | `AudienceGroup`（**建议名**） | **受众对外挂接单元**。无实验时组数 = 1（一份人群配置对外呈现为一组）；有实验时 = 实验人群包下的各臂（多组）。活动 / 投放项挂的是人群组，不是「来源」本身 |
| **可复用实验人群** / **实验人群包**（口语亦称「分好 AB 的用户组」） | `ExperimentAudienceBundle`（**建议名**；用户未给英文偏好，拼写待命名确认，跨子项目暂用此名） | **一等公民发布单元**：绑定**同一来源**上的**一次分流**与各臂**人群组**，打包发布后可被多个活动引用。**不是新的分桶机制**：分流定义仍归实验服务；每臂内部仍是带「第 N 份」条件的**人群配置**（A7） |
| **分流组件** | —（产品说法；本体 = 实验服务的一次分流定义） | 可被活动经实验人群包 / 人群组引用的一次分流**运行单元**。**运行中**：可调比例、白名单等；**不可改「加载组件逻辑」**。**非运行中**：不可被其他活动引用（事实 27、28） |

### 新旧名词映射（关闭歧义）

| 旧说法 / 易混说法 | 现主名 | 说明 |
|---|---|---|
| 「人群定义」`AudienceDefinition` | **人群配置** `AudienceConfig` | 同一求值对象改主名；= 来源 + 筛选 |
| 「待命名的那次筛选配置」（旧名词表空行） | **人群配置** | 空行闭合；与来源生命周期不同（事实 8） |
| 口语「用户组 / 分好 AB 的组 / 名单」在对外挂接义 | **人群组** | 无实验 → 1 组；有实验 → 多臂多组 |
| 「可复用实验人群」作为发布单元 | **实验人群包** `ExperimentAudienceBundle` | AQ1 已确认的一等公民；包内各臂 = 人群组 |
| 「来源」 | **来源**（不变） | 只表示能吐 uid 的供给方，**不含**筛选 |

**来源的三种供给方式**（共同点是「都是一个能吐出 uid 的地方」，区别只在谁主动）：

| 供给方式 | 谁主动 | 用户原话 |
|---|---|---|
| **拉** | 我问它要 | 「从某个地方圈选一组名单」 |
| **推 · 整批** | 它给我一批 | 「等那个地方推给我」 |
| **推 · 逐条** | 它一条一条给 | 「订阅一个消息，按条数推给我」 |

否决过的名字：**数据源**（会跟数仓撞车，运营也会当成技术概念）、**入口**（更像「人进活动的那个动作」，不是「人来自哪儿」）。

## 受众服务要提供的能力

从上面的故事和事实推出来的。每条注明依据，以及它是从 `已确认` 还是 `待确认` 的故事来的。

| # | 能力 | 谁用 | 依据 |
|---|---|---|---|
| A1 | **注册来源** | 研发 | 故事 7 `已确认` |
| A2 | **配置人群**（选一个来源 + 加筛选条件 → 一份**人群配置**） | 运营 | 故事 8 `已确认` |
| A3 | **枚举**——把这批人列出来 | 「找人 · 批量」的投放项 | 事实 9（已修正：求值入口） `已确认` |
| A4 | **判定**——这个 uid 算不算 | 「事件触发」「资源位」的投放项 | 事实 9（已修正：求值入口） `已确认` |
| A5 | 预估规模 | 运营 | 故事 3 `待确认` |
| A6 | 解释——这个人为什么在 / 不在 | 运营、客服 | 故事 12 `待确认` |
| A7 | **引用分流结果作为人群条件**——人群配置里可以写「且 在分流 E 里落在第 2 份」 | 实验、放量 | 边界文档 `已确认`。**分桶本身不归受众服务**，归实验服务。可复用实验人群**建立在本能力之上**，不另开分桶入口 |
| A8 | **消费平台自身的执行结果**作为来源（发了、打开了、领了券） | 条件分流 | 活动文档事实 18 `已确认` |
| A9 | **发布并复用实验人群包**——一次分流与各臂打包发布，多活动引用 | 分组实验 | 故事 15、27 与事实 19–25 `已确认`。机制仍是 A7；本条是一等公民与复用承诺 |
| A10 | **分流修订 / 停用时强制停用包内各臂**，不得继续被活动当作有效人群 | 分组实验、止血 | 事实 24 `已确认`（AQ2） |
| A11 | **分流组件运行态约束**——运行中可调比例 / 白名单；不可改加载组件逻辑；非运行中不可被活动引用 | 分组实验、止血 | 事实 27、28 `已确认` |

**A3 和 A4 是同一份人群配置的两种用法，但性质相反**——这是受众服务最硬的一条约束：

| | 什么时候跑 | 快慢要求 |
|---|---|---|
| **枚举** | 可以离线 | 几百万人跑十分钟也行 |
| **判定** | 在资源位那条线上，APP 在等 | **必须在线、必须快** |

一份人群配置要同时满足这两种。（被删掉的那版设计只做了枚举，所以答不了资源位。）

## 这些故事还没回答的问题

从上面的故事里直接冒出来、但**还没有人表态**的。不猜答案。

**Q1–Q10 已全部关闭。** 结论如下：

| # | 结论 |
|---|---|
| **Q1** | **问题不成立**——事件串的模型里没有「流程」，每个投放项各自判定自己挂的人群组（其下的人群配置）。想「退款就不发」，把「且未退款」**显式写进**那个人群配置 |
| **Q2** | **不做**——频次归各动作对应的组件管，见故事 18 |
| **Q3** | **靠执行记录回溯，不靠快照**。人群是持续判定的，本就没有快照；「当时那批人」= 从执行记录里捞出来的那批 |
| **Q4** | **两件事**。预估归受众服务（A5，允许不准）；「实际多少人」其实是「某次执行覆盖了多少人」，来自执行记录，属运营平台的指标 |
| **Q5** | **停活动 / 停投放项**是止血手段（快、影响面清楚）；**改人群配置是修复手段**——同一份配置可能被多个人群组 / 投放项引用，改一处会波及别处 |
| **Q6** | **只记数量 + 来源侧定位，不存来源原值**。要查具体哪几条，回来源系统查。与「uid 背后是什么不归本平台管」一致 |
| **Q7** | **已闭合**——它就是**人群配置**（`AudienceConfig`，建议名；旧称「人群定义」`AudienceDefinition`），归受众服务，由运营平台的界面创建。对外挂接见**人群组**（事实 26） |
| **Q8** | **推过来之后我们自己筛**。筛选逻辑因此**只有一处**（人群配置），不会出现「对方筛一半我们筛一半」；对方也不用改 |
| **Q9** | **能**。一个活动挂多个投放项，各自人群组 / 人群配置可来自不同来源。至于「一份人群配置能否跨多个来源」是另一件事，见故事 6（仍待确认） |
| **Q10** | **语义上不会互相影响**——来源是只读供给方。**唯一例外**：来源本身若有查询配额或限流，共用会互相挤，那是接入时应声明的属性 |

## 已确认事实清单

散落在上面各条里、来自本次讨论的事实，集中列一遍便于查：

1. 一个人 = 一个 uid（businessId），唯一识别；uid 背后是什么不归这个平台管。
2. 平台能力是：给定一个 uid，做条件判断、策略分流、触达。
3. ~~「一次性圈一批人」和「人不停地流进来」，两种都是常态。~~ **已修正**——这条是在还以为「名单是最上游」时说的，只描述了「我们找人」那半个世界。资源位那类（人自己来了、当场决定给他看什么）**根本不圈人**。现在的完整说法见事实 9。
4. 持续进入里，同一个人每满足一次条件就进一次。
5. 同一个人可以同时有多个流程在跑，互不干扰。
6. 「从某处圈选」「等它推一批」「订阅它按条推」三种拿人方式，是**同一个东西**的三种供给方式，不是三个概念。
7. 来源由研发预先接好，运营从列表里挑。
8. 「来源」和「运营在活动里配的那次筛选」**拆成两个东西**——生命周期不同，不拆的话「改来源」会有两个意思。
9. ~~受众侧**只提供一样东西——「人群定义」**~~ **已修正**——**求值入口**是**人群配置**（旧称「人群定义」）：枚举与判定两种用法不变；**对外挂接**是**人群组**（无实验组数=1；有实验为多臂多组，见事实 26）；另立一等公民**实验人群包**打包「一次分流 + 各臂人群组」供发布与跨活动复用（事实 23）。不圈人的那类同样走判定方向。
10. 这个系统定名 **受众服务 / `Audience Service`**，不叫 CDP。
11. **来源分两类**：外部系统，和**平台自身的执行结果回流**。后者是「下一步根据上一步的结果分流」成立的前提。
12. ~~**分桶归受众侧**（随机稳定切分）~~ **已推翻**——分桶带来的互斥、盐、对齐、实验臂跟「这个人是谁」无关，已拆给**实验服务**（见 [`system-boundaries.md`](system-boundaries.md)）。受众服务只是把「在分流 E 里落第 N 份」当成一个**普通人群条件**来引用，跟「消费满 100」同类。
13. **随机分桶**（实验服务管）和**条件分流**（按事实分）仍是两件事；后者不需要新概念，就是「人群配置（对外呈现为一个人群组）+ 投放项」。
14. **频次上限不归本平台**，归各动作对应的组件。代价：跨渠道总打扰量没有任何一方知道。
15. **止血靠停活动 / 停投放项**，不靠改人群配置——后者是修复手段，会波及其他引用方。
16. **未解析条目只记数量与来源侧定位，不存来源原值**；要查具体是哪几条，回来源系统。
17. 「推 · 逐条」的来源**推过来之后由本平台自己筛**，筛选逻辑只有一处。
18. 「事后回看当时那批人」**靠执行记录，不靠名单快照**——人群是持续判定的，本就没有快照。
19. **同一个人群组（其下的人群配置）可以被多个活动同时引用**（故事 15）——复用的是配置 / 组，不是每次活动各圈一份副本。
20. **可复用实验人群**：在**同一个来源**上建立一次分流，再为各臂写带「第 N 份」条件的人群配置并对外呈现为多个人群组；这套臂可被多个活动 / 多个地方引用。口语「分好 AB 的用户组」指这件事，**不**引入受众服务自己的分桶。
21. **分组实验的默认落点是人群侧**（事实 20 + A7），而不是在活动流程 / 执行链路里再切组。目的是同一套实验臂跨活动复用，并让多数活动配置更简单。
22. **活动内分流仍保留，但是例外**：决策表路由、或仅为单个活动再建分流，属于活动内分组，与可复用实验人群是两件事（详见活动侧事实 58、59）。
23. **实验人群包是一等公民**（`ExperimentAudienceBundle`，建议英文名）：一次发布绑定「一次分流定义 + 各臂人群组」，归受众服务存放与发布；每臂内部仍是人群配置；分流算法与份号仍归实验服务。不是运营界面上的松散约定。
24. **包所引用的分流被修订或停用时，必须强制停用包内相关臂**（及该包的可用状态），不得继续被活动当作有效人群引用。不允许臂与分流静默脱钩、也不允许继续引用「已作废分流」上的旧臂。
25. **同一臂被多个活动引用时，实验指标两种视图都要能看**：（a）按分流臂跨活动聚合；（b）按活动切开。二者并存，不是二选一（活动侧事实 61）。
26. **命名主名已改写（关闭与「来源」的歧义）**：**人群配置** = 来源 + 筛选（旧主名「人群定义」不再使用）；**人群组** = 受众对外挂接（实验可选：无实验组数=1，有实验=多臂多组）。实验人群包 / AQ1–AQ3（事实 23–25）不变——包发布的是多个人群组。映射表见上方「新旧名词映射」。
27. **分流组件运行中**（无论是否已被活动引用）：允许调整**比例**、**白名单**等运行参数；**禁止改「加载组件逻辑」**（换算法 / 换切法结构 / 换组件实现等使历史分配与染色语义不可比的变更）。运行参数调整**不**等同于 AQ2 的「分流修订」，不因此强制停用包内臂。
28. **分流组件非运行中**：不可被其他活动引用（不得新挂为有效人群；已挂引用须随停用路径失效）。进入非运行 / 分流被修订停用时，仍适用事实 24（强制停用包内相关臂）。活动侧事实 62。
