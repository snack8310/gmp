# 名单视角的用户故事

## 这份文档是什么

站在**运营**的视角，列出跟「名单」有关的事情。**这里只写「人想干什么」，不写「系统怎么做」。**

每条标注三态之一：

- `已确认`：本次讨论中用户明确说过，可以找到原话。
- `待确认`：我推测运营会需要，等用户判断。**这是默认值。**
- `明确不做`：用户明确说过不在范围内。

`待确认` 不代表我认为该做，只代表「这件事该不该有，得你来定」。可以直接回「不要」「没想过」「运营不会这么干」。

> **注意**：后来发现**活动才是上游**，本文档下面的开放问题有一半卡在活动上（Q1、Q3、Q5、Q9、Q10）。活动侧的讨论在 [`campaign-user-stories.md`](campaign-user-stories.md)，那边定清之后要回来补这一份。

## 已确认的名词

只记运营和研发都认、且已经拍板的词。**这里不是设计，只是约定大家说同一个词指同一件事。**

| 词 | 英文 | 指什么 |
|---|---|---|
| **受众服务** | `Audience Service` | 这个系统本身。**不叫 CDP**——CDP 的核心是身份拼接与统一档案，而「uid 背后是什么」「账号合并」已明确排除在外（见第六节）。叫 CDP 会招来「统一档案在哪」「跨端身份怎么打通」的错误期待。它做的是 CDP 里**分群那一层** |
| 人群来源，简称**来源** | `AudienceSource` | 一个能吐出 uid 的地方（订单系统、CRM、某个消息流）。**由研发预先接好，运营只能从列表里挑，不能自己新接。** |
| *（待命名）* | — | 运营在某个活动里，选定一个来源之后所做的那次筛选配置。**跟来源是两个东西**——来源跟着系统走，这个跟着活动走 |

**来源的三种供给方式**（共同点是「都是一个能吐出 uid 的地方」，区别只在谁主动）：

| 供给方式 | 谁主动 | 用户原话 |
|---|---|---|
| **拉** | 我问它要 | 「从某个地方圈选一组名单」 |
| **推 · 整批** | 它给我一批 | 「等那个地方推给我」 |
| **推 · 逐条** | 它一条一条给 | 「订阅一个消息，按条数推给我」 |

否决过的名字：**数据源**（会跟数仓撞车，运营也会当成技术概念）、**入口**（更像「人进活动的那个动作」，不是「人来自哪儿」）。

## 已确认事实清单

散落在上面各条里、来自本次讨论的事实，集中列一遍便于查：

1. 一个人 = 一个 uid（businessId），唯一识别；uid 背后是什么不归这个平台管。
2. 平台能力是：给定一个 uid，做条件判断、策略分流、触达。
3. ~~「一次性圈一批人」和「人不停地流进来」，两种都是常态。~~ **已修正**——这条是在还以为「名单是最上游」时说的，只描述了「我们找人」那半个世界。资源位那类（人自己来了、当场决定给他看什么）**根本不圈人**。现在的完整说法见事实 9。
4. 持续进入里，同一个人每满足一次条件就进一次。
5. 同一个人可以同时有多个流程在跑，互不干扰。
6. 「从某处圈选」「等它推一批」「订阅它按条推」三种拿人方式，是**同一个东西**的三种供给方式，不是三个概念。
7. 来源由研发预先接好，运营从列表里挑。
8. 「来源」和「运营在活动里配的那次筛选」**拆成两个东西**——生命周期不同，不拆的话「改来源」会有两个意思。
9. 受众侧**只提供一样东西——「人群定义」**。用它的方式有两种：**枚举**（把这批人列出来，"我们找人 · 批量"用）和**判定**（这个 uid 算不算，"事件触发"和"资源位"用）。**不圈人的那类同样要用人群定义**，只是走判定方向。
10. 这个系统定名 **受众服务 / `Audience Service`**，不叫 CDP。
