# 活动视角的用户故事

## 这份文档是什么

站在**运营**的视角，列出跟「活动」有关的事情。规则与 [`audience-user-stories.md`](audience-user-stories.md) 相同：**只写「人想干什么」，不写「系统怎么做」**；每条标 `已确认` / `待确认` / `明确不做`，默认 `待确认`。

**为什么先有名单文档、却后有这份**：最初判断「名单是最上游、不依赖别人」，讨论中被证伪——名单文档里 10 个开放问题有 5 个（Q1、Q3、Q5、Q9、Q10）全都卡在「活动」上，连「运营配的那次筛选」这个概念，定义里都写着「在某个活动里」。**活动才是上游。**

## 已确认的名词

| 词 | 英文 | 指什么 |
|---|---|---|
| **活动** | `Campaign` | 一个运营业务的定义。下面挂多个投放项。行业标准用法，直接沿用 |
| **投放项** | `Treatment` | 挂在活动下面的那个可执行单元。三个真实例子：APP 资源位图片展示、给特定人群做短信触达、用户停留 30 秒触发一个动作 |

选 `Treatment` 的理由：它是行业里**唯一天然覆盖下面两类**的词（Pega、Adobe Journey Optimizer 的用法）。否决过的：`Delivery`（Adobe Campaign，只覆盖"推出去"，答不了资源位）、`Journey`（Salesforce，只覆盖多步骤的）、`Offer`（不含事件触发）、`Item`（太泛）。

**投放项分两类，性质完全不同：**

| | 谁发起 | 要不要先圈人 | 例子 |
|---|---|---|---|
| **我们找人** | 我们 / 用户的某个行为 | 短信要先圈一批；事件触发是人一个个撞进来 | 短信触达、停留 30 秒触发 |
| **人找我们** | 用户自己来了 | 不圈人，**当场判断来的这个人该看到什么** | APP 资源位展示 |

「人找我们」这一类里，「发给谁」不成立——不是我们挑人发出去，而是他来了、我们当场决定给他看什么；也没有「发送成功」，只有「他看没看到」。

## 投放项跟受众侧的关系

受众侧（[受众服务](audience-user-stories.md)）**只提供一样东西——「人群定义」**。投放项用它的方式只有两种：

| 投放项类型 | 挂什么 | 问受众侧要什么 |
|---|---|---|
| 我们找人 · 批量 | 一个**人群** | 「**这批人是谁**」——把人列出来（枚举） |
| 我们找人 · 事件 | 一个**触发器** | 人一个个撞进来，逐个问「**他算不算**」（判定） |
| 人找我们 · 资源位 | 一个**准入条件** | 他来了，问「**他算不算**」（判定） |

**触发器不是第三种东西**，它是「逐个问」的一个特例。

## 投放项是「一步」，多步靠事件串

**一个投放项 = 对一个人做一件事，就一步。** 「发券 → 等 3 天 → 没用再提醒」不是一个投放项，是两个：第二个的触发器是「发券后 3 天且未使用」。

**投放项之间互不相识**，只通过事件间接相连。

由此得出一条新能力要求：**平台自己也要能产生事件**，不能只消费外部推来的事件——「发了券」这个动作必须变成一个别人能订阅的事件，否则第二个投放项无从触发。

代价（已知并接受）：运营在界面上**看不到一条完整的线**，只能看到几个各自独立的投放项。故事 23、24（「他为什么没收到」「他为什么收到两次」）会因此更难回答。

### 「画布」在这个模型里已经不存在了

「画布」原本指「把好几步串成一张图」。但「一个投放项就一步」+「多步靠事件串、投放项互不相识」两条一出，**就没有需要串在一张图上的多步骤了**——画布没有位置。

⚠️ **待办**：根 `AGENTS.md` 的项目高风险清单第 1 条（画布 DSL、节点与连线的执行语义）和第 3 条（画布运行实例的状态机）整个是围着画布写的。按该表自身的规定「当条目措辞与领域设计文档冲突时，以设计文档为准，并同步修订本表」，这两条将来需要重写。**本轮不动它**——修改高风险清单本身是一次独立的高风险变更，要单独走流程。

### 分流

用户最早描述这个平台时的原话是「给定一个 uid，做条件判断、**策略分流**、触达」。

**用户给的真实例子**：1 万人分成 A 组（对照）、B 组（先短信再权益）、C 组（实验）、D 组（只发权益）。

按已定规则拆开，答案自己就出来了：

| 组 | 用户说的 | 拆出来是 |
|---|---|---|
| A | 对照 | **零个投放项**——什么都不做 |
| B | 先短信、再权益 | **两个投放项**（多步靠事件串） |
| D | 只发权益 | **一个投放项** |

**一个组 ≠ 一个投放项。** 所以分流**不是投放项内部的变体**，它在投放项**之上**：一个组对应的是「一套投放项」，可能 0 个、1 个或好几个。

**它也不是画布回归**——两者切的维度不同：

| | 切什么 | 谁管 |
|---|---|---|
| 画布 | 按**时间**串步骤 | 已交给事件（事实 11、12） |
| 分流 | 按**人**切人群 | 本节 |

分流完全不碰时序，长不回编排。

#### 分桶 与 条件分流 是两件事

| | 按什么分 | 同一个人会不会换组 |
|---|---|---|
| **分桶** | 随机 / 哈希，与这个人是谁无关 | **永远不变**——这是它的全部价值 |
| **条件分流** | 按事实分（打开了没、买了没、领券没） | **本来就该变**：事实变了他就该走另一边 |

#### 条件分流不需要任何新概念

「下一步根据上一步的结果分流」这件事，闭环是这样的：

```
投放项①发短信
      ↓  产生事件（T5）
   执行结果回流
      ↓  成为受众服务的一个来源  ← 新增
「收到过短信但没打开的人」= 一个普通的人群定义
      ↓  判定
投放项②发权益
```

**条件分流 = 一个人群定义 + 一个投放项。** 不需要编排器，不需要"策略画布"。A/B/C/D 四组就是四个人群定义，各自挂各自的投放项。

代价与约束：

- **回流有延迟。** 已确认**小时级够用**；平台应在界面上直接拦住更短的配置，别让运营配「发完立刻看谁没打开」——那会全判成"没打开"，不报错，安静地发错人。
- **对照组必须在系统里存在。** A 组什么都不做，但如果系统里没有它，事后「对照组的人」和「压根不在人群里的人」就分不开，实验无法归因。

### 放量（流量开关）

**用户的问题**：一个运营活动，前期只想放很少的人参与，后面再逐渐放开——这在哪里改？

**答案：还是分桶，不需要新机制。** 把人群切成 100 份，先只放 5 份，过几天放 20 份，最后放满。

**为什么必须用分桶、不能用「随机取 5%」**：分桶稳定，同一个人永远落同一份，所以放量是**单调**的——已经进来的人不会在下次放量时掉出去。用随机取，第二次取的跟第一次不是同一批人，先进来的人会莫名其妙被踢出活动，**而且不报错**。

**「现在放到几成」这个旋钮挂在活动上**，运营可随时调，活动下面所有投放项一起放。挂在投放项上会让 A/B 两组放量不一致，实验结论直接失效且不报错；挂在人群定义上会让同一份定义被两个活动共用时互相干扰。

### 分桶到底是不是一个独立的东西

**用户的问题**：分桶是一个单独的组件吗？桶和分桶策略是一个单独的业务模型吗？

拆成四个，只有一个需要成为业务对象：

| | 是什么 | 要不要独立成一个东西 |
|---|---|---|
| **分流单元** | 按什么粒度分（uid / 设备 / 订单） | **不要**——已被早先的决定定死：平台只认 uid，没有第二种粒度可选 |
| **分桶算法** | 怎么把一个 uid 映射到某个桶 | 实现细节。**但「盐」有业务含义**，见下 |
| **一次分桶** | 「把人群 X 按 25/25/25/25 切成四份」这次操作及其产出 | **要。这是唯一需要成为业务对象的** |
| **单个桶** | A 组、B 组各自 | **不要**——它就是一个人群定义，跟「消费满 100 的人」同类（事实 24） |

**为什么「一次分桶」必须被保存**，三件事离了它答不了：

1. **互斥关系**——「A 组和 B 组互斥」只有"来自同一次分桶"能证明。而放宽后的抢位子规则（人群互斥就允许，事实 23）**正是靠它判断**的。
2. **放量旋钮**——「现在放到几成」= 「当前纳入这次分桶的哪几个桶」，旋钮得有东西可挂。
3. **实验归因**——事后回答「这四组是同一个实验的四个臂」。

**所以：桶不是新概念，「分桶这件事」才是。**

#### 盐：默认打散，允许指定对齐

若所有分桶共用一套哈希，同一个人会在每个实验里落到同一位置——**一批倒霉蛋永远当对照组、永远收不到东西**，另一批永远被反复打扰，且所有实验样本高度重叠、结论互相污染。

**默认：每次分桶各自打散。** 同时**允许运营指定「跟某一次分桶对齐」**，用于同一批人分阶段做实验。

**运营配的是「跟哪次分桶对齐」，不是「盐」**：分桶结果取决于 uid + 盐 + 怎么切（几份、什么比例）。只对齐盐、切法不同的话，「同一个人落到同一组」这个意图并没有实现，**而且不报错**。让运营选一个已有分桶，平台自己取它的盐与切法，并在切法不兼容时当场拦住。**盐是实现细节，「对齐」才是业务意图。**

### 决策表

**用户的真实例子**：1 万人，不论男女都看到广告入口，但只有女性发权益；30 岁发一种权益，40 岁发另一种。

**已定：表放在投放项之上，不放在里面。**

- 投放项保持「对一个人做一件事」不变：`T1` = 发权益 A，`T2` = 发权益 B。
- **决策表只做一件事：把人路由到投放项。它自己不执行任何东西。**

| 命中条件 | 走哪个投放项 |
|---|---|
| 女 + 30 岁 | `T1` |
| 女 + 40 岁 | `T2` |
| 其他 | 不走 |

否决「表放在投放项里面」的理由：那会让「投放项 = 一件事」变松；权益 A 被埋在表的一行里，别的活动复用不了；报结果时要额外带上「命中了哪行」才分得清归因。

**决策表跟「条件分流」是什么关系**：表的每一行拆开就是「一个人群定义 + 一个投放项」，所以它**不需要新的执行机制**。它值得成为一个概念，只因为它比「N 个各自独立的人群定义」多保证三件事：

| | 散着配 N 个人群定义 | 决策表 |
|---|---|---|
| **顺序** | 没有。一个人同时命中两条，谁赢没人知道 | 从上往下，第一个命中的生效 |
| **兜底** | 容易漏掉某类人，**漏了不报错** | 最后一行「其他」 |
| **互斥** | 条件写重叠了**没人会告诉运营** | 表的语义天然保证只走一行 |

所以决策表是个**约束容器**，不是新的执行机制。

### 动作：投放项「做什么」的那一半

**动作（`Action`）= 做哪一类事**：展示素材、发短信、发权益。它决定这次执行长什么样、「成功」怎么定义。

**动作跟「来源」是对称的**，这个对称性是它该独立成一个概念的理由：

| 进来的方向 | 出去的方向 |
|---|---|
| **来源** —— 人从哪来 | **动作** —— 东西怎么出去 |
| 研发预先接好，运营从列表里挑 | **同样是研发接好、运营挑** |
| 三种供给方式：拉 / 推整批 / 推逐条 | 三类动作：展示 / 发短信 / 发权益 |

所以动作**不是投放项里随便填的一个字段**，它跟来源一样是「研发接入的能力清单」——运营能用哪些动作，取决于研发接了哪些。

#### 内容不做统一概念，它是动作的参数

**已确认**：不设一个统一的「内容」模型。**「动作」定义要填什么参数，参数值怎么管，一个动作一个说法。**

| 动作 | 要什么参数 | 这参数是谁的 |
|---|---|---|
| 展示 | 一张素材 | 平台还是资源位系统持有，**未定** |
| 发短信 | 一条文案 | 平台自己持有 |
| 发权益 | 一个**券种 id** | **外部券系统的**，平台只是引用它 |

关键在最后一行：**券种根本不是平台的内容，只是一个外部标识。** 把它包成「内容」概念，等于替外部系统的东西建了个壳，券系统一改这边跟着疼。

**已知代价**：素材不是一等公民，所以「哪张图效果好」这类**跨投放项按素材归因**做不了。要做得回来补。

#### 执行：全都是调外部系统，但有三件事推不出去

三类动作都是跟外部系统打交道，**但方向不同**：

| 动作 | 谁调谁 | 有没有「发放成功」 |
|---|---|---|
| 发短信 / 发券 | **我们调**外部系统 | 有 |
| 资源位展示 | **外部系统调我们**，我们返回「给他看哪个」的 id，由它自己渲染 | **没有**——返回 id 之后有没有真展示、有没有被看见，我们不知道，除非有曝光回传（见 C5） |

外部系统内部的失败逻辑（库存不足、号码无效）归它们自己。**但下面三件即使全调外部接口，仍是本平台的责任**：

| | 为什么推不出去 |
|---|---|
| **幂等** | 见下方接入门槛 |
| **回执关联** | 「拿到执行结果」是两件事：**调用返回**（立刻，「对方收下了」）和**异步回执**（几秒到几分钟后，「真的送达了没有」）。短信尤其明显：接口返回成功 ≠ 用户收到。高风险第 9 条点名的正是「回执关联错误会导致重复发送，或让执行状态永远悬空」 |
| **资格判定** | 退订、免打扰、频次疲劳。短信系统可能有自己的退订名单，但**「这个人本月已被本平台打扰 5 次」只有我们知道**。见受众侧故事 18 |

#### 幂等：门槛卡在接入，不在调用时

**已确认：下游必须是幂等的，不幂等的不接入。** 超时按重试策略重试（例如 3 次），仍失败则报异常。

这把「漏发还是重发」的两难**消掉了**，而不是选一边——下游幂等，重试就安全。门槛卡在接入那一刻，与「动作由研发接入、运营只能挑」正好配套。

推论与未覆盖项：

1. **幂等键必须由本平台生成，且三次重试之间不变**——换了键，下游会当成新的一次。
2. **「下游幂等」是声明，不是保证**。若某下游声称幂等而实际不是，失效是静默的（重试两次、用户收到两条、无任何报错）。**接入时需要验证手段**（如接入前跑一次「同键调两次」的验证），不能只凭对方口头保证。
3. **资源位那类无法重试**——人已经走了。重试策略只适用于我们主动调的那类。
4. **重试耗尽后那个人仍算实验组**（下一节）。

#### 执行失败的人，实验里仍算实验组

**已确认**：分到实验组但执行失败（重试耗尽）的人，做实验分析时**仍按分组计入实验组**（业界称 ITT）。

否决「只统计真收到的」的理由：发失败的人往往有共性（号码无效、长期不活跃），剔掉他们等于**偷偷筛选了人群**，随机性被破坏，结论系统性偏乐观——**而且不会报错**。

#### 一条被推翻的理由（如实记录）

主 Agent 曾主张「内容必须独立，因为权益有库存，埋在投放项里会超发」，并引 `AGENTS.md` 高风险第 7 条佐证。

**用户指出这条不成立**：库存归券系统，本平台只管发放。超发是券系统要防的失效，不是这里。

由此收窄了高风险第 7 条的适用范围：该条写「变更权益侧的**额度、库存与发放逻辑**」，而**额度与库存不归本平台**，只有发放逻辑归。

## 投放项要提供的能力

| # | 能力 | 说明 | 依据 |
|---|---|---|---|
| T1 | **说清对谁** | 挂一个人群（走枚举），或挂一个触发器 / 准入条件（走判定） | 事实 10 `已确认` |
| T2 | **说清做什么** | 选一个**动作**（研发接好的），填这个动作要的参数 | 故事 3、7、8 `已确认` |
| T3 | **参与裁决** | 抢同一个位子时，带着**活动的**优先级去比 | 事实 6、8 `已确认` |
| T4 | **报结果** | 推那类报「发没发出去」；资源位那类报「有没有被展示」——**两者不是一回事**，见 C5 | 事实 5 `已确认` |
| T5 | **产生事件** | 自己做完的事要变成事件，供别的投放项订阅 | 本节 `已确认` |

## 走一遍：一个真实场景

用户的原始问题：「1 万人分成 4 组，A 对照、B/C/D 实验；C 组 5000 人再细分成 2000 / 3000。这在模型里涉及哪些动作？」

**全程只用已定的东西，没有新概念、没有编排器、没有策略画布：**

| 步 | 动作 | 用到什么 |
|---|---|---|
| ① | 建人群定义「近 30 天消费满 100」 | 受众 A2 |
| ② | 枚举一下看看多少人 → 1 万 | 受众 A3 |
| ③ | 对它**分桶**，切 4 份 | 受众 A7 |
| ④ | 对 C 组（本身也是个人群定义）**再分桶一次**，切 2000 / 3000 | 受众 A7 |
| ⑤ | 每组挂投放项：A 挂 **0 个**，B / C-1 / C-2 / D 各挂若干 | 投放项 T1、T2 |
| ⑥ | 需要多步的组，再建一个投放项 + 配触发器（「收到过短信 且 3 天 且 没用」） | 事实 11、12 |
| ⑦ | 跑：枚举 → 逐个执行；结果回流 | 受众 A3、A8 |

**关键在第 ③④ 步**：分桶的输入是一个人群定义，**输出还是人群定义**。所以「再细分」不是新机制，就是分桶套分桶，想切几层切几层。

**「策略画布」在这个走查里散成了两样早就有的东西**：分桶（切人）和事件（串步骤）。

## 已确认事实清单

1. 活动是一个运营业务的定义，下面有多个细分投放项。
2. 投放项的三个真实例子：APP 资源位图片展示、给特定人群做短信触达、用户停留 30 秒触发动作。
3. 投放项分两类：**我们找人**（推出去）和**人找我们**（他来了当场决定）。两类都要做。
4. 平台**必须有当场决定的能力**——APP 拿一个 uid 来问，平台实时算该给他看什么。
5. 同一个资源位多个活动命中同一个人时，**按优先级，运营自己排**。
6. **抢位子的是投放项**，但**优先级配在活动上、穿透到投放项**。
7. **同一个活动内，两个投放项不能抢同一个位子**——建的时候就拦住，不留到运行时。
8. 优先级是**全局一个**：一个活动自带一个优先级，到哪个位子都用它，不按位子分别排。
9. 活动定名 **Campaign**；活动下的可执行单元定名 **投放项 / `Treatment`**。
10. **受众侧只提供「人群定义」一样东西**；投放项用它的方式只有两种——**枚举**（这批人是谁）和**判定**（这个人算不算）。触发器是「判定」的一个特例，不是第三种东西。
11. **一个投放项就一步**；多步靠事件串，投放项之间互不相识。
12. 因此**平台自己也要能产生事件**，不只是消费外部推来的事件。
13. 接受的代价：运营看不到一条完整的线，只能看到几个各自独立的投放项。
14. **「画布」在本模型中已不存在**——被事实 11、12 消掉了。`AGENTS.md` 高风险清单第 1、3 条需要另行修订。
15. **分流在投放项之上，不是投放项的一部分**——一个组对应「一套投放项」，可能 0 个、1 个或好几个。
16. **分桶**（随机切分，同一个人永不换组）和**条件分流**（按事实分，事实变了就该换）是**两件事**。
17. **条件分流不需要新概念**：它就是「一个人群定义 + 一个投放项」。
18. **平台自己的执行结果必须回流，成为受众服务的一个来源**——这是条件分流成立的前提。来源不再只有外部系统。
19. 回流延迟**小时级够用**；平台应在界面上拦住更短的配置。
20. **对照组（什么都不做的那组）必须在系统里存在**，否则事后无法把它和「压根不在人群里的人」分开。
21. **决策表放在投放项之上**，不放在里面。投放项保持「对一个人做一件事」不变；决策表只做路由，不执行。
22. 决策表**不需要新的执行机制**（每一行 = 人群定义 + 投放项），它值得存在只因为多保证三件事：**顺序、兜底、互斥**。
23. **「同一活动内两个投放项不能抢同一个位」这条要放宽为「人群互斥就允许」**——否则同一个位子上的 A/B 实验根本建不出来。（此条随「决策表放在上面」一并接受，因为 `T1`/`T2` 都要投同一个位。）
24. ~~**分桶的输入是人群定义，输出还是人群定义**，「再细分」是分桶套分桶。~~ **已推翻**——实验服务不产出人群定义，只产出**第几份**；人群定义把它当条件引用。所以「C 组 5000 人再细分」不是分桶套分桶，而是人群定义写成「分流 E 第 3 份 **且** 分流 F 第 1 份」。两个分流叠加，语义反而更清楚。
25. **放量也是分桶**，不是新机制；必须用分桶而非随机取样，否则放量不单调，先进来的人会被悄悄踢出。
26. **放量旋钮挂在活动上**，活动下所有投放项一起放量。
27. ~~**分桶不是独立组件**，是受众服务的能力（A7）。~~ **已推翻**——**分桶拆成独立子项目「实验服务」**，只管稳定分配。四个相关概念的归属见 [`system-boundaries.md`](system-boundaries.md)：「一次分流」归实验服务；「第 N 份」在受众服务眼里只是一个人群条件；分流单元与分桶算法归实验服务。
28. **每次分流默认各自打散**（实验服务负责），避免「永远的对照组」和样本重叠；**允许运营指定「跟某一次分流对齐」**。
29. 运营配的是**「跟哪次分流对齐」而不是「盐」**——盐一致但切法不同会得到不完全对齐的结果且不报错。
30. **实验服务管稳定分配 + 实验指标**（观测期、显著性、哪一份更好）——这些指标围着「份」建，离开分流无从谈起。实验和放量都是稳定分配的用法。
31. **运营平台的指标是另一个维度**：按投放项聚合，问「发了多少、成了多少」。与实验服务的指标**不是两套数据，是同一批事实的两个聚合维度**。
32. 因此**执行结果那条记录必须同时带上「哪个投放项」和「哪次分流的第几份」**，少一个就有一边算不出来。
33. **指标口径统一一处定义，两边引用**——各自定义会让数字对不上且不报错。
34. 三个子项目定名：**运营平台**、**受众服务 / `Audience Service`**、**实验服务 / `Experimentation Service`**；实验服务**现在就建独立 repo**。
35. **分流单元留字段不放开取值**（当前只允许 uid）；**跨租户隔离靠盐里带租户**，不是新机制；**指标口径是一份共享契约**，不是第四个服务。
36. **动作（`Action`）跟来源对称**：研发接入的能力清单，运营从中挑，不是投放项里的自由字段。
37. **不设统一的「内容」模型**——内容是动作的参数，一个动作一个说法。券种是外部券系统的标识，不包成平台自己的概念。
38. **额度、库存、对账归券系统**；本平台只负责发放、幂等、处理失败。据此收窄 `AGENTS.md` 高风险第 7 条：只有「发放逻辑」归本平台。
39. 已知代价：素材不是一等公民，**跨投放项按素材归因做不了**。
40. 三类动作都是跟外部系统打交道，但**方向不同**：短信、发券是我们调对方；资源位是对方调我们、我们返回一个 id。**资源位没有「发放成功」这回事。**
41. 外部系统的失败逻辑（库存不足等）归它们自己。**但幂等、回执关联、资格判定三件事推不出去**，仍是本平台的责任。
42. **下游必须幂等，不幂等的不接入**；超时按重试策略重试，仍失败则报异常。幂等键由本平台生成，**重试之间不变**。
43. 「下游幂等」是声明不是保证，**接入时需要验证手段**；资源位那类无法重试。
44. **执行失败的人在实验分析中仍算实验组**（ITT）——剔掉他们会破坏随机性，结论系统性偏乐观且不报错。
