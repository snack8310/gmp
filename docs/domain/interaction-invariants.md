# 不变量与平台介入时点

## 状态

**草稿。** 最后修订对应 issue #28。

本文档是 `docs/domain/` 的第一份**设计文档**。它不引入任何新的领域语义——每条不变量都追到既有的已确认事实，追不到的一律落在「待澄清问题清单」，不补。

## 这份文档补的是什么缺口

[`campaign-user-stories.md`](campaign-user-stories.md) 与 [`system-boundaries.md`](system-boundaries.md) 已经说清了**什么必须恒真**。但除事实 7 之外，没有任何一处说**平台在哪一刻介入**。

这个区别对本项目格外要紧，因为这些不变量有一个共同特征：**违反时不报错**。同一条约束，在配置时拦住和在运行时才发现，后果是两回事——后者往往等于「已经发出去了」，而触达不可撤回。

本文档把这三件事并列：不变量本身、违反时会怎样、平台在哪一刻介入。前两件是既有事实的重述与收拢，第三件是本文档做的决定。

## 概念与关系

引用方向单向，无环。

- **活动**引用一份**人群定义**，挂若干**投放项**，自带一个**优先级**与一个**放量旋钮**。
- **投放项**引用一份**人群定义**（或一个触发器、一个准入条件）与一个**动作**。投放项之间互不相识，只通过事件间接相连。
- **决策表**位于投放项之上，每一行是「一个人群定义 + 一个投放项」。
- **人群定义**可以把「某次分流的第几份」当成一个普通条件引用，与「消费满 100」同类。
- **一次分流**只产出份号，不产出人群定义。再细分是条件叠加，不是分流套分流。
- **执行结果**回流后成为受众服务的一个来源——这是条件分流成立的前提。

## 不变量

每条写成可证伪的断言。「平台在哪一刻介入」分三档：**当场拦住**（配置保存不了）、**提醒**（配置合法，但后果静默，须显式告知）、**机制保证**（不依赖运营记得，形状本身使它成立）。

## 状态机

**有生命周期且已定的只有两个**，其余在本文档成文时尚未表态。

**一次分流的定义**

```
（不存在） → 已建立 ──改切法/比例/染色开关──→ 同一标识下的新修订
                 └──────────────────────────→ （定义本身不可就地修改）
```

定义不可变，改定义即在同一分流标识下新建一个修订。分流标识跨修订稳定——染色按标识归档，否则「定义变了、已染色的人不动」不成立。非法流转：就地修改一个已被用于分配的定义。

**出处与诚实性边界**：本目录此前没有这条。「定义不可就地修改」由人工在 issue #23 所属会话中裁定，「标识跨修订稳定」是它与 `system-boundaries.md` 染色一节（「定义变了 → 已染色的人不动」）合起来的唯一自洽读法，已随 PR #27 落进 `gmp-core` 的实现。**仓库内可验证的只有「谁在何时写下了这条引用」**，与 `business-scenarios.md`「确认记录」同一写法。

**一个键在某次分流中的染色**

```
（未染色） ──首次分配且该分流开启染色──→ 已染色（份号与当时算法版本固化）
```

首写者胜，之后重复分配不产生第二条记录，也不改变份号。非法流转：覆盖一条已有染色记录。「只读问一下」不触发任何流转。

**活动与投放项的状态机尚未表态。** 故事 20、21、22 提到「停掉」，并要求停的时候能决定已进来还没走完的人是继续走完还是立刻停下——这蕴含至少存在一个「进行中」与一个「已停」，但状态集合、合法流转、以及停掉之后已在途执行的处置**都没有被确认过**。按「不得臆造」，此处不补，见待澄清问题清单。

## 边界与非目标

- **本文档不定视觉样式**：配色、字体、构件形态、界面布局不在此，也不在本目录——按 [`README.md`](README.md) 的「可判定的边界」，那些约束的是「它内部长什么样」。它们落在 [`docs/product/`](../product/)；三档介入时点叫什么、各自意味着什么仍归本文档，那边只规定它们长什么样。
- **不定接口协议、序列化格式、存储结构**。
- **不新增领域语义**。本文档是对既有已确认事实的收拢与补齐，不是对它们的修订；与四份既有文档冲突时以那四份为准。
- **受众服务与实验服务没有人类界面**，它们是被调用的。本文档所说的「平台介入时点」全部发生在运营平台这一侧，或发生在服务的接口契约上。
- **不覆盖未表态项**：退订与免打扰时段的归属、Holdout 是否纳入——两者在 `campaign-user-stories.md` 中明确记为未表态，此处不推进。

## 决策记录

### 介入时点分三档，而不是「校验通过 / 不通过」两档

**选了**：当场拦住 / 提醒 / 机制保证。

**否决「一律当场拦住」**：不变量 3（对照组必须存在）与 4（兜底行）都可能有正当的例外——运营确实可能先建一份空的、稍后再挂投放项。一律硬拦会让人去找绕过的办法，而绕过之后就再也没有提醒了。

**否决「一律提醒」**：不变量 6（回流延迟）与 7（对齐切法）无论如何都不该放行——放行之后的失效是静默的，且已经发出去的触达不可撤回。提醒在这里等于没有。

**「机制保证」不是第三档强度，是另一种东西**：它意味着违反这条不变量在形状上不可表达。不变量 1、2、18 都是这样——界面不提供随机取样、旋钮不出现在投放项层，运营想违反也无从下手。**能做成这一档的就不该退到前两档**，这与根 `AGENTS.md`「约束落地优先级」同源。

### 「平台在哪一刻介入」写进规格真源，而不是留给各自实现

**否决「这是实现细节，各子项目自己定」**：同一条不变量，运营平台在配置时拦、实验服务在运行时拒，两边都「实现了」它，而运营的体验是配完保存成功、跑起来才失败。介入时点决定的是**职责归属与契约形状**，不是内部做法。事实 7 已经是这个写法的先例——它把「建的时候就拦住，不留到运行时」写成了已确认事实。

### 不变量清单以「会静默失效」为准入，不收全部已确认事实

**判据**：一条已确认事实进入本清单，须同时满足——它描述一种必须恒真的性质，且违反它时系统不会报错。

**否决「把五十多条事实全部收进来」**：那样本清单会变成事实清单的副本，读者无从判断哪些是真正危险的。承接情况见下节，判定不适用的一并登记，不沉默略过。
