# 系统边界：拆成哪几个子项目

## 这份文档是什么

本项目是多 repo 的。这份文档记录**哪些东西归哪个子项目**，以及**什么跨边界**。

规则同其他需求文档：只写归属与边界，**不写实现**。

## 拆法

拆成系统内的**子项目 / 独立 repo**，不是独立运行的产品。

```
              运营平台
   活动、投放项、决策表、优先级、放量旋钮
        │                        │
        │ 引用                    │ 引用
        ▼                        ▼
   受众服务  ────── 引用 ──────→  分流服务
 来源、人群定义                 一次分流的定义
 枚举、判定                     份数、比例、盐、对齐
                                稳定分配：id → 第几份
```

**依赖单向、无环。**

## 三个子项目各自回答什么问题

| 子项目 | 它回答的唯一问题 |
|---|---|
| **运营平台** | 「要对这些人做什么」 |
| **受众服务** | 「这个人是谁 / 这批人是谁」 |
| **分流服务** | 「这个 id 落在第几份」 |

## 受众服务与分流服务之间的接缝

**关键转换**：

> 「分流 E 的第 2 份」在受众服务眼里，**就是一个普通的人群条件**，跟「消费满 100」是同一类东西。

所以受众服务**不需要懂实验**，只需要能问一句「这个 id 在分流 E 里是第几份」。

- 人群定义写「消费满 100 **且** 分流 E 第 2 份」，跟写「消费满 100 且 女性」没有区别。
- 枚举同样成立：先枚举「消费满 100」，再逐个问份号过滤。
- 「再细分」不是分流套分流，而是**条件叠加**：「分流 E 第 3 份 且 分流 F 第 1 份」。

## 差点成环的那条，和它为什么没成环

执行结果回流（活动文档事实 18）：运营平台调受众服务要人，受众服务又消费运营平台的执行结果当来源——方向是反的。

**不成环，是因为运营平台不被调用，它只往外发事件**（事实 12）。受众服务把这些事件当成一个普通来源消费，从不反向调用运营平台。

选「多步靠事件串」的时候，顺手把这个循环依赖解掉了。

## 跨边界的东西，归属定死

| 东西 | 归谁 | 理由 |
|---|---|---|
| **「一次分流」的定义**（份数、比例、盐、对齐） | 分流服务 | 「同一次分流的两份天然互斥」由它证明。放宽后的抢位子规则（活动事实 23）靠这个判断 |
| **「第 N 份」作为人群条件** | 受众服务 | 它只是人群定义里的一个条件，跟性别、消费额同类 |
| **放量旋钮的值** | 运营平台（挂在活动上） | 「当前纳入哪几份」的判断在受众服务，值在运营平台 |
| **人群定义** | 受众服务 | 由运营平台的界面创建，但存放与求值都在受众服务 |
| **指标口径、观测期、显著性** | **未定** | 分流服务明确不管。见 C7 |

## 分流服务的范围：只管稳定分配

**已确认**：分流服务只提供「把一个 id 稳定地分到 N 份」这个通用能力。

- **实验**和**放量**都只是它的用法。放量不是实验（没有对照组、没有指标、没有结论），但机制上同样需要稳定分配。
- **指标口径、观测期、显著性不归它管。**

## 开放给第三方时，会推翻一条已定的事实

活动文档事实 27 原写「分流单元已定死为 uid」，理由是"平台只认 uid"。

**那个理由只对运营平台成立。** 第三方可能要按设备、按订单、按会话分。所以：

> **一旦分流服务对第三方开放，分流单元就从「定死」变成「必须可配置」。**

这不是小改动——它会影响一次分流的定义长什么样。**若确定以后要开放，这个口子现在就得留**；等做完一版再改，已有分流数据要迁，而分流数据一迁，历史实验的分组全变，之前的结论作废。

同理「每次分流默认打散」在跨租户下更要紧：你的实验和第三方的实验若共用分流服务却不打散，**两边样本会重叠，且谁都不知道**。
