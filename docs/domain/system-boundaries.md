# 系统边界：拆成哪几个子项目

## 这份文档是什么

本项目是多 repo 的。这份文档记录**哪些东西归哪个子项目**，以及**什么跨边界**。

规则同其他需求文档：只写归属与边界，**不写实现**。

## 拆法

拆成系统内的**子项目 / 独立 repo**，不是独立运行的产品。

```
              运营平台
   活动、投放项、决策表、优先级、放量旋钮
        │                        │
        │ 引用                    │ 引用
        ▼                        ▼
   受众服务  ────── 引用 ──────→  实验服务
 来源、人群定义                 一次分流：份数、比例、盐、对齐
 枚举、判定                     稳定分配：id → 第几份
                                实验指标：观测期、显著性

        ┌──────────────────────────────┐
        │  指标口径（共享契约，无运行时）  │  ← 两个服务都读
        └──────────────────────────────┘
```

**「实验服务」这个名字的由来**：定范围时它只管稳定分配，后来加上了实验指标，名字跟着变。行业里 Experimentation Platform 管的正是这一套——分配 + 指标 + 显著性 + 放量（Statsig、LaunchDarkly 都这么包），所以放量归它不别扭。

**「一次分流」和「实验」不是一回事**：分流是机制（把 id 分成 N 份），实验是分流 + 指标。放量是一次分流，但不是实验。

**依赖单向、无环。**

## 三个子项目各自回答什么问题

| 子项目 | 它回答的唯一问题 |
|---|---|
| **运营平台** | 「要对这些人做什么」 |
| **受众服务** | 「这个人是谁 / 这批人是谁」 |
| **实验服务** | 「这个 id 落在第几份」 |

## 受众服务与实验服务之间的接缝

**关键转换**：

> 「分流 E 的第 2 份」在受众服务眼里，**就是一个普通的人群条件**，跟「消费满 100」是同一类东西。

所以受众服务**不需要懂实验**，只需要能问一句「这个 id 在分流 E 里是第几份」。

- 人群定义写「消费满 100 **且** 分流 E 第 2 份」，跟写「消费满 100 且 女性」没有区别。
- 枚举同样成立：先枚举「消费满 100」，再逐个问份号过滤。
- 「再细分」不是分流套分流，而是**条件叠加**：「分流 E 第 3 份 且 分流 F 第 1 份」。

## 差点成环的那条，和它为什么没成环

执行结果回流（活动文档事实 18）：运营平台调受众服务要人，受众服务又消费运营平台的执行结果当来源——方向是反的。

**不成环，是因为运营平台不被调用，它只往外发事件**（事实 12）。受众服务把这些事件当成一个普通来源消费，从不反向调用运营平台。

选「多步靠事件串」的时候，顺手把这个循环依赖解掉了。

## 跨边界的东西，归属定死

| 东西 | 归谁 | 理由 |
|---|---|---|
| **「一次分流」的定义**（份数、比例、盐、对齐） | 实验服务 | 「同一次分流的两份天然互斥」由它证明。放宽后的抢位子规则（活动事实 23）靠这个判断 |
| **「第 N 份」作为人群条件** | 受众服务 | 它只是人群定义里的一个条件，跟性别、消费额同类 |
| **放量旋钮的值** | 运营平台（挂在活动上） | 「当前纳入哪几份」的判断在受众服务，值在运营平台 |
| **人群定义** | 受众服务 | 由运营平台的界面创建，但存放与求值都在受众服务 |
| **观测期、显著性、哪一份更好** | 实验服务 | 这些指标围着「份」建，离开分流无从谈起 |
| **发了多少、送达多少、成了多少** | 运营平台 | 它自己发的，它自己知道 |
| **指标口径的定义**（什么算下单 / 活跃） | **唯一一处**，两边引用 | 各自定义会导致数字对不上且不报错 |

## 实验服务的范围

**已确认**：实验服务管**稳定分配 + 实验指标**。

- **稳定分配**：把一个 id 稳定地分到 N 份。**实验**和**放量**都是它的用法（放量不是实验——没有对照组、没有结论——但机制上同样需要稳定分配）。
- **实验指标**：观测期、显著性、哪一份更好。理由是这些指标本来就是围着分流建的，离开「份」无从谈起。

## 两种指标：同一批事实，两个聚合维度

不是两套数据。

| | 实验服务的指标 | 运营平台的指标 |
|---|---|---|
| **按什么聚合** | 一份（arm） | 一个投放项 |
| **问的问题** | 哪个更好？差异显著吗？ | 发出去了吗？成了多少？ |
| **形态** | 比较 + 统计推断 | 计数 + 汇总 |
| **数据来自** | **业务结果**（下单、留存）——不是运营平台产生的 | **执行结果**——运营平台自己产生的 |

最后一行是这两者能分开的根据：运营平台自己发的东西，它自己就知道结果；但「这组人有没有多下单」它不知道，那得从业务系统来。**所以实验服务需要独立于运营平台去拿业务结果。**

### 由此得出的硬要求

> **执行结果那条记录，必须同时带上「哪个投放项」和「哪次分流的第几份」。**

少任何一个就有一边算不出来：只带投放项，实验服务没法把结果归到某一份，算不了显著性；只带份号，运营平台答不了「这个投放项发得怎么样」。

### 指标计算走数据流，不走服务调用

实验服务要算指标就得拿业务结果，而业务数据源受众服务已经接了。**若实验服务去调受众服务就成环**（受众服务本来就依赖实验服务）。

不成环的条件与「执行结果回流」相同：**实验服务像消费一个普通数据源那样消费业务结果，不反向调用受众服务。**

### 指标口径只有一处定义

**已确认**：什么算「下单」、什么算「活跃」，**统一一处定义，实验服务与运营平台都引用它**。

各自定义的后果是两边数字对不上，**而且不报错**——运营通常是在对不上数的那天才发现，然后就再也不信这个系统了。根 `AGENTS.md` 高风险清单第 5 条点名的「指标口径」正是此项。

## 开放给第三方：一条曾被担心的事，已被「分流键」消除

曾判断「分流单元定死为 uid」会在开放给第三方时被推翻（第三方要按设备、按订单、按会话分），因而需要提前留口子，否则要迁分流数据、历史实验分组全变。

**「分流键」的引入让这个担心不再成立**——服务只认不透明的键，粒度由调用方决定，没有任何东西需要留口子或迁移。

**仍然成立的是打散**：你的实验与第三方的实验若共用实验服务却不打散，**两边样本会重叠，且谁都不知道**。跨租户隔离靠盐里带租户（B4）。

## 抽象模型：先不接数据库，用场景跑通

**已确认**：先做一套**抽象模型**（领域模型 + 接口 + 内存实现），不接真实数据库与外部链路，用 [`business-scenarios.md`](business-scenarios.md) 的五个场景跑出真实结果，把它们作为**核心模型的回归用例**。技术栈倾向 Go，但方案与语言无关。

**放在单独一个 repo，定名 `gmp-core`**。选 `core` 而非 `domain` / `model`：它里面不只有领域模型，还有内存实现与场景测试。

### 内部必须按依赖方向分层

```
抽象模型 repo
├── experimentation/   不依赖任何其他包 ← 未来可整块搬走
├── audience/          只依赖 experimentation
├── campaign/          只依赖 audience
└── scenarios/         五个场景，依赖全部三者
```

**硬约束：`experimentation` 不得依赖另外两个包。** 理由：实验服务未来可能独立开放给第三方，而它是最底层、本就不依赖任何人。这条只写文档会被静默穿透——**穿透后不报错**，直到某天想搬走才发现搬不动。应固化为「只编译 `experimentation` 自身」的检查。

**要盯住的**：实验服务的接口是 `(分流键, 一次分流的定义) → 第几份`，**只认键、不认人群**，这是它能对外开放的前提。**不得为图方便加「按人群分流」的便利接口**——那会把它绑死在本项目里。

### 分流键：实验服务里没有 uid 这个概念

**已确认**：实验服务只认一个不透明的**分流键（`AssignmentKey`）**，对它做哈希。**它是什么、代表谁，服务完全不关心，由调用方决定。**

- 受众服务传 uid → 按人分
- 第三方传设备号 → 按设备分
- 传订单号 → 按订单分

服务本身一行不变。

**这让 B3 消失而不是被回答**：原答案是「留个字段记录用的是什么单元，当前只允许 uid」；现在**根本不需要那个字段**，「分流单元可配置」这个需求也一起没有了——没有东西需要配。

否决 `BID` / `Business ID` 这个名字：**「Business」三个字本身就是一层业务含义**，与「不引入任何业务含义」的初衷相拧。在本平台里分流键确实等于 uid，但那是**调用方的事实**，不该写进服务的词汇表。

**一个责任因此转移了**：「跟某次分流对齐」若两次传进去的不是同一类东西（一次 uid、一次设备号），对齐即无意义——而**分流服务不知道类型，拦不住**。这个责任归调用方：受众服务知道自己传的是 uid，由它保证对齐的两次都是 uid。服务保持纯粹，代价由知道语义的一方承担。

**由此，实验服务成为一个纯函数**：全部输入是 `(分流键, 一次分流的定义)`，全部输出是一个份号，**零业务概念**。这不只是它能对外开放的必要条件，基本已是充分条件。

### 场景测试跟着分层

| 场景 | 归哪儿 |
|---|---|
| 只涉及实验服务的（分桶稳定性、放量单调性） | **跟着 `experimentation` 走**，未来一起搬，不重写 |
| 跨三者的（场景 ③ 同时踩抢位、判定、分桶） | 留在 `scenarios/`，即 B7 所指 |

### 内存实现测得出来 / 测不出来

| 测得出来 | 测不出来 |
|---|---|
| 分桶稳定性、放量单调性 | **回流延迟**——内存里事件瞬时到达，「发完 10 分钟拿到旧数据」根本不会出现 |
| 决策表的顺序 / 兜底 / 互斥 | **并发**——单线程跑不出竞态 |
| 抢位优先级 + 人群互斥放行 | **下游是否真幂等**——假 downstream 写成幂等它就是幂等 |
| ITT、事件串、幂等键贯穿三段 | **规模**——「枚举可跑十分钟、判定必须快」是性能约束 |
| 依赖方向无环（可做成编译期约束） | |

**前两项不是天生测不了，取决于怎么设计**：

> **时间与事件投递必须做成可注入的**——不用真实时钟，投放项之间不直接函数调用。

这样测试里就能拨快时钟、让事件延迟或乱序到达，那两类最危险的失效立刻可测。用了真实时钟和直接调用，以后想补得把所有路径拆一遍。**这是本方案里唯一「现在不做以后很贵」的点。**

### Go 的一个具体影响

Go 接口是隐式实现的，没有 `implements`。好处是领域层可以完全不依赖实现；代价是「这个实现符合契约」编译期查不全，需要**契约测试**——同一组测试同时跑在内存实现和真实实现上。

这正是 `AGENTS.md` 高风险第 10 条点名的东西（「测试在一种实现下全绿，线上跑的是另一种」）。**只有现在就用内存实现做第一版，契约测试才是免费的。**

| **B6** | 指标口径的形式、位置、修改权限 | **声明式清单**（不是代码），每项写：名字、业务含义、口径、归属人。放 **`gmp-core` 的独立目录**——引用方与抽象模型相同，但生命周期不同（数据团队改「活跃」的定义时不该动领域模型）。**口径变更按破坏性变更处理**（版本化、兼容期、`CHANGELOG`） |

| **B8** | 抽象模型 repo 的名字 | **`gmp-core`** |
| **B9** | 子项目与抽象模型的关系 | **分层，不一刀切**（见下） |

### B6 的理由：为什么改口径算破坏性变更

不是流程洁癖。**改一个指标的口径，等于让所有历史数字的含义变了**——上周的转化率与这周的不再可比，而**没有任何地方会报错**。这与改一个对外接口是同一性质的事，因此适用同一套规则。

「唯一一处」若谁都能随手改，等于没有唯一。

### B9：实验服务的依赖方向是反的

| | 抽象模型阶段 | 落地之后 |
|---|---|---|
| **实验服务** | 在 `gmp-core` 的 `experimentation/` 包里，**不 import 另外两个** | **方向反转**：它自己持有接口定义、保持**零依赖**，由 `gmp-core` 引用它 |
| **受众服务** | `audience/` 包 | 引用 `gmp-core` |
| **运营平台** | `campaign/` 包 | 引用 `gmp-core` |

否决「三个都直接引用 `gmp-core`」：那会把实验服务绑死在 `gmp-core` 上，**未来搬不走**，与「可开放给第三方」的目标直接冲突。

否决「三个都各自定义 + 契约测试」：接口定义会有四份（含 `gmp-core`），漂移只靠契约测试兜，成本高于收益。

**那条「`experimentation` 不许 import 另外两个」的分层规则，作用正是让这次方向反转成为可能**——它若偷偷依赖了别人，到时候搬不走，而且在那天之前不会有任何报错。
