# 系统边界：拆成哪几个子项目

## 这份文档是什么

本项目是多 repo 的。这份文档记录**哪些东西归哪个子项目**，以及**什么跨边界**。

规则同其他需求文档：只写归属与边界，**不写实现**。

## 拆法

拆成系统内的**子项目 / 独立 repo**，不是独立运行的产品。

```
              运营平台
   活动、投放项、决策表、优先级、放量旋钮
        │                        │
        │ 引用                    │ 引用
        ▼                        ▼
   受众服务  ────── 引用 ──────→  实验服务
 来源、人群定义                 一次分流：份数、比例、盐、对齐
 枚举、判定                     稳定分配：id → 第几份
                                实验指标：观测期、显著性

        ┌──────────────────────────────┐
        │  指标口径（共享契约，无运行时）  │  ← 两个服务都读
        └──────────────────────────────┘
```

**「实验服务」这个名字的由来**：定范围时它只管稳定分配，后来加上了实验指标，名字跟着变。行业里 Experimentation Platform 管的正是这一套——分配 + 指标 + 显著性 + 放量（Statsig、LaunchDarkly 都这么包），所以放量归它不别扭。

**「一次分流」和「实验」不是一回事**：分流是机制（把 id 分成 N 份），实验是分流 + 指标。放量是一次分流，但不是实验。

**依赖单向、无环。**

## 三个子项目各自回答什么问题

| 子项目 | 它回答的唯一问题 |
|---|---|
| **运营平台** | 「要对这些人做什么」 |
| **受众服务** | 「这个人是谁 / 这批人是谁」 |
| **实验服务** | 「这个 id 落在第几份」 |

## 受众服务与实验服务之间的接缝

**关键转换**：

> 「分流 E 的第 2 份」在受众服务眼里，**就是一个普通的人群条件**，跟「消费满 100」是同一类东西。

所以受众服务**不需要懂实验**，只需要能问一句「这个 id 在分流 E 里是第几份」。

- 人群定义写「消费满 100 **且** 分流 E 第 2 份」，跟写「消费满 100 且 女性」没有区别。
- 枚举同样成立：先枚举「消费满 100」，再逐个问份号过滤。
- 「再细分」不是分流套分流，而是**条件叠加**：「分流 E 第 3 份 且 分流 F 第 1 份」。

## 差点成环的那条，和它为什么没成环

执行结果回流（活动文档事实 18）：运营平台调受众服务要人，受众服务又消费运营平台的执行结果当来源——方向是反的。

**不成环，是因为运营平台不被调用，它只往外发事件**（事实 12）。受众服务把这些事件当成一个普通来源消费，从不反向调用运营平台。

选「多步靠事件串」的时候，顺手把这个循环依赖解掉了。

## 跨边界的东西，归属定死

| 东西 | 归谁 | 理由 |
|---|---|---|
| **「一次分流」的定义**（份数、比例、盐、对齐） | 实验服务 | 「同一次分流的两份天然互斥」由它证明。放宽后的抢位子规则（活动事实 23）靠这个判断 |
| **「第 N 份」作为人群条件** | 受众服务 | 它只是人群定义里的一个条件，跟性别、消费额同类 |
| **放量旋钮的值** | 运营平台（挂在活动上） | 「当前纳入哪几份」的判断在受众服务，值在运营平台 |
| **人群定义** | 受众服务 | 由运营平台的界面创建，但存放与求值都在受众服务 |
| **观测期、显著性、哪一份更好** | 实验服务 | 这些指标围着「份」建，离开分流无从谈起 |
| **发了多少、送达多少、成了多少** | 运营平台 | 它自己发的，它自己知道 |
| **指标口径的定义**（什么算下单 / 活跃） | **唯一一处**，两边引用 | 各自定义会导致数字对不上且不报错 |

## 实验服务的范围

**已确认**：实验服务管**稳定分配 + 实验指标**。

- **稳定分配**：把一个 id 稳定地分到 N 份。**实验**和**放量**都是它的用法（放量不是实验——没有对照组、没有结论——但机制上同样需要稳定分配）。
- **实验指标**：观测期、显著性、哪一份更好。理由是这些指标本来就是围着分流建的，离开「份」无从谈起。

## 两种指标：同一批事实，两个聚合维度

不是两套数据。

| | 实验服务的指标 | 运营平台的指标 |
|---|---|---|
| **按什么聚合** | 一份（arm） | 一个投放项 |
| **问的问题** | 哪个更好？差异显著吗？ | 发出去了吗？成了多少？ |
| **形态** | 比较 + 统计推断 | 计数 + 汇总 |
| **数据来自** | **业务结果**（下单、留存）——不是运营平台产生的 | **执行结果**——运营平台自己产生的 |

最后一行是这两者能分开的根据：运营平台自己发的东西，它自己就知道结果；但「这组人有没有多下单」它不知道，那得从业务系统来。**所以实验服务需要独立于运营平台去拿业务结果。**

### 由此得出的硬要求

> **执行结果那条记录，必须同时带上「哪个投放项」和「哪次分流的第几份」。**

少任何一个就有一边算不出来：只带投放项，实验服务没法把结果归到某一份，算不了显著性；只带份号，运营平台答不了「这个投放项发得怎么样」。

### 指标计算走数据流，不走服务调用

实验服务要算指标就得拿业务结果，而业务数据源受众服务已经接了。**若实验服务去调受众服务就成环**（受众服务本来就依赖实验服务）。

不成环的条件与「执行结果回流」相同：**实验服务像消费一个普通数据源那样消费业务结果，不反向调用受众服务。**

### 指标口径只有一处定义

**已确认**：什么算「下单」、什么算「活跃」，**统一一处定义，实验服务与运营平台都引用它**。

各自定义的后果是两边数字对不上，**而且不报错**——运营通常是在对不上数的那天才发现，然后就再也不信这个系统了。根 `AGENTS.md` 高风险清单第 5 条点名的「指标口径」正是此项。

## 开放给第三方时，会推翻一条已定的事实

活动文档事实 27 原写「分流单元已定死为 uid」，理由是"平台只认 uid"。

**那个理由只对运营平台成立。** 第三方可能要按设备、按订单、按会话分。所以：

> **一旦实验服务对第三方开放，分流单元就从「定死」变成「必须可配置」。**

这不是小改动——它会影响一次分流的定义长什么样。**若确定以后要开放，这个口子现在就得留**；等做完一版再改，已有分流数据要迁，而分流数据一迁，历史实验的分组全变，之前的结论作废。

同理「每次分流默认打散」在跨租户下更要紧：你的实验和第三方的实验若共用实验服务却不打散，**两边样本会重叠，且谁都不知道**。

## B1–B5 已定

| # | 问题 | 结论 | 理由 |
|---|---|---|---|
| **B1** | 这个子项目叫什么 | **实验服务 / `Experimentation Service`** | 范围已含实验指标，「分流服务」低估了那一半。行业里 Experimentation Platform 正是这个范围 |
| **B2** | 现在建 repo 还是先做模块 | **现在就建独立 repo** | 边界已想清楚，建 repo 成本低；而「在同一个 repo 里留好口子」**没有任何机制保证**，人一忙就穿透。对应 `AGENTS.md`「能用结构固化就别靠纪律」 |
| **B3** | 分流单元现在可配置吗 | **留位置，不放开取值**——每次分流记下它用的是什么单元，但当前只允许 uid | 不是二选一。留个字段几乎不要钱；晚了要迁分流数据，而**分流数据一迁，历史实验分组全变、结论作废** |
| **B4** | 跨租户隔离现在设计吗 | **不需要额外设计——盐的生成里带上租户标识即可** | 「每次分流默认各自打散」已经定了，跨租户隔离是它的一个应用，不是新机制。只要把「盐怎么生成」的口径定对 |
| **B5** | 指标口径放哪 | **一份共享契约，不是第四个服务**——两个服务都读它 | 放受众服务会成环（受众服务已依赖实验服务）；放实验服务概念上别扭（「实验服务定义什么算下单」）。**契约没有运行时，不产生依赖环** |
