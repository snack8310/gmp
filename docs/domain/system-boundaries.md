# 系统边界：拆成哪几个子项目

## 这份文档是什么

本项目是多 repo 的。这份文档记录**哪些东西归哪个子项目**，以及**什么跨边界**。

规则同其他需求文档：只写归属与边界，**不写实现**。

## 拆法

用户已确认：拆成系统内的**子项目 / 独立 repo**，不是独立运行的产品。

```
运营平台
  活动、投放项、决策表、优先级、放量旋钮
        │
        │ 引用
        ▼
受众服务  Audience Service
  来源、人群定义、枚举、判定、人群切分、「一次分桶」
        │
        │ 引用
        ▼
分配服务  （待命名）
  (一个 id, 一次分桶的定义) → 落在哪个桶
```

**依赖单向、无环。** 运营平台不需要知道分配服务的存在，它只跟受众服务打交道。

## 差点成环的那条，和它为什么没成环

执行结果回流（活动文档事实 18）：运营平台调受众服务要人，受众服务又消费运营平台的执行结果当来源——方向是反的。

**不成环，是因为运营平台不被调用，它只往外发事件**（事实 12）。受众服务把这些事件当成一个普通来源消费，从不反向调用运营平台。

选「多步靠事件串」的时候，顺手把这个循环依赖解掉了。

## 跨边界的东西，归属定死

| 东西 | 归谁 | 理由 |
|---|---|---|
| **「一次分桶」这个对象** | 受众服务 | 它要证明互斥（抢位子规则靠它）、要被放量引用。分配服务只提供算法，不该知道「这次分桶属于哪个人群」 |
| **放量旋钮的值** | 运营平台（挂在活动上） | 但「当前纳入哪几个桶」的判断在受众服务 |
| **人群定义** | 受众服务 | 由运营平台的界面创建，但存放与求值都在受众服务 |
| **分桶算法与盐** | 分配服务 | 「跟哪次分桶对齐」是受众服务翻译出来的意图，分配服务只认盐与切法 |

## 分配服务开放给第三方时，会推翻一条已定的事实

活动文档事实 27 写着「**分流单元已定死为 uid**」，理由是"平台只认 uid，没有第二种粒度"。

**那个理由只对运营平台成立。** 第三方可能要按设备、按订单、按会话分。所以：

> **一旦分配服务对第三方开放，分流单元就从「定死」变成「必须可配置」。**

这不是小改动——它会影响分桶定义长什么样。**若确定以后要开放，这个口子现在就得留**；等做完一版再改，已有分桶数据要迁。

同理，「每次分桶默认打散」（事实 28）在跨租户场景下更要紧：你的实验和第三方的实验若共用分配服务却不打散，**两边样本会重叠，且谁都不知道**。租户隔离要在一开始想清楚。
