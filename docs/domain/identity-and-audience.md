## 2. 名词表

| 中文名 | 英文名 | 定义 |
|---|---|---|
| 主体 | Subject | 可被圈选、被触达、被授予权益的对象。本项目中主体恒等于一个用户标识 |
| 用户标识 | UserId | 平台内部签发的唯一主标识。主体的主键 |
| 身份别名 | IdentityAlias | 一个 `(标识域, 值)` 二元组，指向某个用户标识。手机号、设备号、各渠道账号都是别名 |
| 标识域 | IdentityDomain | 别名值的取值空间与解释规则。决定该域的值是否可变、是否可验证、能否作为送达地址 |
| 送达地址 | DeliveryAddress | 可作为触达终点的别名。送达地址一定是别名，别名不一定是送达地址 |
| 继任标识 | SuccessorUserId | 账号合并后，被归并方指向的存续用户标识 |
| 名单定义 | AudienceDefinition | 「怎么圈出这批人」的稳定描述。构成为：来源接入 + 圈选规则 + 名单模式 + 求值调度 + 版本有效期 + 生命周期状态。此为封闭枚举，全文不得引用枚举外的属性 |
| 名单版本 | AudienceVersion | 名单定义的一次求值结果，不可变。即高风险清单第 4 条所称的「快照」 |
| 求值输入指纹 | EvaluationInputDigest | 一次求值所依赖的全部输入的可比较摘要，用于判定两次求值是否应当同结果 |
| 名单模式 | AudienceMode | 静态或动态，决定名单定义产生版本的方式 |
| 求值调度 | EvaluationSchedule | 名单定义产生新版本的时机。动态模式必须声明；静态模式恒为「仅生效时一次」，不可另行声明 |
| 版本有效期 | VersionValidity | 名单版本自求值时点起可被**新执行**绑定的时长。到期即进入失效态。具体取值口径见待澄清项 O8 |
| 解析后主体 | ResolvedSubject | 执行时点，名单版本中的成员沿继任链解析后得到的存续用户标识。见 3.5 |

### 2.1 概念关系

引用方向单向，不成环：

```
标识域 ──定义取值规则──> 身份别名 ──N:1 指向──> 用户标识 ──继任──> 用户标识
                            │                        ▲
                       （子集）                      │（成员）
                            ▼                        │
                       送达地址              名单版本 ─┘
                                                 ▲
                                            （求值产生）
                                                 │
                                            名单定义 ──引用──> 来源
```

- 名单版本引用用户标识，**不引用**别名或送达地址（I2）。
- 执行引用名单版本，**不引用**名单定义（I3）。
- 送达地址由用户标识在执行时反向解析得到，不被任何持久概念持有。

## 3. 用户身份

### 3.1 主标识

**平台内部签发的用户标识（UserId）是主体的唯一主键。**

- 用户标识由平台签发，**不可变、不回收、不复用**。
- 一个用户标识恒等于一个主体。不存在「没有用户标识的主体」。
- 所有下游模型——名单成员、分桶输入、幂等键构成、权益归属、执行记录——一律以用户标识为准，不得以任何别名替代。

**代价（已知并接受）**：外部导入的名单、未登录场景的候选人群，必须先解析到用户标识才能进入名单；解析不到的条目不进入名单版本，且必须在求值结果中可见地记为「未解析」，不得静默丢弃。

### 3.2 标识域与别名

别名是 `(标识域, 值) → 用户标识` 的映射。每个标识域必须显式声明四项属性，缺一不可：

| 属性 | 含义 | 为什么必须声明 |
|---|---|---|
| 唯一性 | 同一时刻一个值是否只能指向一个用户标识 | 决定能否用作反查入口 |
| 可变性 | 值是否会在主体不变的前提下改变（如换号） | 决定是否需要解绑 / 重绑流程 |
| 可验证性 | 平台是否验证过该值确实属于该主体 | 决定能否用作送达地址 |
| 可送达性 | 该域的值能否作为触达终点 | 决定是否进入送达地址解析 |

**本轮不枚举具体标识域。** 具体域清单（各渠道账号、手机号、设备号等）依赖渠道接入协议，属触达模型的范围；本模型只约束「任何标识域必须声明上述四项」。这是有意的边界，不是遗漏——见第 10 节待澄清项 O1。

### 3.3 映射基数

- 一个用户标识可以拥有**多个**别名，同一标识域内也可以有多个（1:N）。
- 一个别名在任一时刻**至多**指向一个存续的用户标识（N:1）。
- 因此整体是 N:1，不是 N:N。跨域归并的结果只能是「多个别名指向同一个用户标识」，不能是「一个别名指向多个用户标识」。

### 3.4 身份变更与解释时点

**名单版本只存用户标识；送达地址在每次执行时实时解析。**

三类身份变更的语义由此确定：

| 变更 | 对用户标识 | 对别名 | 对已冻结的名单版本 | 对已产生的执行记录 |
|---|---|---|---|---|
| 换号 | 不变 | 旧别名解绑，新别名绑定 | 不变，成员仍在 | 保留原记录。后续执行解析到新地址 |
| 注销 | 进入注销态，不删除 | 全部解绑 | 不变，成员仍在 | 保留原记录。后续执行解析不到地址，判定为不可送达 |
| 合并 | 被归并方进入已归并态，记录继任标识 | 别名改指继任标识 | **不变，不回填** | 保留原用户标识不改写 |

三条推论，都是有意为之：

1. **不可送达是执行时的判定结果，不是名单的错误。** 名单版本包含一个注销用户是合法的；执行时解析不到地址、跳过该主体，同样是合法的。把注销判定提前到圈选期，会让名单版本失去可复现性。
2. **历史名单版本永不回填。** 合并发生后，已有版本中的旧用户标识保持原样。回填历史版本会命中高风险清单第 12 条——已完成的流程可能被重新拉起，已发出的触达可能再发一次。
3. **继任链在执行时解析，不在名单中展开。** 已归并的用户标识不再作为**新**名单版本的成员出现；旧版本中的它，执行时沿继任链解析到存续主体。继任链必须无环且有限。

### 3.5 执行主体解析

名单版本中的成员是**冻结时点的用户标识**；执行时点真正被作用的对象是**解析后主体**。归并发生后二者可能不同，因此必须区分——这是本模型自身的继任链语义产生的事实，其归属由本模型负责，不下放给下游。

**解析规则**：

1. 执行开始时，对名单版本中的每个成员沿继任链解析，得到解析后主体。
2. **解析后去重**：同一版本中多个成员解析到同一个解析后主体时，该主体在本次执行中只被作用一次。
3. 解析不到存续主体的（注销、继任链断裂），判定为不可送达，跳过并可见地记录，不视为错误。

**归属规则**——本模型对下游作出的承诺：

| 事项 | 按哪个标识计 |
|---|---|
| 执行记录 | **两者都记**：版本内原用户标识与解析后主体，缺一不可 |
| 幂等与去重 | **解析后主体**。版本内原用户标识在归并后不稳定，不得单独用作幂等键 |
| 频次疲劳、总量控制、权益归属 | **解析后主体** |
| 名单成员数、圈选结果回溯 | **版本内原用户标识** |

解析在**执行侧**发生：本模型规定其语义与归属，不规定实施位置。

**执行结果不承诺可复现。** I1 约束版本内容不变，I5 约束成员集合可重放，二者都不承诺同一版本在不同时点执行会得到相同的送达结果——身份变更、资格判定、渠道可用性都会改变结果。可复现的是「圈出了谁」，不是「发到了哪」。

## 4. 用户名单

### 4.1 核心结构：定义与版本分离

名单不是一个实体，是两个：

```
名单定义 (AudienceDefinition)          稳定，描述「怎么圈」
    │
    │  求值（一次或多次）
    ▼
名单版本 (AudienceVersion)             不可变，描述「圈出了谁」
    │
    │  被引用
    ▼
执行（画布运行实例 / 触达 / 权益）
```

**这一分离是两种名单模式能够共存的前提。** 静态与动态的差别只在「产生多少个版本、何时产生」，不在版本本身的语义——下游看到的永远是同一种不可变版本。

### 4.2 来源接入（Source Binding）

名单定义引用一个或多个**来源**。来源是候选主体的供给方。

对来源的约束：

- 来源必须声明它供给的**标识域**。若来源供给的不是用户标识，圈选阶段必须完成到用户标识的解析。
- 来源必须声明**时效语义**：其数据代表哪个时点的事实。求值时点与来源时效不一致时，以来源自身声明的时点为准记入求值输入指纹。
- 来源必须可在求值时点被**重新指认**——即事后能回答「那次求值读的是哪一份数据」。不可指认的来源不得用于动态模式。

本轮不枚举具体来源系统与接入方式，理由同 3.2：接入形态依赖尚未确定的技术栈。见待澄清项 O2。

### 4.3 圈选（Selection）

圈选是从来源产出候选主体集合的规则。

**核心约束——可重放**：同一圈选规则 + 同一求值输入指纹，必须产出同一个成员集合。

这条不是性能要求，是可复现性要求：它是分桶稳定（高风险第 5 条）与实验结论可回算的共同前提。**它不支撑回执可关联**——回执关联依赖执行时的地址解析结果，而地址不进版本（D3），该性质由渠道接入模型（第 9 条）负责。若某个圈选规则无法满足可重放（例如依赖随机采样或依赖求值时刻的外部实时状态），该规则**必须显式声明为不可重放**，并且：

- 不可重放的名单定义只能使用静态模式；
- 其产出的版本不得作为实验的分流输入。

圈选阶段必须产出三类结果，缺一不可：

| 结果 | 含义 | 为什么必须单独产出 |
|---|---|---|
| 成员集合 | 解析成功、纳入本版本的用户标识 | 名单版本的正文 |
| 未解析条目 | 来源中存在、但无法解析到用户标识的条目 | 静默丢弃会让「圈出来的人变少了」无法被发现 |
| 排除记录 | 命中圈选规则的排除条件而被剔除的主体 | 事后回答「他为什么不在名单里」 |

### 4.4 快照（Snapshot）

「快照」即**名单版本**。一个名单版本一经产生即不可变，包含且仅包含：

- 成员集合（用户标识的集合，可以为空）
- 求值时点
- 求值输入指纹
- 所属名单定义与版本序号
- 未解析条目与排除记录

**名单版本中不得出现任何送达地址或别名值。** 这是 3.4 决策的直接推论，也是本模型最重要的一条结构约束。

空集是合法的名单版本，不是错误。把空集当错误会诱使实现方「补一点人进去」。

### 4.5 生命周期（Lifecycle）

生命周期分两层，不能混为一谈：

- **名单定义的生命周期**：草稿 → 生效 → 暂停 → 归档。见 6.1。
- **名单版本的生命周期**：求值中 → 就绪 → 失效（或求值中 → 失败）。见 6.2。

关键规则：**名单定义的生命周期变化不改变已产生版本的内容。** 归档一个名单定义，只意味着它不再产生新版本，不意味着它的历史版本失效或被删除，也不影响已经绑定这些版本的执行。

### 4.6 两种模式

| | 静态模式 STATIC | 动态模式 DYNAMIC |
|---|---|---|
| 版本数量 | 恰好一个 | 多个，随调度累积 |
| 产生时机 | 名单定义生效时求值一次 | 按定义声明的调度重复求值 |
| 典型场景 | 一次性活动、外部导入名单 | 长周期运营、生命周期触达 |
| 可重放要求 | 建议满足 | **必须满足**（见 4.3） |

**两种模式共用的规则（这是「并存」不至于分叉的关键）：**

1. 模式在名单定义**生效时确定，此后不可切换**。切换模式等同于新建名单定义。
2. 任何执行绑定到**具体的名单版本**，不绑定名单定义。动态模式不提供「总是最新」的绑定方式——需要跟随最新版本的编排语义，由画布模型显式表达为「在每次调度上新建执行」，而不是让一次执行的人群在运行中漂移。
3. 动态模式的历史版本**不可变、不删除、不合并**。

第 2 条是本节的实质内容。它把「动态」限制在**版本产生侧**，不让它渗透到执行侧——否则「这次执行到底发给了谁」将无法回答，而这正是高风险清单第 4 条要防的失效。

## 5. 不变量

每条都写成可证伪的断言。违反任一条即为缺陷。

| 编号 | 不变量 |
|---|---|
| I1 | 名单版本一经进入就绪态，其成员集合、求值时点、求值输入指纹、未解析条目、排除记录均不再改变 |
| I2 | 名单版本的成员只能是用户标识，不含任何别名值或送达地址 |
| I3 | 任何执行绑定到具体名单版本，不绑定名单定义 |
| I4 | 同一名单定义的版本序号严格单调递增，不复用、不回收。**版本的先后一律以序号为准**；求值时点仅作记录，二者不一致时（并发或同时点求值）不以时点为准 |
| I5 | 声明为可重放的圈选规则，同规则 + 同求值输入指纹必然产出同一成员集合 |
| I6 | 一个 `(标识域, 值)` 别名在任一时刻至多指向一个存续的用户标识 |
| I7 | 用户标识不可变、不回收、不复用；注销与合并均不删除用户标识 |
| I8 | 已归并的用户标识不出现在**新产生**的名单版本中；已存在的历史版本不因归并而被修改 |
| I9 | 继任链无环且长度有限 |
| I10 | 名单定义的模式在生效后不可变更 |
| I11 | 空成员集合是合法的就绪版本 |
| I12 | 名单定义生效后，其来源接入、圈选规则与求值调度不可变更 |
| I13 | 一次执行中，同一解析后主体至多被作用一次（解析后去重，见 3.5） |
| I14 | 执行记录同时保留版本内原用户标识与解析后主体，二者均不可省略 |
| I15 | 名单版本一旦进入 EXPIRED 或 INVALIDATED，不再接受新的执行绑定；已存在的绑定不受影响 |

I12 的理由：允许改规则会让同一名单定义下的版本彼此不可比，I5 的可重放随之失去意义。需要改规则时新建名单定义，代价是显式的。

## 6. 状态机

### 6.1 名单定义

```
草稿 DRAFT ──生效──> 生效 ACTIVE ──暂停──> 暂停 PAUSED
                        │  ▲                  │
                        │  └────── 恢复 ───────┘
                        │
                     归档
                        │
                        ▼
                   归档 ARCHIVED
```

| 状态 | 含义 | 允许的操作 |
|---|---|---|
| DRAFT | 编辑中，尚未求值 | 修改来源与圈选规则；生效；删除 |
| ACTIVE | 已生效 | 静态模式：已产出唯一版本；动态模式：按调度持续产出版本 |
| PAUSED | 暂停产出 | 恢复；归档。**已有版本仍可被新执行绑定** |
| ARCHIVED | 终态 | 无。已有版本仍可被新执行绑定 |

**非法流转（必须被拒绝，不是被容忍）**：

- `ARCHIVED → 任何状态`：归档是终态。
- `DRAFT → PAUSED`：未生效的定义没有可暂停的产出。
- `DRAFT → ARCHIVED`：未生效的定义用删除，不用归档。归档承载「曾经生效过」的语义。
- `ACTIVE → DRAFT`、`PAUSED → DRAFT`：退回草稿等同于开放规则编辑，违反 I12。
- 在 `ACTIVE` / `PAUSED` / `ARCHIVED` 下修改来源或圈选规则（违反 I12）。
- 在 `ACTIVE` / `PAUSED` / `ARCHIVED` 下变更模式（违反 I10）。模式在 `DRAFT` 阶段可自由设定，生效时随定义一并冻结。

暂停与归档**不阻断已有版本被新执行绑定**——这是有意的。阻断它意味着运营停用一个名单定义会连带打断正在编排的流程，而那不是「停止产出新版本」这个动作应有的影响面。

### 6.2 名单版本

```
求值中 EVALUATING ──成功──> 就绪 READY ──到期────> 失效 EXPIRED
        │                     │
        │                     └──人工作废──> 作废 INVALIDATED
        │
        └──失败──> 失败 FAILED
```

| 状态 | 含义 | 能否被执行绑定 |
|---|---|---|
| EVALUATING | 求值进行中，内容未定 | 否 |
| READY | 求值成功，内容已冻结 | 是 |
| EXPIRED | 超出定义声明的版本有效期，自动到达 | 否（仅影响**新**绑定） |
| INVALIDATED | 被人工判定为不可再用（圈选口径错误、误操作、合规要求），终态 | 否（仅影响**新**绑定） |
| FAILED | 求值失败 | 否 |

**非法流转**：

- `READY → EVALUATING`：就绪版本不得重新求值。需要新结果就产生新版本。
- `FAILED → READY`、`FAILED → EVALUATING`：失败版本不可修复。重试等同于产生一个新版本，序号继续递增（I4），不复用失败版本的序号。
- `READY → FAILED`：已就绪的版本不得被追溯判为失败。发现内容有问题时用作废，不用失败。
- `EXPIRED → READY`、`EXPIRED → EVALUATING`：失效不可撤销。
- `INVALIDATED → 任何状态`：作废是终态，不可恢复。

**为什么必须有 INVALIDATED**：6.1 把「停止产出新版本」与「阻断已有版本被使用」正确地分成了两件事，因此后一件事必须有自己的机制。归档名单定义不阻断已有版本，而 EXPIRED 的唯一入口是有效期自然到达——若无作废态，一个圈选口径错误的版本将无任何合法路径可以停用，只能等它到期。这正是高风险清单第 4 条所说的「对错误人群执行，且已经发出的触达不可撤回」。

**谁能作废**属于执行授权模型（第 13 条），不在本模型定义。

**EXPIRED 与 INVALIDATED 都只影响新绑定，不影响已绑定的执行。** 一个正在运行的流程不会因为它引用的名单版本到期或被作废而中断——中断的语义属于运行实例状态机（高风险第 3 条），不属于本模型。作废一个正在被执行引用的版本时，停止该执行需要同时在运行实例侧发起，本模型不代劳。

## 7. 边界与非目标

以下职责**不**属于本模型。写出来是为了让后续讨论不必反复重划边界。

| 不属于本模型 | 属于谁 | 关键澄清 |
|---|---|---|
| 退订、免打扰时段、频次疲劳 | 触达资格模型（高风险第 8 条） | **在名单里 ≠ 可触达。** 资格判定在执行时进行，不在圈选时进行。把资格前置到圈选会让名单版本随资格状态变化而不可复现 |
| 谁能对这批人发起执行、发布由谁批准、谁能作废名单版本 | 执行授权模型（第 13 条） | 本模型只回答「是谁」与「哪个版本还能用」，不回答「谁有权这么做」 |
| 分流单元、分桶算法、实验定义 | 实验模型（第 5 条） | 本模型只保证用户标识稳定；分桶以它为输入，但分桶规则不在此定义 |
| 送达地址的解析规则与渠道映射 | 渠道接入模型（第 9 条） | 本模型规定「执行时解析」，不规定「怎么解析」 |
| 名单版本的存储实现、保留期限、容量上限 | 实现侧 | 技术栈未定；保留期限见待澄清项 O4 |
| 权益额度的归属与总量控制 | 权益模型（第 7 条） | 额度归属以用户标识为键，但归属规则不在此定义 |
| 执行的幂等键的其余构成 | 组件契约模型（第 2、11 条） | 本模型保证**解析后主体**（3.5）是幂等键的稳定组成部分，并规定幂等按解析后主体计；键的其余构成不在此定义 |
| 继任链解析在哪一层实施、执行记录如何存放 | 实现侧 | 本模型规定解析语义与归属（3.5），不规定实施位置 |

## 9. 决策记录

| 编号 | 决策 | 备选方案与否决理由 |
|---|---|---|
| D1 | 平台内部用户标识为唯一主键 | **渠道账号即主体**：接入成本低，但同一个人在多渠道被视为多个主体，频次疲劳与总量控制都算不准，且事后归并要重算历史。**uid 为主但允许匿名主体并存**：覆盖拉新场景，代价是主键变成复合键、归并时历史需重新归因——本轮否决，若拉新场景成为主线，作为后续修订项（见 O3） |
| D2 | 静态与动态两种模式并存，但统一为「定义 + 版本」结构 | **只做静态快照**：最简单、可复现性最强，但长周期运营必须反复手工重建名单。**只做动态求值**：运营自然，但历史实验无法回算、回执无法关联。选择并存，并用「执行只绑定具体版本」把动态限制在版本产生侧 |
| D3 | 名单版本只存用户标识，送达地址在执行时解析 | **快照冻结时点全量解释**（连送达地址一并冻结）：完全可复现，但换号后会发到旧号的现任机主、注销用户会被继续触达——这是不可撤回的错误，代价高于可复现性收益 |
| D5 | 执行按解析后主体去重、计频次与归属；名单成员数按版本内原用户标识计 | **全部按版本内原用户标识**：回溯最简单，但归并后同一自然人被算作两个人，频次疲劳与总量控制失效——超发与重复发送都不会被幂等挡住。**全部按解析后主体**：执行侧正确，但名单成员数会随归并悄悄变化，圈选结果无法回溯 |
| D6 | 名单版本新增可人工触发的作废态（INVALIDATED） | **不设作废态，靠有效期自然失效**：状态机更简单，但圈选口径错误的版本在到期前无法停用。**靠归档名单定义来阻断**：会让停用一个定义连带打断正在编排的流程，把两件不同的事耦合起来 |
| D4 | 名单定义生效后来源与圈选规则不可变更（I12） | **允许修改规则**：运营改起来方便，但同一定义下的版本彼此不可比，I5 的可重放失去意义，实验结论无法归因。需要改时新建定义，代价显式 |

## 11. 建模顺序与本轮位置

本文档是第 ① 轮。完整顺序及排序依据（依赖方向与可补救性，非重要性）：

| 顺序 | 模型 | 排序理由 |
|---|---|---|
| ① | **用户身份 + 用户名单**（本文档） | 唯一不依赖下游的模型；定下全局标识口径，②③④⑤ 全部引用它；错了是数据迁移（第 12 条），本主线里唯一不能靠重跑自愈的一类 |
| ② | 组件契约 + 一次执行 | 项目的支点抽象（第 2、6 条）。必须用触达与权益**两个**实例反推——只有一个实例时抽象无法被证伪 |
| ③ | 流程画布 DSL + 运行实例状态机 | 第 1、3 条。节点指向 ② 的组件，② 未定时讨论 DSL 会空转 |
| ④ | 触达资格 / 权益额度 | 第 7、8 条。② 两个实例各自的特殊约束，是检验 ② 是否塌陷的试金石 |
| ⑤ | 分流单元 + 实验 + 指标口径 | 第 5 条。横切 ①③，分桶稳定性依赖本文档的标识口径 |

进入第 ② 轮时，须按根 `AGENTS.md` 要求**复审项目高风险清单，包括卡点密度**。
