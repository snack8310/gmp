## 2. 名词表

| 中文名 | 英文名 | 定义 |
|---|---|---|
| 用户标识 | UserId | 本平台的唯一主体标识，由上游签发并带入。对本模型**不透明**：只要求唯一、稳定、可比较，不解释其含义 |
| 送达地址 | DeliveryAddress | 触达的终点（某渠道所需的地址或账号）。**属渠道接入模型的概念**，本模型引用它只为约束「名单里不许存它」 |
| 名单定义 | AudienceDefinition | 「怎么圈出这批人」的稳定描述。构成为：来源接入 + 圈选规则 + 名单模式 + 求值调度 + 版本有效期 + 生命周期状态。此为封闭枚举，全文不得引用枚举外的属性 |
| 名单版本 | AudienceVersion | 名单定义的一次求值结果，不可变。即高风险清单第 4 条所称的「快照」 |
| 求值输入指纹 | EvaluationInputDigest | 一次求值所依赖的全部输入的可比较摘要，用于判定两次求值是否应当同结果 |
| 名单模式 | AudienceMode | 静态或动态，决定名单定义产生版本的方式 |
| 求值调度 | EvaluationSchedule | 名单定义产生新版本的时机。动态模式必须声明；静态模式恒为「仅生效时一次」，不可另行声明 |
| 版本有效期 | VersionValidity | 名单版本自求值时点起可被**新执行**绑定的时长。到期即进入失效态。具体取值口径见待澄清项 O8 |

### 2.1 概念与关系

引用方向单向，不成环：

```
        名单定义 ──引用──> 来源
            │
        （求值产生）
            ▼
        名单版本 ──成员──> 用户标识（不透明，上游带入）
            ▲                    ┊
        （绑定）                 ┊ 执行时由渠道模型解析
            │                    ▼
          执行 ················> 送达地址
```

- 名单版本引用用户标识，**不引用**送达地址或任何其他标识（I2）。
- 执行引用名单版本，**不引用**名单定义（I3）。
- 送达地址不被本模型的任何概念持有；虚线部分发生在执行时，归渠道接入模型。
- 图中实线箭头混用了两种关系，读图时须区分：`名单定义 → 名单版本` 是**产生**方向（引用方向相反，版本记录其所属定义）；其余为**引用**方向。按引用方向重画同样无环。

## 3. 用户标识

### 3.1 定位：不透明主键

本平台的能力是「**给定一个用户标识，做条件判断、策略分流与触达**」。**用户标识背后代表什么，不在本模型的考虑范围内。**

- 用户标识由上游签发并带入，本模型只**消费**它：不产生、不解释、不管理其生命周期。
- 对本模型而言它是**不透明**的：不得从中推断自然人、设备、账号或任何业务属性，也不得依赖其编码格式。
- 本模型对它只有三条要求：

| 要求 | 含义 | 谁依赖它 |
|---|---|---|
| **唯一** | 同一时刻一个用户标识只对应一个主体 | 名单成员语义、权益归属 |
| **稳定** | 不可变、不回收、不复用 | 分桶可复现（第 5 条）、幂等键（第 11 条）、频次疲劳（第 8 条） |
| **可比较** | 相等判定明确且全局一致 | 去重、集合运算、名单交并差 |

这三条是本模型对上游提出的**全部**要求。满足它们，本模型不需要知道任何别的东西；不满足，下游的分桶稳定、幂等去重、频次控制、权益归属会同时失去地基，且都属于不会报错的静默失效。

一个用户标识恒等于一个主体，不存在「没有用户标识的主体」。

### 3.2 本模型不管的身份事项

写出来是为了让这些事项不会因为「看起来和身份有关」而被塞回本模型：

| 事项 | 归谁 | 说明 |
|---|---|---|
| 用户标识的签发、注销、合并、跨系统映射 | 上游身份系统 | 本模型不感知，也不因此修改任何已冻结的名单版本 |
| 手机号、设备号、各渠道账号等标识及其映射关系 | 上游身份系统与渠道接入模型 | 本模型全程不接触这些值 |
| 从用户标识得到送达地址 | 渠道接入模型（第 9 条） | 在**执行时**进行，不在圈选时进行 |
| 这个人当下是否可触达（退订、免打扰、频次疲劳） | 触达资格模型（第 8 条） | 在**执行时**判定 |

由此得到本模型对名单内容的硬约束（I2）：**名单版本只存用户标识，不得存放送达地址或任何其他标识的值。** 存了就等于把上游的身份状态冻结进了快照——那正是 D3 否决的做法，代价是换号后发给旧号的现任机主、注销用户被继续触达。

### 3.3 名单成员不保证可送达

这是上面两节的直接推论，也是最容易被实现方误解的一条：

- **「在名单里」只意味着「圈选规则命中了这个用户标识」**，不意味着这个人存在、活跃、已授权或可被送达。
- 执行时解析不到送达地址、或被资格判定拦下的，跳过并可见地记录，**不视为错误**，也不回头修改名单版本。
- 跳过的主体不计入触达成功；其后续处理归运行实例状态机（第 3 条）。

**执行结果不承诺可复现。** I1 约束版本内容不变，I5 约束成员集合可重放，二者都不承诺同一版本在不同时点执行会得到相同的送达结果——上游身份状态、资格判定、渠道可用性都会改变结果。**可复现的是「圈出了谁」，不是「发到了哪」。**

## 4. 用户名单

### 4.1 核心结构：定义与版本分离

名单不是一个实体，是两个：

```
名单定义 (AudienceDefinition)          稳定，描述「怎么圈」
    │
    │  求值（一次或多次）
    ▼
名单版本 (AudienceVersion)             不可变，描述「圈出了谁」
    │
    │  被引用
    ▼
执行（画布运行实例 / 触达 / 权益）
```

**这一分离是两种名单模式能够共存的前提。** 静态与动态的差别只在「产生多少个版本、何时产生」，不在版本本身的语义——下游看到的永远是同一种不可变版本。

### 4.2 来源接入（Source Binding）

名单定义引用一个或多个**来源**。来源是候选主体的供给方。

对来源的约束：

- 来源必须声明它供给的是**用户标识**还是别的什么。若供给的不是用户标识，圈选阶段必须完成到用户标识的解析，解析不到的条目记为未解析条目（见 4.3），不得静默丢弃。本模型不定义解析规则——那属上游身份系统（3.2）。
- 来源必须声明**时效语义**：其数据代表哪个时点的事实。求值时点与来源时效不一致时，以来源自身声明的时点为准记入求值输入指纹。
- 来源必须可在求值时点被**重新指认**——即事后能回答「那次求值读的是哪一份数据」。不可指认的来源不得用于动态模式。

本轮不枚举具体来源系统与接入方式，理由同 3.2：接入形态依赖尚未确定的技术栈。见待澄清项 O2。

### 4.3 圈选（Selection）

圈选是从来源产出候选主体集合的规则。

**核心约束——可重放**：同一圈选规则 + 同一求值输入指纹，必须产出同一个成员集合。

这条不是性能要求，是可复现性要求：它是分桶稳定（高风险第 5 条）与实验结论可回算的共同前提。**它不支撑回执可关联**——回执关联依赖执行时的地址解析结果，而地址不进版本（D3），该性质由渠道接入模型（第 9 条）负责。若某个圈选规则无法满足可重放（例如依赖随机采样或依赖求值时刻的外部实时状态），该规则**必须显式声明为不可重放**，并且：

- 不可重放的名单定义只能使用静态模式；
- 其产出的版本不得作为实验的分流输入。

圈选阶段必须产出三类结果，缺一不可：

| 结果 | 含义 | 为什么必须单独产出 |
|---|---|---|
| 成员集合 | 解析成功、纳入本版本的用户标识 | 名单版本的正文 |
| 未解析条目 | 来源中存在、但无法解析到用户标识的条目 | 静默丢弃会让「圈出来的人变少了」无法被发现 |
| 排除记录 | 命中圈选规则的排除条件而被剔除的主体 | 事后回答「他为什么不在名单里」 |

### 4.4 快照（Snapshot）

「快照」即**名单版本**。一个名单版本一经产生即不可变，包含且仅包含：

- 成员集合（用户标识的集合，可以为空）
- 求值时点
- 求值输入指纹
- 所属名单定义与版本序号
- 未解析条目与排除记录

**名单版本中不得出现送达地址或任何其他标识的值，只能是用户标识。** 这是 3.2 与 D3 的直接推论，也是本模型最重要的一条结构约束。

空集是合法的名单版本，不是错误。把空集当错误会诱使实现方「补一点人进去」。

### 4.5 生命周期（Lifecycle）

生命周期分两层，不能混为一谈：

- **名单定义的生命周期**：草稿 → 生效 → 暂停 → 归档。见 6.1。
- **名单版本的生命周期**：求值中 → 就绪 → 失效（或求值中 → 失败）。见 6.2。

关键规则：**名单定义的生命周期变化不改变已产生版本的内容。** 归档一个名单定义，只意味着它不再产生新版本，不意味着它的历史版本失效或被删除，也不影响已经绑定这些版本的执行。

### 4.6 两种模式

| | 静态模式 STATIC | 动态模式 DYNAMIC |
|---|---|---|
| 版本数量 | 恰好一个 | 多个，随调度累积 |
| 产生时机 | 名单定义生效时求值一次 | 按定义声明的调度重复求值 |
| 典型场景 | 一次性活动、外部导入名单 | 长周期运营、生命周期触达 |
| 可重放要求 | 建议满足 | **必须满足**（见 4.3） |

**两种模式共用的规则（这是「并存」不至于分叉的关键）：**

1. 模式在名单定义**生效时确定，此后不可切换**。切换模式等同于新建名单定义。
2. 任何执行绑定到**具体的名单版本**，不绑定名单定义。动态模式不提供「总是最新」的绑定方式——需要跟随最新版本的编排语义，由画布模型显式表达为「在每次调度上新建执行」，而不是让一次执行的人群在运行中漂移。
3. 动态模式的历史版本**不可变、不删除、不合并**。

第 2 条是本节的实质内容。它把「动态」限制在**版本产生侧**，不让它渗透到执行侧——否则「这次执行到底发给了谁」将无法回答，而这正是高风险清单第 4 条要防的失效。

## 5. 不变量

每条都写成可证伪的断言。违反任一条即为缺陷。

| 编号 | 不变量 |
|---|---|
| I1 | 名单版本一经进入就绪态，其成员集合、求值时点、求值输入指纹、未解析条目、排除记录均不再改变 |
| I2 | 名单版本的成员只能是用户标识，不含送达地址或任何其他标识的值 |
| I3 | 任何执行绑定到具体名单版本，不绑定名单定义 |
| I4 | 同一名单定义的版本序号严格单调递增，不复用、不回收。**版本的先后一律以序号为准**；求值时点仅作记录，二者不一致时（并发或同时点求值）不以时点为准 |
| I5 | 声明为可重放的圈选规则，同规则 + 同求值输入指纹必然产出同一成员集合 |
| I6 | 用户标识唯一、稳定（不可变、不回收、不复用）、可比较；本模型不校验此性质，而是要求上游保证（见 3.1） |
| I7 | 名单定义的模式在生效后不可变更 |
| I8 | 空成员集合是合法的就绪版本 |
| I9 | 名单定义生效后，其来源接入、圈选规则、求值调度与版本有效期均不可变更。构成六项中只有生命周期状态可变 |
| I10 | 名单版本一旦进入 EXPIRED 或 INVALIDATED，不再接受新的执行绑定；已存在的绑定不受影响 |

I9 的理由分两半：

- **来源接入、圈选规则、求值调度**：允许修改会让同一名单定义下的版本彼此不可比，I5 的可重放随之失去意义。
- **版本有效期**：若允许生效后延长，一个已进入 `EXPIRED` 的版本会同时满足「按新有效期尚未超期」与「失效不可撤销」（6.2）两条互斥解释，且没有任何一条能自动胜出。冻结它，冲突不成立。

需要改这四项中的任何一项时，新建名单定义，代价是显式的。

## 6. 状态机

### 6.1 名单定义

```
草稿 DRAFT ──生效──> 生效 ACTIVE ──暂停──> 暂停 PAUSED
                        │  ▲                  │
                        │  └────── 恢复 ───────┘
                        │
                     归档
                        │
                        ▼
                   归档 ARCHIVED
```

| 状态 | 含义 | 允许的操作 |
|---|---|---|
| DRAFT | 编辑中，尚未求值 | 修改来源与圈选规则；生效；删除 |
| ACTIVE | 已生效 | 静态模式：已产出唯一版本；动态模式：按调度持续产出版本 |
| PAUSED | 暂停产出 | 恢复；归档。**已有版本仍可被新执行绑定** |
| ARCHIVED | 终态 | 无。已有版本仍可被新执行绑定 |

状态集为 {DRAFT, ACTIVE, PAUSED, ARCHIVED}，12 组有序流转全部裁定，合法 5 组、非法 7 组，无未表态项。

**合法流转**：`DRAFT → ACTIVE`、`ACTIVE → PAUSED`、`PAUSED → ACTIVE`、`ACTIVE → ARCHIVED`、`PAUSED → ARCHIVED`。

**非法流转（必须被拒绝，不是被容忍）**：

- `ARCHIVED → 任何状态`：归档是终态。
- `DRAFT → PAUSED`：未生效的定义没有可暂停的产出。
- `DRAFT → ARCHIVED`：未生效的定义用删除，不用归档。归档承载「曾经生效过」的语义。
- `ACTIVE → DRAFT`、`PAUSED → DRAFT`：退回草稿等同于开放规则编辑，违反 I9。
- 在 `ACTIVE` / `PAUSED` / `ARCHIVED` 下修改来源接入、圈选规则、求值调度或版本有效期中的任何一项（违反 I9）。
- 在 `ACTIVE` / `PAUSED` / `ARCHIVED` 下变更模式（违反 I8）。模式在 `DRAFT` 阶段可自由设定，生效时随定义一并冻结。

暂停与归档**不阻断已有版本被新执行绑定**——这是有意的。阻断它意味着运营停用一个名单定义会连带打断正在编排的流程，而那不是「停止产出新版本」这个动作应有的影响面。

### 6.2 名单版本

```
求值中 EVALUATING ──成功──> 就绪 READY ──到期────> 失效 EXPIRED
        │                     │
        │                     └──人工作废──> 作废 INVALIDATED
        │
        └──失败──> 失败 FAILED
```

| 状态 | 含义 | 能否被执行绑定 |
|---|---|---|
| EVALUATING | 求值进行中，内容未定 | 否 |
| READY | 求值成功，内容已冻结 | 是 |
| EXPIRED | 超出定义声明的版本有效期，自动到达 | 否（仅影响**新**绑定） |
| INVALIDATED | 被人工判定为不可再用（圈选口径错误、误操作、合规要求），终态 | 否（仅影响**新**绑定） |
| FAILED | 求值失败 | 否 |

**非法流转**：

状态集为 {EVALUATING, READY, EXPIRED, INVALIDATED, FAILED}，20 组有序流转全部裁定，合法 5 组、非法 15 组，无未表态项。

**合法流转**：`EVALUATING → READY`、`EVALUATING → FAILED`、`EVALUATING → INVALIDATED`、`READY → EXPIRED`、`READY → INVALIDATED`。

`EVALUATING → INVALIDATED` 合法：求值途中即发现圈选口径错误时，无需等它就绪再作废。作废对内容未定的版本同样成立——作废断言的是「这个版本不可再用」，不是「这个版本的内容有问题」。

**非法流转**：

| 从 → 到 | 理由 |
|---|---|
| `EVALUATING → EXPIRED` | 有效期自求值时点起算，内容未定时谈不上到期。求值超时是失败，不是失效 |
| `READY → EVALUATING` | 就绪版本不得重新求值。需要新结果就产生新版本 |
| `READY → FAILED` | 已就绪的版本不得被追溯判为失败。发现内容有问题时用作废，不用失败 |
| `EXPIRED → READY`、`EXPIRED → EVALUATING` | 失效不可撤销（有效期已由 I9 冻结，不存在「延长后复活」） |
| `EXPIRED → FAILED` | 已成功求值过的版本不得被追溯判为失败，理由同 `READY → FAILED` |
| `EXPIRED → INVALIDATED` | 二者对新绑定的效果相同，转换无收益，却让「这个版本为什么不能用」有了两个答案 |
| `FAILED → READY`、`FAILED → EVALUATING` | 失败版本不可修复。重试等同于产生一个新版本，序号继续递增（I4），不复用失败版本的序号 |
| `FAILED → EXPIRED`、`FAILED → INVALIDATED` | 失败是终态。从未就绪过的版本无需再被作废或失效 |
| `INVALIDATED → 任何状态`（4 组） | 作废是终态，不可恢复 |

**为什么必须有 INVALIDATED**：6.1 把「停止产出新版本」与「阻断已有版本被使用」正确地分成了两件事，因此后一件事必须有自己的机制。归档名单定义不阻断已有版本，而 EXPIRED 的唯一入口是有效期自然到达——若无作废态，一个圈选口径错误的版本将无任何合法路径可以停用，只能等它到期。这正是高风险清单第 4 条所说的「对错误人群执行，且已经发出的触达不可撤回」。

**谁能作废**属于执行授权模型（第 13 条），不在本模型定义。

**EXPIRED 与 INVALIDATED 都只影响新绑定，不影响已绑定的执行。** 一个正在运行的流程不会因为它引用的名单版本到期或被作废而中断——中断的语义属于运行实例状态机（高风险第 3 条），不属于本模型。作废一个正在被执行引用的版本时，停止该执行需要同时在运行实例侧发起，本模型不代劳。

## 7. 边界与非目标

以下职责**不**属于本模型。写出来是为了让后续讨论不必反复重划边界。

| 不属于本模型 | 属于谁 | 关键澄清 |
|---|---|---|
| 退订、免打扰时段、频次疲劳 | 触达资格模型（高风险第 8 条） | **在名单里 ≠ 可触达。** 资格判定在执行时进行，不在圈选时进行。把资格前置到圈选会让名单版本随资格状态变化而不可复现 |
| 谁能对这批人发起执行、发布由谁批准、谁能作废名单版本 | 执行授权模型（第 13 条） | 本模型只回答「是谁」与「哪个版本还能用」，不回答「谁有权这么做」 |
| 分流单元、分桶算法、实验定义 | 实验模型（第 5 条） | 本模型只保证用户标识稳定；分桶以它为输入，但分桶规则不在此定义 |
| 送达地址的解析规则与渠道映射 | 渠道接入模型（第 9 条） | 本模型规定「执行时解析」「不进快照」，不规定「怎么解析」。另见 3.2 |
| 名单版本的存储实现、保留期限、容量上限 | 实现侧 | 技术栈未定；保留期限见待澄清项 O4 |
| 权益额度的归属与总量控制 | 权益模型（第 7 条） | 额度归属以用户标识为键，但归属规则不在此定义 |
| 执行的幂等键的其余构成 | 组件契约模型（第 2、11 条） | 本模型保证用户标识是幂等键的稳定组成部分；键的其余构成不在此定义 |
| 用户标识的产生、签发、注销、跨系统映射 | 上游身份系统 | 本模型只消费用户标识，对其只有唯一 / 稳定 / 可比较三条要求（3.1、D5） |
| 用户标识的**合并** | 不指派给任何模型——**本模型假定它不发生** | 合并恰恰是使「稳定」不再成立的那个事件，因此它不是可以下放给上游的职责，而是本模型成立的前提。上游一旦引入合并，本模型即失效，必须回本文档修订（O9），不得在下游变通 |

根 `AGENTS.md` 高风险清单第 4 条为「变更用户名单的来源接入、圈选、快照或生命周期」。按 [`source-enumeration-fidelity`](../history/memory/source-enumeration-fidelity.md) 的要求，以**来源侧**为遍历基准逐项承接：

## 9. 决策记录

| 编号 | 决策 | 备选方案与否决理由 |
|---|---|---|
| D1 | 用户标识为唯一主键，由上游带入 | **渠道账号即主体**：接入成本低，但同一个人在多渠道被视为多个主体，频次疲劳与总量控制都算不准。**用户标识为主但允许匿名主体并存**：覆盖拉新场景，代价是主键变成复合键、绑定后历史需重新归因——本轮否决，若拉新场景成为主线，作为后续修订项（见 O3） |
| D2 | 静态与动态两种模式并存，但统一为「定义 + 版本」结构 | **只做静态快照**：最简单、可复现性最强，但长周期运营必须反复手工重建名单。**只做动态求值**：运营自然，但历史实验无法回算、回执无法关联。选择并存，并用「执行只绑定具体版本」把动态限制在版本产生侧 |
| D3 | 名单版本只存用户标识，送达地址在执行时解析 | **快照冻结时点全量解释**（连送达地址一并冻结）：完全可复现，但换号后会发到旧号的现任机主、注销用户会被继续触达——这是不可撤回的错误，代价高于可复现性收益 |
| D4 | 名单定义生效后来源接入、圈选规则、求值调度与版本有效期不可变更（I9） | **允许修改规则**：运营改起来方便，但同一定义下的版本彼此不可比，I5 的可重放失去意义，实验结论无法归因。需要改时新建定义，代价显式 |
| D5 | 用户标识对本模型不透明：只要求唯一、稳定、可比较，其含义与生命周期（含签发、注销、合并）一律不在本模型范围 | **在本模型内定义继任链与解析后去重**：能处理「同一人曾持有两个用户标识、合并后同在一个已冻结版本里被发两次」的场景，但代价是引入继任标识、继任链、解析后去重、双轨执行记录一整套概念，且执行侧必须实现解析。经业务确认本系统不存在账号合并，故整块移除——**若未来引入，必须回到本文档修订，不得在下游变通**（见 O9） |
| D6 | 名单版本新增可人工触发的作废态（INVALIDATED） | **不设作废态，靠有效期自然失效**：状态机更简单，但圈选口径错误的版本在到期前无法停用。**靠归档名单定义来阻断**：会让停用一个定义连带打断正在编排的流程，把两件不同的事耦合起来 |

## 11. 建模顺序与本轮位置

本文档是第 ① 轮。完整顺序及排序依据（依赖方向与可补救性，非重要性）：

| 顺序 | 模型 | 排序理由 |
|---|---|---|
| ① | **用户身份 + 用户名单**（本文档） | 唯一不依赖下游的模型；定下全局标识口径，②③④⑤ 全部引用它；错了是数据迁移（第 12 条），本主线里唯一不能靠重跑自愈的一类 |
| ② | 组件契约 + 一次执行 | 项目的支点抽象（第 2、6 条）。必须用触达与权益**两个**实例反推——只有一个实例时抽象无法被证伪 |
| ③ | 流程画布 DSL + 运行实例状态机 | 第 1、3 条。节点指向 ② 的组件，② 未定时讨论 DSL 会空转 |
| ④ | 触达资格 / 权益额度 | 第 7、8 条。② 两个实例各自的特殊约束，是检验 ② 是否塌陷的试金石 |
| ⑤ | 分流单元 + 实验 + 指标口径 | 第 5 条。横切 ①③，分桶稳定性依赖本文档的标识口径 |

进入第 ② 轮时，须按根 `AGENTS.md` 要求**复审项目高风险清单，包括卡点密度**。
