# 业务场景：拿真实案例压模型

## 这份文档是什么

五个具体业务场景，用来**检验模型是否成立**。它们不是需求——**全部由主 Agent 拟定，未经业务确认**，标 `待确认`。

用法：**每次核心业务模型改动后，把这五个场景重跑一遍**，看是否还能完整表达。表达不了的地方就是模型的洞。

后续这五个场景应转成 `test/` 下的业务回归用例，见根 [`AGENTS.md`](../../AGENTS.md)「业务回归用例」。

## ① 新客首单转化 `待确认`

> 注册满 24 小时还没下单的人，发一张新人券；3 天后没用，短信提醒一次。

| 踩到模型的哪里 | |
|---|---|
| 进入方式 | **持续进入**——人一个一个流进来 |
| 投放项 | **两个，不是一个流程**：发券（动作 = 发权益）、短信（动作 = 发短信） |
| 多步怎么串 | 第二个的触发器是「领了券 + 过了 3 天 + 未使用」，**靠事件串**；「领了券」是平台自己发的事件回流成来源 |

## ② 双十一预热分组实验 `待确认`

> 圈近 30 天有加购的 10 万人，测哪种触达组合转化最好。
> A 对照 / B 只短信 / C 短信 + 券 / D 只券

| 踩到模型的哪里 | |
|---|---|
| 进入方式 | **一次性圈选** |
| 分组 | 分桶切 4 份（实验服务） |
| 对照组 | **A 组挂 0 个投放项**，但必须在系统里——否则事后分不清「对照组」与「压根不在人群里的人」 |
| 失败的人 | 短信发失败的**仍算 B 组**（ITT） |
| 指标 | 实验指标归实验服务；「发了多少条」归运营平台 |

## ③ APP 首页 banner 个性化 `待确认`

> 用户打开 APP，首页 banner 位。大促活动与会员召回都想投；大促内部还要新客看 A 图、老客看 B 图。

| 踩到模型的哪里 | |
|---|---|
| 进入方式 | **人找我们**——APP 拿 uid 来问，平台当场算（判定，必须快） |
| 抢位 | 大促优先级 100 > 召回 50。**召回输了**：不计频次、仍算它的实验组、**要留痕** |
| 大促内部分流 | **决策表**：新客 → `T1`、老客 → `T2`、其他 → 不走 |
| 同活动抢同一位 | `T1`/`T2` 靠**人群互斥**放行（放宽后的抢位规则） |
| 结果 | **没有「发放成功」**——返回 id 之后有没有被看见，不知道 |

## ④ 新玩法灰度放量 `待确认`

> 自动发券的新玩法，先放 5%，观察 3 天，再到 20%、100%。

| 踩到模型的哪里 | |
|---|---|
| 放量机制 | **分桶切 100 份，逐步纳入**，不是新机制 |
| 旋钮位置 | 挂在**活动**上，下面所有投放项一起放 |
| 为什么必须用分桶 | 分桶稳定 → **已进来的人不会在下次放量时掉出去**。用「随机取 5%」会把先进来的人悄悄踢出，**且不报错** |

## ⑤ 跨境召回 · 两级触达 `待确认`

> 90 天未活跃的用户，先发 WhatsApp；4 小时后未读的，转发短信。

| 踩到模型的哪里 | |
|---|---|
| 条件分流 | 「发过 WhatsApp 且 4 小时 且 未读」就是一个普通人群定义，数据来自平台自身执行结果回流 |
| 回流延迟 | 4 小时合法（回流小时级）。若运营想配「发完 10 分钟」，**平台应在界面上拦住** |
| 幂等与重试 | 接口超时 → 按重试策略重试 → 下游必须幂等，**三次重试用同一个幂等键** |
| 失败的人 | 重试耗尽的**仍算实验组** |

## 这五个没覆盖到的

补场景时优先补这些：

- 外部名册导入（受众侧故事 4，`待确认`）
- 圈人时排除黑名单 / 内部员工（受众侧故事 5，`待确认`）
- 多个活动共用同一份人群定义（受众侧故事 15，`待确认`）
- 「跟某次分流对齐」的实验（边界文档，已确认但无场景）
- 按素材归因——**已知做不了**（活动侧事实 39）
