# Issue #88：纯业务 Core 与 MySQL 持久化应用层

关联 Issue [#88](https://github.com/snack8310/gmp/issues/88)；分支 `feat/88-pure-core-mysql-layer`。新需求开发，大任务；高风险。

## 任务入口检查

### 分类与问题本质

- 类型：新需求开发，含架构边界调整与 MySQL 持久化。
- 等级：大任务。理由：会调整 `gmp-core` 的存储职责，新增外层业务应用与 MySQL 适配，并涉及实验染色、执行状态与回执等跨模块生命周期。
- 用户表面请求：用 MySQL 保存真实业务数据，并用真实业务结构支撑 CRUD。
- 用户确认的核心方向：`gmp-core` 是业务模型的足够抽象，不应持有任何数据存储，包含内存 Store；真实 CRUD、持久化与外部 I/O 位于基于 Core 的外层业务应用。
- 要解决的真实问题：当前 Core 含内存实现，`management` 又维护独立的演示结构与内存 Store。只把后者替换成 SQL 仍会留下两套模型，无法证明 CRUD 遵守 Core 业务规则。
- 硬约束：Core 只接收明确的业务输入并产出决策 / 状态转换；不导入数据库、网络、时钟、调度或渠道实现；不能因拆分而改变稳定分组、幂等重试与执行回执关联语义。
- 方案选择：纯 Core + 外层应用编排 + MySQL / 数据源 / 渠道适配器。用户已授权开始实现；确认 Core 不持有存储、人群成员通过来源接口获取、首个来源只读查询 MySQL 用户池，外层负责受众 / 实验 / 活动存储。
- 补充确认（2026-11-08）：当前开发提供一张独立用户名单来源表和构造 SQL 种子数据，与平台管理表位于同一 MySQL 数据库，并复用同一个应用连接池；运行中的来源适配器仍只发只读查询，不复制名单快照。该样例不是外部生产用户池，也不表示已获生产数据访问授权。
- 补充确认（2026-11-08）：本次 MySQL 开发范围包括执行记录与回执持久化。Outbox 未被选入本次范围；跨进程可靠投递与崩溃恢复不能据此宣称已保证。用户确认同一 execution key 下首次有效回执生效；完全相同回执重放幂等，任何冲突回执拒绝且不得推进另一条流程边。
- 修复授权（2026-11-08）：用户批准修复独立评估器发现的并发相同回执重复发布 / 重复沿边问题。实现采用 `ReceiptAcceptor` 原子地区分首次接受与同值重放；Runner 只让首次接受者发布回执事件并推进流程边。

### 范围与非目标

- 本轮目标范围：将 `gmp-core` 收敛为纯业务模型 / 规则 / 决策；把受众、实验、活动的来源读取、持久化与应用编排放到外层 `management` 应用及适配器；保持现有 `/api/v1` 请求 / 响应兼容；从同一应用 MySQL 连接池只读查询独立用户名单来源表；持久化活动执行记录与回执。
- 外层持久化目标：包括受众配置 / 人群组 / 实验人群包、实验分流定义与染色记录、活动 / 投放项 / 流程定义、执行记录与回执。Outbox 不在本次已确认范围；不因此承诺跨进程可靠投递或崩溃恢复。实际实现仍须分阶段并如实标注未完成项，不得落回 Core。
- 非目标：不发送真实触达、不接入券系统、不做生产部署与权限体系；用户池的实际 schema、字段、查询约束未提供前不连接真实用户池、不臆造查询。历史演示种子和浏览器草稿不自动回填。
- 外部读 / 写影响：平台管理表与本期 demo 用户池位于同一 MySQL 数据库并复用同一应用连接池；平台自有表会写入本期已实现的管理配置、执行与回执状态，用户池适配器代码路径只读。生产用户池所在实例和部署账户的权限隔离仍未知。来源查询只取求值所需数据，不写回来源、不保存来源成员快照或来源原值；连接配置缺失时必须失败，日志不得含凭据或成员载荷。

### 实现验收标准

1. `gmp-core` 不含内存 Store、来源 Feed、数据库 / 外部 I/O 端口、执行日志实现或依赖外层服务的有状态注册表；核心规则以显式值输入 / 输出表达。
2. 外层 `management` 使用 `gmp-core` 业务规则，承接受众来源查询、实验与活动 CRUD、MySQL 持久化和运行态编排；不能继续以独立规则实现同一业务语义。
3. 现有 `/api/v1` 路由与 JSON 契约保持兼容；连接配置、迁移和 schema 检查失败时启动明确失败，不切到内存实现。
4. 首个受众来源适配器只读查询 MySQL 用户池，平台筛选按人群配置执行；平台不保存来源成员快照或来源原值，只保留领域规格允许的数量与来源侧定位。
5. 实验染色唯一性、活动流程回执关联、UID / execution key / placements 延续、重试幂等在外层存储边界保持；不改变既有业务语义。
6. MySQL 适配器契约覆盖 CRUD、迁移、事务与并发唯一性；纯 Core 场景覆盖已确认业务不变量；验证结果来自真实执行命令。

### 风险三档

- 真风险（阻断）：当 Core 仍保留内存 Store 或 MySQL 具体实现时，存储职责没有离开 Core；须由包结构、依赖方向与代码搜索证据证明。
- 真风险（阻断）：当持久化不覆盖唯一性、事务、染色及回执生命周期时，重启或并发可能造成分组漂移、重复触达或悬空执行；须先定实体与事务边界。
- 真风险（放行后续跟进）：首稿用户名单表为构造 demo；生产来源 schema / 授权仍未知，且同一应用账户未必在数据库权限层只读来源表。adapter 在代码路径中只发 SELECT，但不能据此声称生产权限隔离。
- 真风险（仅观察）：外层服务的应用接口和内部 Core 类型映射可能增加维护成本；需保持映射边界显式，并避免平行的第二套业务真源。
- 伪风险：Core 无 Store 不等于流程没有状态模型；Core 可接收已有状态作为值并返回下一状态，外层负责加载和提交。
- 未讨论项（实施阻断 / 评估器攻击点）：执行 / 回执保留期限；同一连接池共享时如何限制来源表写权限；现有浏览器演示数据如何处理；跨模块业务回归与外层集成测试分别落在哪个 module。Outbox 已明确不在本期。
