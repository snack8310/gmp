# Issue #88：纯业务 Core 与 MySQL 持久化应用层

关联 Issue [#88](https://github.com/snack8310/gmp/issues/88)；分支 `feat/88-pure-core-mysql-layer`。新需求开发，大任务；高风险。

## 任务入口检查

### 分类与问题本质

- 类型：新需求开发，含架构边界调整与 MySQL 持久化。
- 等级：大任务。理由：会调整 `gmp-core` 的存储职责，新增外层业务应用与 MySQL 适配，并涉及实验染色、执行状态与回执等跨模块生命周期。
- 用户表面请求：用 MySQL 保存真实业务数据，并用真实业务结构支撑 CRUD。
- 用户确认的核心方向：`gmp-core` 是业务模型的足够抽象，不应持有任何数据存储，包含内存 Store；真实 CRUD、持久化与外部 I/O 位于基于 Core 的外层业务应用。
- 要解决的真实问题：当前 Core 含内存实现，`management` 又维护独立的演示结构与内存 Store。只把后者替换成 SQL 仍会留下两套模型，无法证明 CRUD 遵守 Core 业务规则。
- 硬约束：Core 只接收明确的业务输入并产出决策 / 状态转换；不导入数据库、网络、时钟、调度或渠道实现；不能因拆分而改变稳定分组、幂等重试与执行回执关联语义。
- 方案选择：纯 Core + 外层应用编排 + MySQL / 数据源 / 渠道适配器。用户已确认此架构方向；本轮 draft MR 先送审设计，不进入代码实现。

### 范围与非目标

- 本轮范围：正式说明纯 Core、应用编排、存储与外部适配器的职责；记录运行时调用顺序、持久化候选实体及未决问题；更新任务卡与设计稿。
- 后续实施范围（待实体清单确认）：把内存 Store 移出 `gmp-core`，使外层业务服务组合 Core 类型与规则，新增真实 CRUD、MySQL schema / migration、事务边界和存储契约验证。
- 非目标：本轮不改代码、不连接 MySQL、不接入真实名单或券系统、不发送真实触达、不做生产部署与权限体系；不臆造客户数据结构、连接配置或历史迁移。
- 外部读 / 写影响：本轮只读 GitHub issue 与仓库内容；不接触数据库、缓存、队列、客户数据或渠道。后续实施预计读写 MySQL，并需按确认后的范围记录外部数据源 / 渠道的影响面。

### 风险三档

- 真风险（阻断）：当 Core 仍保留内存 Store 或 MySQL 具体实现时，存储职责没有离开 Core；须由包结构、依赖方向与代码搜索证据证明。
- 真风险（阻断）：当持久化不覆盖唯一性、事务、染色及回执生命周期时，重启或并发可能造成分组漂移、重复触达或悬空执行；须先定实体与事务边界。
- 真风险（放行后续跟进）：真实名单来源和真实渠道不在默认范围；adapter 契约可留后续实现，但不可宣称真实业务可运行。
- 真风险（仅观察）：外层服务的应用接口和内部 Core 类型映射可能增加维护成本；需保持映射边界显式，并避免平行的第二套业务真源。
- 伪风险：Core 无 Store 不等于流程没有状态模型；Core 可接收已有状态作为值并返回下一状态，外层负责加载和提交。
- 未讨论项（实施阻断 / 评估器攻击点）：究竟持久化定义数据还是同时包含染色、执行、回执与发件箱；现有浏览器演示数据如何处理；跨模块业务回归与外层集成测试分别落在哪个 module。
