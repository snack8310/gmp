## 问题本质

- **用户表面请求**：把 #12 收了。
- **实施中先做的一件事是核实 #12 还剩什么**。结果：**正文中引用旧版 `docs/domain/README.md` 约定的条目已失效**——状态机流转矩阵、不变量固化层级列、引用纪律在 README 重写后都已不存在。本卡只承接现行约定仍支持的部分。
- **要解决的真实问题**：`test/docs/consistency_check.py` **零测试**，而它的每一条检查都是发现驱动的——改个目录名或标题，循环体一次都不执行，退出码照样是 0。**#12 的硬约束 1 正是「脚本自身必须配空断言变异测试」**，这是所有新增检查的前置：没有它，新加的检查只是更多不知道自己有没有在工作的绿灯。
- **硬约束**：见 issue #12「硬约束」四条。
- **已考虑并否决的更本质解法**：继续靠评估器人工发现——否决理由见 issue #12 正文（同型缺陷每轮复现、发现成本高、修复成本极低）。
- **成功标准**：每条检查都有一个「破坏它之后必须红」的用例；且变异框架自身也被证明有齿。

## 评估器重点

- **需要重点攻击的反例**：
  1. **变异框架自身是否有齿**——删掉一条下限断言、或把一条检查改成永远不报错，框架必须红。
  2. **夹具是否完整**——夹具缺了被链接到的目录时，链接检查会对所有外链报假阳。**本轮实施中正是变异用例抓到了这一点。**
  3. 下限断言是否按遍历基准**分别**计数——合并计数时，一个基准消失而另一个还在，检查仍会通过。**本轮实施中也正是变异用例抓到了这一点。**
  4. 被撤掉的那条检查是否真的无法做到高精度，还是我放弃得太早。
  5. `design-system.md` 重排后取值是否一个未变。
- **需要检查的历史规则**：上方清单逐条，含判定不适用的一条。
- **需要核对的验证证据**：必跑命令真实退出码；元变异实证；CI 的 `headSha` 等于送审 SHA。
- **需要判断是否新增抽象记忆**：候选——「给检查写变异用例时，最先被抓到的往往是夹具与下限断言本身的缺陷」。本轮有两处实测实例。由评估器裁定。
