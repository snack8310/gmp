# 任务入口检查：gmp-core 第六轮 · 事件与回流

关联 issue：#40 ｜ 分支：`feat/40-events-and-backflow`

## 任务分类

- 类型：新需求开发
- 等级：**大任务**
- 判断依据：首次引入事件这个业务对象；跨全部四层；命中项目高风险清单第 1 条（平台自身事件的语义与关联方式）。

## 问题本质

- **用户表面请求**：做事件与回流。
- **要解决的真实问题**：事实 18——**执行结果必须回流成为受众服务的一个来源，这是条件分流成立的前提**。没有它，「多步靠事件串」只是一句话，第二步没有任何东西能让它知道该对谁动手；而回流没接上时，第二步是一个人都不触发，**看起来跟「条件太严」一模一样**。
- **让本轮比看起来小的一条事实**：事实 17 明写「条件分流不需要任何新概念，它就是一个人群定义加一个投放项」。**本轮因此不引入触发器机制**——第二步就是一个普通的批量投放，只是人群定义建在回流来源上。
- **硬约束**：H1–H10，见 issue #40。
- **已考虑并否决的更本质解法**：见 issue #40「A 是不是唯一方式」表（独立触发器与编排 / 让 `audience` 直接读执行日志 / 核心持有时钟 / 用回执表达「未读」）。
- **成功标准**：issue #40「验收标准」每条能被一个命令或一个测试判定。

## 范围

- **范围内 / 非目标**：见 issue #40。**特别地：触发器机制、事件时序（乱序重复延迟）、事件持久化与重放全部在非目标内**；`docs/domain/` 语义一字不动。
- **影响面**：`gmp-core/campaign/` 新增事件与回执结构（`RecordReceipt` 签名改为 `Receipt`）；`gmp-core/scenarios/` 新增回流桥接与两步场景；`cmd/gmp-demo` 新增一节；根 `AGENTS.md` 的场景清单。`audience` 与 `experimentation` **不改动**。
- **外部系统读写影响**：无。事件投递是端口，本轮只给桥接实现。

## 人工确认

- **是否需要实施前人工确认**：**是**。
- **需要确认的问题**：五项**按规格与先例自行裁定并如实标注**，不阻塞实施。
  1. **事件名由「动作 + 发生了什么」组合**（U1）。平台为自己的事件命名，取值确定性推导。
  2. **回执带回的渠道说法是键值对，核心不解释**（U2）。与事实 37「内容是动作的参数，一个动作一个说法」同形。
  3. **事件去重本轮不做**（U3）。事件带幂等键，去重由订阅方承担。
  4. **回流桥接放在 `scenarios`**（U4）。它是唯一同时看见两层的地方，`Stack` 已有先例。
  5. **事件出口必填**（新增）。`DiscardEvents()` 让「无人订阅」成为写下来的决定——丢事件看起来就跟第二步条件太严一模一样。
- **已确认事项与来源**：同前几轮，诚实性边界不变。

## 评估器重点

- **需要重点攻击的反例**：
  1. **两步之间是否真的互不相识**——第二步的配置里有没有任何指向第一步的引用。
  2. **事件名是否足以区分动作**——若不能，为一个动作配的条件会被另一个动作的事件满足。**本轮实施中正是变异暴露出缺少这条断言，已补。**
  3. **演练是否在某条路径上仍发了事件**——演练发出的事件会触发下一步，等于演练启动了它要预览的运行。
  4. **失败的第一步是否仍可能发出「已送达」事件**。
  5. **时间是否真的只归回流来源**——核心里有没有任何一处读了当前时间。
  6. 回流桥接放在 `scenarios` 是否在把基础设施塞进场景包（U4）。
  7. 场景 ① 的「未使用」缺席是否被正确地标记为缺席，而不是被近似掉。
- **需要检查的历史规则**：上方清单逐条，含判定不适用的两条。
- **需要核对的验证证据**：必跑命令真实退出码；六条变异实证；CI 的 `headSha` 等于送审 SHA。
- **需要判断是否新增抽象记忆**：候选——「变异跑出全绿时，缺的往往不是实现而是断言」。本轮有实测实例（事件名不带动作那一条）。由评估器裁定。
