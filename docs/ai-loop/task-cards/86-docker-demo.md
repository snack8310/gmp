# 任务卡：运营演示的 Docker 构建与编排

关联 issue [#86](https://github.com/snack8310/gmp/issues/86)。用户于 2026-11-06 在本会话确认采用双容器方案。

## 任务入口检查

### 任务分类与问题本质

- 类型：重构优化；等级：大任务。原因是部署入口同时涉及前端演示和管理 API 两个服务，命中根 `AGENTS.md` 高风险通用标准 7。
- 表面请求：构建 Dockerfile，准备部署演示。
- 真实问题：目前必须在本机分别运行 Node 同源入口与 Go 管理 API；入口固定使用回环地址，现状不能直接在独立容器中连通。
- 硬约束：不改变现有本机启动方式和管理 API 契约；API 不发布宿主机端口；默认只在宿主机回环地址开放页面；不宣称生产就绪。
- 已考虑并否决的方案：单容器同时运行 Node 与 Go，需额外处理进程退出和信号转发；只容器化静态页面，活动管理 API 会不可用。用户已选择独立服务编排。
- 成功标准：镜像可构建，Compose 可启动，宿主机访问页面及同源 API 成功，直接本机运行仍可用。

### 范围与影响

- 范围内：Dockerfile、Compose、构建上下文排除规则、前端入口的监听与上游主机配置、运行文档和相关验证。
- 非目标：远端部署、公开互联网访问、鉴权、生产存储、多实例、真实渠道、`gmp-core` 与管理 API 契约修改。
- 影响面：容器内的 Node 页面服务和 Go 管理 API；浏览器仍通过同源入口访问 API。
- 外部系统读写影响：构建与启动读写本机 Docker 守护进程；浏览器经前端代理读写 API 进程内构造状态。无生产数据库、缓存、消息队列和真实渠道读写。

### 最小验证集与约束落地

- 必跑：`docker compose config -q`、`docker compose build`、`docker compose up` 后宿主机 HTTP 页面与同源 API 检查、管理 API `go build ./...` / `go test ./...`、前端相关回归、`python3 test/docs/consistency_check.py`、`git diff --check`。
- 必查边界：容器 API 无宿主机端口映射；前端上游失败返回可判别的 502；配置为空时启动失败；本机默认回环行为保留；容器重启使 API 进程内编辑重置。
- 未覆盖：远端网络、TLS、访问控制、生产存储、真实数据和真实执行。
- 新约束：容器版必须显式给出监听与上游主机；通过启动参数校验、Compose 配置及真实 HTTP 验证落实，无需新增散文规则。

### 风险三档与评估器重点

- 真风险·阻断：当代理指向错误主机时页面仍可打开但活动 API 不可用；容器验收必须穿过同源代理请求 API。
- 真风险·阻断：当未鉴权的演示入口直接暴露公网时，访问者可改写当前进程内活动；默认端口只绑定宿主机回环地址，文档说明外部访问必须另配访问控制。
- 真风险·仅观察：当容器重启时 API 内存编辑丢失，浏览器草稿仍只留在原设备；运行说明明确边界。
- 伪风险：未接真实渠道或生产存储不构成本轮缺陷，因为本轮仅封装构造数据演示，不迁移真实数据。
- 未讨论项（交评估器攻击）：任一容器异常退出或 API 未就绪时用户看到什么；端口配置异常是否导致 API 直接暴露。
- 评估器重点核对：同源代理、配置失败、端口隔离、原本机兼容性、日志不含敏感内容、实际构建与 HTTP 证据。
