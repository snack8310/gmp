## 问题本质

- **用户表面请求**：做事件串和执行侧。
- **主 Agent 的拆分与理由**：三样东西（执行侧、事件与回流、「我们找人」方向）一轮做完是 PR #14 整份作废的规模。**本轮只做执行侧与批量投放方向**；顺序不可颠倒，事件是从执行产生的。已向用户说明并获同意。
- **要解决的真实问题**：事实 48 那条约束——**幂等键必须贯穿决策 → 执行 → 回执三段**。三段里此前只有第一段存在，而它的三种失效全部不报错：键在重试之间变了、回执带着对不上的键被静默丢弃、下游声称幂等而实际不是。
- **硬约束**：H1–H12，见 issue #38。
- **已考虑并否决的更本质解法**：见 issue #38「A 是不是唯一方式」表。
- **成功标准**：issue #38「验收标准」每条能被一个命令或一个测试判定。

## 人工确认

- **是否需要实施前人工确认**：**是**。
- **需要确认的问题**：四项**按规格与先例自行裁定并如实标注**，不阻塞实施。
  1. **幂等键由「活动 + 投放项 + 分流键 + 本次进入的标识」组合**（U1）。「本次进入的标识」必填、由触发方给出——只有触发方知道这是新的一次进入还是一次重试（受众侧事实 4）。
  2. **一次执行只引入本轮动作能直接产出的状态**（U2）：已投递 / 投递失败 / 已送达 / 未送达。不建完整状态机——`interaction-invariants.md` 待澄清 D1 未表态。
  3. **回执只收「成功与否」加一个外部标识**（U3）。规格未表态，按不臆造处理。
  4. **批量按顺序逐个处理**（U4），如实记为内存实现测不出并发的一类。
- **已确认事项与来源**：同前几轮，诚实性边界不变。

## 评估器重点

- **需要重点攻击的反例**：
  1. **键真的在三段间不变吗**——决策产出、投递携带、回执查找三处是否确为同一个值，还是看起来一样。
  2. **重试复用同一键是结构保证还是纪律**——能否在不改构造输入的前提下让重试拿到不同的键。
  3. **投递侧契约套件能否把「声称幂等而实际不是」区分出来**——若不能，接入验证等于没有。
  4. **回执对不上时是否真的报错**，还是某条路径上被吞掉。
  5. **演练是否在某个分支上仍写了记录或发了投递**。
  6. 「本次进入的标识」必填是否真能挡住「同一个人重复进入被当成重试」。
  7. 执行记录是否**两个字段都带**——只带一个会让某一侧的结果算不出来。
- **需要检查的历史规则**：上方清单逐条，含判定不适用的两条。
- **需要核对的验证证据**：必跑命令真实退出码；六条变异实证；CI 的 `headSha` 等于送审 SHA。
- **需要判断是否新增抽象记忆**：候选——「跨阶段必须一致的标识应当由输入推导而非每阶段生成，使一致性成为结构而非纪律」。由评估器裁定。
