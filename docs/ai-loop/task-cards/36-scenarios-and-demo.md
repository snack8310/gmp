- **硬约束**：H1–H6，见 issue #36。
- **已考虑并否决的更本质解法**：见 issue #36「A 是不是唯一方式」表（做成能服务请求的系统 / 只做 demo / 只做 scenarios / 一次做完五个场景）。
- **成功标准**：issue #36「验收标准」每条能被一个命令或一个测试判定。

## 范围

## 人工确认

- **是否需要实施前人工确认**：**是**（`risk/high`，且触及规则真源）。
- **需要确认的问题**：三项**自行裁定并如实标注**，不阻塞实施。
  1. **`cmd` 不受分层约束**（U1）——装配根按定义要看见所有层。已在代码中写明理由，并由「表完整性」断言把它显式排除而非默默漏掉。
  2. **demo 的输出不做快照断言**（U2）——快照会把可读性改动变成红灯。CI 只断言它能跑通且退出码为 0。
  3. **`AGENTS.md`「业务回归用例」改为逐场景如实清单**（U4）——不停在「尚未建立」，也不含糊地写「已建立」。措辞交人工裁定。
- **已确认事项与来源**：技术栈 Go、`gmp-core` 为本仓库内子项目、份号从 1 起，出处同前几轮，诚实性边界不变。

- **需要重点攻击的反例**：
