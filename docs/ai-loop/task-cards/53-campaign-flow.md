关联 issue：#53 ｜ 分支：`cursor/campaign-flow-edges-65b8`

## 任务分类

- 类型：新需求开发
- 等级：**大任务**
- 判断依据：首次把活动流程与边落成 `gmp-core/campaign` 的类型与执行路径；命中根 `AGENTS.md` 高风险清单第 1 条（活动流程 / 边的语义、条件与关联方式），并改动回执与下一步执行的关联。

## 问题本质

- 用户表面请求：在 `gmp-core/campaign` 增加活动流程与边，让活动内串行 / 按回执分支沿边走，并保持一个投放项一个动作。
- 要解决的真实问题：事实 68、69 已裁定活动内下一步以边为准，但投放项注释与执行路径仍把「投放项互不相识、第二步只能建在回流人群上」写成唯一做法。不落成可执行的边，这条裁定在运行时不存在，活动内分支会继续静默退化成「再建一份人群」。
- 硬约束：一个投放项仍一个动作（事实 52、64）；边的条件来自动作回执的成功 / 失败 / 契约定义的其他结果（事实 65、69）；无边相连的多个入口投放项仍可并行（事实 67、69）；回流仍保留给实验、圈人、跨活动与边上未表态的时间条件（事实 18）；不臆造边的时间条件、流程运行态状态机，也不把同步受理默认当成契约成功。
- 已考虑并否决的更本质解法：继续只用回流人群表达活动内分支。事实 67 的首版就是这个解法，同日已被事实 68、69 推翻——它让「走错边」和「人群条件过严」看起来一样，且运营看不到完整的线。把多步塞进一个投放项同样否决：那会推翻事实 52、64。
- 成功标准：边在回执结果匹配时把**同一个人**送进下一步，且该下一步的人群可以谁都不命中；RCS 成功只去邮件、失败只去短信；没有连接边的多个入口投放项各自仍能跑；`go test ./...` 与分层检查通过。

## 范围

- 范围内：`gmp-core/campaign` 的活动流程、边、动作回执契约结果、沿边投递；覆盖串行、按回执分支、并行入口的测试；仍写着「多步只靠互不相识的投放项 / 没有编排器」的注释与演示文案。
- 非目标：人群配置 / 人群组 / 实验人群包改名；完整 frontend demo；边上的「等待 N 天」；活动 / 投放项 / 活动流程运行态状态机（D1）；把领域文档 D2 的英文产品名标成已定；改写历史变更证据里已被推翻的首版记录。
- 影响面：`gmp-core/campaign` 的动作、活动、执行回执；`gmp-core/scenarios` 与 `gmp-core/cmd/gmp-demo` 里记录回执的调用点（签名增加活动参数）；相关注释。`audience` 与 `experimentation` 不改。
- 外部系统读写影响：无。投递仍走既有端口，本轮不接真实渠道。

## 人工确认

- 是否需要实施前人工确认：**是**（清单第 1 条）。
- 已确认事项与来源：活动流程为一等公民、边的条件来自动作回执、一个投放项仍一个动作、并行是无边相连的多个入口投放项——事实 52、64、65、67、68、69、70 与两则确认记录已在 main（PR #52）。issue #53 要求按该语义实现。
- 按规格自行裁定、不阻塞实施，并写明：
  1. 代码类型名用 issue #53 的 `Flow` / `Edge`。领域文档 D2 仍写产品英文名未定；本轮不回写领域文档把 D2 标成已关闭。
  2. 边的种类必填。零值不是「无条件并行」——漏填条件若被当成并行，下一步会对整个人群发出而不是等回执。并行边必须写成 `parallel`；不连边同样表示并行。
  3. 回执边只把回执所属的那个人交给目标投放项，不枚举目标人群、不重查放量。否则目标人群谁都不命中时，边会静默不走。
  4. 同步受理不自动合成契约成功。边上的成功只认回执里的契约结果。
  5. 回执边的目标必须是推送动作。拉类没有批量投递，留到回执时才发现会让回执已记下、下一步却没人发出。

## 风险点

### 真风险

1. **阻断**：当回执没带契约结果、或结果不在动作契约里时，若仍去投递下一步，会走错边且不报错。构造与回执校验拒绝这种回执，并用用例锁住。
2. **阻断**：当目标投放项仍按自己的人群枚举时，人群谁都不命中会让边静默不走。沿边投递只使用回执上的人，用例里的目标人群为空仍会送达。
3. **阻断**：当同一回执记两次时，若下一步另起一个键，同一个人会再收一次。下一步的键由上游执行键推导，已落定的执行不再投递。
4. **阻断**：当回执边成环时，后续回执会把同一个人送回上游。构造期拒绝环。

### 伪风险

1. 并行投放项抢同一个展示位。展示位互斥仍是事实 7、23，本轮不放宽。并行在测试里用不同的位，表达的是「没有回执边」，不是「两个投放项抢一个位」。
2. 场景 ⑤ 会因为引入边而坏掉。那两个活动没有活动流程，回执也不带契约结果，批量跑第二步的路径不变。
3. 为签名变更做兼容垫片。没有仓库外调用方，垫片会留下一条不带活动、因此看不见边的回执入口，漏走边时看起来像没人匹配。

### 未讨论项

1. 边是否支持「等待 N 天」——规格未表态。本轮不做。评估器攻击点：实现是否用回流时间或回执上的时间戳充当时长条件。
2. 同步受理是否等于契约成功——规格未表态。本轮不在 `Run` 结束时走出成功边。评估器攻击点：没有回执时成功边是否已经投递。
3. 活动流程运行态状态机（D1）——未表态。不新增流程状态。评估器攻击点：是否发明了运行中的流程状态。
4. 产品英文名（D2）——未在领域文档关闭。评估器攻击点：是否改了领域文档里的英文名裁定。
5. 同一个契约结果引出两个不同的目标投放项——规格没有禁止。本轮两条边都会走，键不同，是两次投递。评估器可核对这是不是把一次投递发了两遍。

## 约束落地方式

- 本次是否新增约束：是。
- 能否由类型 / 接口固化：能。一个投放项只有一个 `Call`；边的种类没有零值；动作一旦列出回执结果就必须同时有成功和失败；回执边的结果必须是源动作声明过的。
- 能否由自动化检查固化：行为由 `go test ./...` 覆盖。不另写一份只存在于文档里的纪律。
- 若仍不能：等待时长与运行态状态机不是本轮约束，保持未表态。

## 评估器重点

- 需要重点攻击的反例：
  1. 送达与否被当成成功 / 失败，契约结果被绕开。
  2. 目标人群或放量把边上的人静默滤掉。
  3. 没有回执时，`Run` 已经把成功边的下一步发出去了。
  4. 同一回执再记一次，下一步又发出去了。
  5. 非入口投放项仍能按人群批量跑，和边各发一次。
  6. 漏填边的种类被当成并行，整个人群被发出。
  7. 注释或演示文案仍把「投放项互不相识」写成活动内多步的唯一做法。
  8. 场景 ①⑤ 被改成边，或时间条件被偷偷做进边里。
- 需要检查的历史规则：上表，含判定不适用的几条。
- 需要核对的验证证据：`go test ./...` 的真实退出结果；分层检查随该命令执行。
- 需要判断是否新增抽象记忆：候选是「活动内下一步的人选来自回执上的那个人，不来自目标投放项的人群枚举」。由评估器裁定是否写入 `docs/history/memory/`。
