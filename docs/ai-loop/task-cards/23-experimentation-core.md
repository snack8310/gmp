## 问题本质

- **用户表面请求**：写 `gmp-core`。
- **要解决的真实问题**：把领域语义从散文降级到「约束落地优先级」的第 1、2 层。仓库至今零业务代码，`docs/domain/` 的断言没有一条能被机器证伪——`2026-08-31-business-scenarios-confirmed.md` 的「回退变异」是实测证据：整轮改动完整回退后门禁仍全绿。写代码是手段，让「分桶必须稳定」「放量必须单调」变成**会失败的测试**才是目的。
- **硬约束**：H1–H10，逐条见 issue #23「硬约束」表。本卡不复述，避免与来源分叉。
- **已考虑并否决的更本质解法**：见 issue #23「A 是不是唯一方式」表（文档机检清单 / 直接接真实存储 / 自顶向下从 campaign 起 / 一轮做完整个 gmp-core）。
- **成功标准**：issue #23「验收标准」每一条都能被一个命令或一个测试判定，且这些检查在 CI 上真跑。

## 范围

- **范围内**：`gmp-core` 子项目骨架与依赖分层承载；Go 构建 / 测试 / `go vet` / 依赖方向检查接入既有 `gates` workflow；`experimentation` 领域模型与内存实现；该层的场景断言（业务场景 ② 分组部分、④ 放量单调性部分）；契约测试骨架。
- **非目标**：见 issue #23「非目标」。**特别地：不修改 `docs/domain/` 的任何语义**——实施中发现规格有洞走澄清，不顺手改。
- **影响面**：新增 `gmp-core/`；修改 `.github/workflows/shell.yml`（扩为含 Go 的 `gates`）；新增任务卡目录 `docs/ai-loop/task-cards/`。
- **外部系统读写影响**：无。不接数据库、不接网络、不接外部渠道。CI 新增 Go toolchain 的获取。

## 人工确认

- **是否需要实施前人工确认**：**是**（`risk/high`，`AGENTS.md`「高风险操作额外卡点」要求实施前列出问题并等待确认）。
- **需要确认的问题**：Q1 时间依赖、Q2 版本化策略、Q3 验收基准、Q4 份号起始值。四问的选项与后果见 PR 正文与会话记录。**未答复前不进入实施。**
- **已确认事项与来源**：
  - 技术栈 Go：issue #23 的 H1，人工裁定。诚实性边界——出处是一份 issue 与它所属的一次会话，会话不在仓库内。
  - `gmp-core` 为本仓库内子项目：#21，已合并。
  - 五个业务场景各自成立：`business-scenarios.md`「确认记录」。**未确认「这些就是全部场景」**。
  - **Q1 已裁定：本轮不引入时钟，`experimentation` 无时间概念。** 人工给出的依据：定时触发交给外部基础设施（延迟队列 / 调度器），到点投事件，核心模型只对事件与状态作出反应，不问「现在几点」。逐场景核对结果：① 的 24 小时 / 3 天、⑤ 的 4 小时均为调度器到点投递后的状态查询；「发完 10 分钟」的拦截是两个配置值比大小；实验指标观测期比的是事件自带的时间戳；② 的「近 30 天」在数据源 / 受众侧，不在本轮。
  - **由 Q1 衍生的文档欠账（仅记账，本轮不动）**：`system-boundaries.md`「内存实现测得出来 / 测不出来」一节写着「时间的来源与事件的投递都必须是可被替换的依赖」并称其为唯一「现在不做以后很贵」的点，`AGENTS.md` 高风险清单第 17 条据此而立。**Q1 的裁定使该句前半截（时间的来源）不再成立**；后半截（事件的投递可替换）反而被外部调度器方案加强。本轮非目标含「不修改 `docs/domain/` 的任何语义」，故**仅登记，不在本轮修改，也未开 issue**。

## 评估器重点

- **需要重点攻击的反例**：
  1. 实现悄悄加了 H5 禁止的「按人群分流」便利接口，而两边都绿（U6 指出的具体路径）。
