## 问题本质

- **用户表面请求**：把「一个活动带一组关联 AB 实验的人群、各自做不同的事」加进 demo。
- **要解决的真实问题**：这个形状是场景 ② 的真实形状，**模型已经支持，仓库内却没有任何产物展示或保障它**。现状把场景 ② 拆成互不相连的两处：`showArms` 只列各臂人数（纯人群，不触达），`ArmDelivery` 只对单个臂投递且把它建成**自己的一个活动**。要拼出「一个活动挂多个臂」只能读代码后在脑子里合成。

  顺带暴露一条**不报错**的失效面：同一活动里两个投放项落在同一个位子上时，平台要求它们**能被证明互斥**，否则建活动即失败（`campaign/campaign.go` 的 `ErrSlotContestedWithinCampaign`）。实验的不同份是当前唯一能构成该证明的东西（`audience/exclusivity.go` 的 `ProvablyExclusive`）。该规则在 `campaign` 包内有守卫用例，但**没有任何地方按业务场景走一遍**——而运营真正会配的就是这个形状。
- **硬约束**：H1–H6，见 issue #43。核心两条：不改三层既有代码、不引入新领域概念来凑形状。
- **已考虑并否决的更本质解法**：见 issue #43「A 是不是唯一方式」表（只进 demo 不落用例 / 只落用例不进 demo / 改造既有 `ArmDelivery` / 顺手把实验指标一起做）。
- **成功标准**：issue #43「验收标准」每条能被一个命令或一个测试判定。

## 评估器重点

- **需要重点攻击的反例**：
  1. 新增用例是否**空转**——把某个臂的投放项从活动里删掉、或把某臂人群改空，用例是否真的变红？
  2. 「各臂拿到且只拿到自己那份动作」是否真的断言了**「只」**——只断言「拿到了」而不断言「没拿到别的」，等于没有覆盖串臂。
  3. A 对照组的断言是否只是「查不到」——「查不到」与「不在人群里」不可区分，正是场景 ② 点名要防的。
  4. 新增装配与 `ArmDelivery` 是否各写了一套人群定义（违反 H2 与上一轮的装配根共享约定）。
  5. 互斥失守用例是否真的因**互斥**而失败，而非因别的构造错误恰好也返回了错误。
