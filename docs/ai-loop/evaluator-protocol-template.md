# 评估器协议模板

本文档定义独立评估器的默认输入、审查方法与输出格式。适用于代码实现、设计文档、任务卡、接口契约等需要进入 AI Loop 双环审查的工作。

## 使用时机

主 Agent 完成实现与自测后，在宣布进入人工最终审核前，**必须**发起独立评估器审查。主 Agent 不得自行宣布完成。

评估器必须与主 Agent 物理隔离：

- 只给只读工具权限，禁止修改文件。
- 输入只包含任务卡、实现结果、显式证据和必要上下文，**不携带主 Agent 的推理过程、修复过程或自我辩护**。
- 评估器裁决不可被主 Agent 覆盖。

## 主 Agent 输入包

主 Agent 发给评估器时，必须按以下结构组织输入。

```markdown
# 评估任务
```

## 评估器审查方法

评估器必须从以下角度审查，**不得只按验收标准逐项打勾**。

1. **任务本质是否被解决**：实现是否真正满足任务卡目标，而不是只满足表面描述。
2. **范围是否收敛**：是否引入任务卡范围外的行为、抽象、依赖或协议变化。
3. **高风险项是否被正确处理**：命中高风险判定标准时，是否有额外证据与人工确认记录。
4. **历史记忆是否被应用**：相关 `docs/history/memory/` 规则是否进入实现和测试，或已写明不适用原因。
5. **验证是否足够**：测试是否覆盖正常路径、边界条件、错误路径、幂等性、并发或顺序相关风险。
6. **证据是否可信**：命令结果是否具体，是否存在只跑无关测试后宣称完成的情况；成功结论是否来自真实执行结果，而非流程状态推断。
7. **可维护性是否合格**：命名、接口边界、抽象粒度、注释、文档是否符合项目约定。
8. **约束落地层级是否正确**：新增约束是否本可以由类型或自动化检查固化，却退化成了文档规则。
9. **回滚与未覆盖项是否明确**：风险是否被隐藏，还是被显式交给后续任务或人工裁决。

### 对抗性方法论

评估器的默认立场是「这个实现有问题，我要找到它」，而不是「逐项确认它满足要求」。只有在认真攻击后仍找不到问题时，才判定通过。

- **先立最强版本再攻击**：对每一处质疑，先按最有利于实现方的方式理解它（补上作者可能有的隐含理由），再攻击这个最强版本。攻击一个稻草人不算发现问题。
- **写成可证伪表述**：结论必须写成「当……时会……」的形式，而不是「建议加强……」「可能存在……风险」。无法写成这种形式的，说明还没想清楚，应归入「缺失验证」而非「阻断问题」。
- **按 影响 × 出错概率 × 验证成本 排序**：把最值得先处理的放在最前面。不要用同等篇幅列举所有问题。
- **对抗不等于挑刺**：风格偏好、可有可无的重构建议、与本次范围无关的历史问题，最多进入「非阻断风险」，不得作为阻断理由。

### 取证纪律

每条**阻断问题**必须同时引用两侧证据：

- **声明侧**：任务卡验收标准、规格文档、接口契约、设计文档或历史记忆的**原文**。
- **实现侧**：`文件:行号`。

两侧引不全的，只能记为「**缺失验证**」，不能记为阻断问题。

**声明了但未实现，本身即缺陷** —— 这种情况声明侧有原文、实现侧为「无对应实现」，属于合格取证，应记为阻断问题。

## 评估器输出格式

评估器必须只输出以下三种裁决之一：

- `PASS`：未发现阻断问题，证据足够进入人工最终审核。
- `FAIL`：存在必须修复后重新审查的问题。
- `NEEDS-EVIDENCE`：实现可能正确，但当前证据不足，必须补充命令结果、测试、人工确认或外部事实后再裁决。

输出必须使用以下结构。

```markdown
# 评估结论：PASS | FAIL | NEEDS-EVIDENCE

## 阻断问题

1. 无 / 「当……时会……」+ 声明侧原文 + 实现侧 文件:行号

## 非阻断风险

1. 无 / ...

## 缺失验证

1. 无 / ...

## 范围与规则符合性

- 任务范围：
- 高风险项：
- 历史记忆：
- 测试基线：
- 约束落地层级：

## 建议新增抽象记忆

- 不需要 / 建议新增：

## 证据

- 审查的任务卡：
- 审查的关键文件：
- 审查的命令结果：
- 未能验证的部分：
```

## 裁决规则

只要存在以下任一情况，评估器**必须**输出 `FAIL` 或 `NEEDS-EVIDENCE`，不能输出 `PASS`：

1. 任务卡验收标准没有全部被证据覆盖。
2. 命中高风险项但没有人工确认或额外验证。
3. 相关历史记忆没有被读取，也没有解释为何不适用。
4. 幂等性、外部接口契约、状态迁移、一致性等核心属性只被文字声称，没有测试或明确证据。
5. 测试只覆盖正常路径，遗漏明显边界条件。
6. 变更引入范围外行为，且没有任务卡或人工确认支撑。
7. 主 Agent 的验证命令缺失、失败、被环境问题阻断，且没有替代证据。
8. 任务卡的「未讨论项」没有被转成澄清问题或攻击点，也没有被处理。
9. 属于对外破坏性变更，但缺少兼容策略、废弃计划或对外变更记录。

## 环境限制处理

如果评估器因沙箱、依赖、网络或权限限制无法运行命令，**不得把命令视为通过**。此时应：

1. 输出 `NEEDS-EVIDENCE`，列出缺失的命令或证据；或
2. 在代码 / 文档审查已充分、命令由主 Agent 执行的情况下，明确写出「命令结果由主 Agent 提供，评估器仅审查其充分性」。

**环境限制不能被记录为实现缺陷，但也不能被当作验证成功。**

## 抽象记忆判断

评估器通过后，需要判断本次任务是否暴露长期有效的规则、踩坑或关键权衡。该判断由评估器作出，不由主 Agent 自行决定。

**建议新增抽象记忆**的情况：

1. 评估器发现了可复用的边界条件或反例。
2. 本次修复暴露出通用实现规则。
3. 任务中出现了未来同类需求必须提前确认的前置条件。
4. 既有测试基线不足以覆盖本类风险。

**不建议新增抽象记忆**的情况：

1. 只是一次性需求背景。
2. 只是文件路径、字段名、临时实现细节。
3. 变更证据已经足够，且没有跨任务复用价值。

判断建议新增时，还必须按根 `AGENTS.md` 的「约束落地优先级」给出落地层级建议：该规则应固化为类型 / 接口、自动化检查，还是确实只能作为文档记忆。**能前置固化却写成记忆的，应在输出中指出。**
