# 任务入口检查清单

本文档定义主 Agent 在进入实施前必须完成的入口检查。它把自然语言需求整理成可评估、可验证、可审查的任务上下文，并作为 [评估器协议模板](evaluator-protocol-template.md) 的输入来源之一。

## 使用时机

主 Agent 在任何**代码、接口、配置、测试或项目文档修改前**，必须先完成本清单。

纯问答、只读分析、无需落地文件的讨论可以不填写完整清单；一旦进入文件修改，就必须补齐入口检查。

## 输出格式

入口检查建议直接写入任务卡；如果任务很小，也可以在对话中按以下结构列出，但**进入评估器审查前必须能追溯**。

## 分类规则

### 类型

- **新需求开发**：新增用户可见能力、接口、状态、实体类型或业务流程。
- **缺陷修复**：修正已存在行为、测试、文档或设计中的错误。
- **重构优化**：不改变外部行为，改善结构、命名、可维护性、测试或协作协议。
- **文档治理**：新增或修改协作规则、任务卡、变更证据、测试基线、README 或历史沉淀。

### 等级

**小任务**通常同时满足：

1. 影响文件少、边界清晰。
2. 不改变核心领域语义或外部契约。
3. 不触发高风险项，或只触发低风险文档说明。
4. 可用少量命令和人工复核完成验证。

**大任务**满足任一条件：

1. 涉及多个模块或跨服务。
2. 命中根 `AGENTS.md` 的任一高风险判定标准。
3. 需要持久化结构变更、数据迁移、数据回填或外部系统联调。
4. 验收依赖人工业务确认或多阶段验证。

判不准时按大任务处理。

## 问题本质要求

「问题本质」不是把用户请求换一种说法重写一遍，必须完成三件事：

1. **拆开表面请求**：用户说要做 A，真正想解决的问题是什么；A 是不是解决该问题的唯一方式。
2. **列出硬约束**：哪些条件不可协商（正确性、兼容性、性能下限、上线时间、既有契约）。
3. **验证有没有更本质的解法**：至少考虑一个「不这么做」的候选方案，并写明否决原因。不得直接套用惯例或已有实现的形状。

如果这三点写不出来，说明需求还没想清楚，不应进入实施。

## 高风险处理规则

只要任一高风险项为「是」，主 Agent 必须：

1. 在任务卡中明确标注高风险项。
2. 实施前列出需要人工确认的问题，并等待确认。
3. 将相关规格、历史记忆、验证方案放入评估器输入包。
4. 在变更证据中记录风险处理方式、验证结果和未覆盖项。

如缺少人工确认或验证证据，评估器应按 [评估器协议模板](evaluator-protocol-template.md) 输出 `FAIL` 或 `NEEDS-EVIDENCE`。

## 风险三档判定标准

风险点必须分三档，不能平铺成一张清单。

### 真风险

确实可能出问题，且后果可描述。每条必须写成可证伪的「当……时会……」表述，并标注处理档位：

- **阻断**：不解决不允许进入人工审核。
- **放行后续跟进**：本次接受，但必须记录到变更证据的未覆盖项，并有明确的后续动作。
- **仅观察**：本次接受，只需在文档中留痕。

### 伪风险

表面像问题、但经判断不成立的项。**必须写明为何不投入**，不能只写「不是问题」。写伪风险的目的是留下判断依据，避免同一个问题在后续任务里被反复重新讨论。

### 未讨论项

不确定是不是问题、且当前没有人在看的认知盲区。这一档是三档中最重要的一档：

- 每条必须转成一个**澄清问题**（交人工）或一个**评估器攻击点**（交评估器）。
- 不允许因为「暂时想不清楚」而省略；想不清楚本身就是这一档要记录的内容。
- 评估器有权因未讨论项未被处理而输出 `NEEDS-EVIDENCE`。

## 历史规则读取要求

入口检查阶段必须先读：

1. `docs/history/memory/` 中与任务相关的长期规则。
2. `docs/history/changes/` 中近期同领域变更证据。
3. 当前相关规格、功能文档或任务卡。

**历史命中必须落到规则级**，而不是只写「已读取某目录」。每条命中至少写明：来源文件、规则 / 章节 / 行号、是否命中、应用方式；若不适用，写明不适用原因。**判断为不适用也必须写明，不能留空。**

近期同领域变更证据的选择规则：

1. 优先读取同能力、同目录、同核心风险的最近变更证据。
2. 默认至少检查最近 30 天内的同领域变更；若同领域超过 3 条，优先列出最相关的 3 条，并说明筛选依据。
3. 如果没有同领域变更，写明检索方式和「未命中」结论。

项目早期 `docs/history/` 可能为空，此时仍必须写明检索方式与「未命中」结论，不得跳过本节。

## 最小验证集要求

最小验证集不是「能跑什么就跑什么」，而是「**这次改动至少必须证明什么没有坏**」。

选择验证项时优先覆盖：

1. 本次直接修改的行为。
2. 历史规则要求的边界条件。
3. 高风险项对应的系统性质（幂等、并发、顺序、一致性、兼容性）。
4. 最近同领域变更曾经出错的点。

同时必须写明**本次不覆盖项**。不写不覆盖项，等同于声称全覆盖，评估器可据此判定证据不足。

## 与评估器协议的关系

入口检查的结果必须进入评估器输入包：

1. 任务分类进入「任务卡」。
2. 高风险项、历史规则、测试基线进入「命中的项目规则」。
3. 最小验证集和实际命令结果进入「主 Agent 已执行验证」。
4. 未覆盖项和人工确认问题进入「已知限制」。
5. 评估器重点进入「评估要求」。

小任务若入口检查没有独立任务卡文件，评估器输入包中的「任务卡路径」可以填写「会话内入口检查」，并粘贴入口检查全文或给出可追溯的对话摘录。**不得只写「见上文」。**

这保证 AI Loop 的入口与出口使用同一套风险上下文。
