# 领域需求整理：从用户故事到子项目边界

关联：issue #10

## 背景

主 Agent 最初被问「多 repo 项目要做业务模型，先从哪个模型开始」，却直接产出了一份 361 行的领域规格（`docs/domain/identity-and-audience.md`）——10 条不变量、2 套状态机、6 个决策、10 个待澄清项，经四轮对抗审查仍未通过，自修复轮次用尽。

真正的问题不是那两条没修完的缺陷，而是**顺序错了**：在没有一句需求原文的情况下，从「业务主线」这个概括短语直接推导出了设计。用户明确表示跟不上，并要求删掉重来、先描述用户故事。

本次变更承接该判断：删除那份推导出来的设计，改为**先整理需求，再谈边界**。

### 方法

- 每条故事标 `已确认` / `待确认` / `明确不做`，**默认 `待确认`**；`已确认` 必须能追到用户原话。
- 需求整理文档中**不出现设计词汇**（字段、状态机、接口、存储、不变量）。
- 每个由讨论得出的结论都记入「已确认事实清单」，供后续追溯。

### 主要结论

拆成三个子项目，依赖单向无环：**运营平台** → **受众服务** → **实验服务**；另有 `gmp-core` 承载抽象模型与跨子项目场景测试。

核心语义：投放项只决策不执行；多步靠事件串（画布不存在）；受众服务只提供人群定义，两个使用方向（枚举 / 判定）；实验服务只认不透明的分流键。

## 卡点密度复审

`AGENTS.md` 要求「核心抽象落地或调整时，必须复审本表，**包括卡点密度**」。本次是核心抽象首次成形并新增两条卡点，触发该条。**结论如下：**

**当前密度（15 条）判定为合理，不收窄。** 依据是该条自己给的判据——「核心抽象未落地阶段几乎每个任务都命中高风险是正确结果；抽象稳定后做增量功能时若仍然全命中，说明清单需要收窄」。目前核心抽象刚定、**代码零行**、五个业务场景全部 `待确认`，尚未进入「做增量功能」阶段，全命中是预期结果。

**但新增的第 14、15 条是全表中最接近可删除的两条**，如实记录：

| 条目 | 能否由通用判定标准推出 | 保留理由 |
|---|---|---|
| 14 决策表的顺序 / 兜底 / 互斥 | **能**——通用标准 1「变更核心领域模型的语义」直接命中 | 本表定位是「免去现场推导」，非「唯一入口」 |
| 15 优先级的配置层级与抢位裁决 | **能**——同上 | 同上 |

**下次复审时应优先重审这两条。** 触发点：抽象稳定、开始做增量功能，且业务回归用例已建立——届时若它们仍每次命中，即为收窄信号。

## 风险与未覆盖项

- **真风险（放行后续跟进）**：**业务回归用例不存在**。核心语义（分桶稳定性、幂等键贯穿三段、演练无副作用）目前只有文字约束。承接方式见 `AGENTS.md`「业务回归用例」与边界文档 B7。
- **真风险（放行后续跟进）**：**演练的「只读问一下」若调用方传错，会静默染色**，改变后续真实执行结果且不报错。接入时需验证手段。
- **真风险（仅观察）**：五个场景由主 Agent 拟定，若与真实业务不符，基于它们的回归用例会验证错的东西。
- **真风险（放行后续跟进）**：**`已确认` 标记的真实性无法在仓库内验证**。判据是「能追到用户原话」，但仓库只保留了极少数直接引语，评估器无法区分「用户裁定」与「主 Agent 推断后被默认」。这是本次自称最关键的诚实性指标，却是唯一完全不可验证的部分。后续动作：为 `已确认` 项补「裁定出处」列，或至少标注确认轮次。
- **落地层级残余（评估器指出）**：**文档内交叉引用一致性本身可脚本化校验**——「划线短语在别处以未划线形式复活」「文档 A 声称 B 的某编号区间未关闭而 B 声称已关闭」两类，正是本次六条阻断里第 1、2 条的形态。建议并入 issue #9 与既有的送审一致性校验一并固化。**能前置固化却停留在人工核对，本身即缺陷。**
- **伪风险**：「需求整理文档没有评估器把关会失控」——不成立。这些文档的内容全部来自用户原话，主 Agent 的推断均标为 `待确认` 且不参与结论。真正需要对抗性审查的是 `AGENTS.md` 的规则变更部分，已纳入本次评估器输入包。
