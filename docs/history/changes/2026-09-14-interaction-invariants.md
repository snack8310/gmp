# docs/domain 的第一份设计文档：不变量与平台介入时点

关联：issue #28

## 背景

`docs/domain/README.md` 定义了三类文档，但目录下**一份设计文档都没有**，四份全是决策记录。README 自己写着「尚无设计文档」。

缺的那一类要承接的东西现在散在两处：`campaign-user-stories.md` 与 `audience-user-stories.md` 的已确认事实清单说清了**什么必须恒真**，但除活动侧事实 7（同活动内两个投放项抢同一位子「建的时候就拦住，不留到运行时」）之外，**没有任何一处说平台在哪一刻介入**。

这个缺口有实际后果，因为这些不变量的共同特征是**违反时不报错**。同一条约束，配置时拦住与运行时才发现，后果是两回事——后者通常等于「已经发出去了」，而触达不可撤回。

缺口是在一次运营平台界面设计中暴露的：画每一屏都要回答「这条在哪一刻拦」，文档答不了，只能逐条回去推。

## 关键实现

- **新增设计文档** `interaction-invariants.md`，覆盖 README「设计文档的写法约定」要求的全部章节。
- **核心是不变量清单**：每条写成可证伪断言，并补上三件既有文档没有的事——违反时会怎样、平台在哪一刻介入、来源是哪条已确认事实。
- **介入时点分三档**：当场拦住（配置保存不了）、提醒（配置合法但后果静默）、机制保证（形状本身使违反不可表达）。条款内写明了否决「一律硬拦」与「一律提醒」的理由，并写明「能做成机制保证的就不该退到前两档」与根 `AGENTS.md`「约束落地优先级」同源。
- **准入判据写死**：一条已确认事实进入清单，须同时满足「描述一种必须恒真的性质」与「违反它时系统不报错」。否决了「把全部事实收进来」——那会让本清单退化成事实清单的副本。
- **来源侧承接表**按「编制纪律」编制，遍历基准是两份文档的已确认事实清单**全部条目**，判定不适用的一并登记，不沉默略过。
- **状态机一节如实分两半**：已定的两个（分流定义的修订、染色）写出流转与非法流转；活动与投放项的状态机**未表态，不补**，转入待澄清问题清单。
- **分流定义不可变这条标注了出处与诚实性边界**——它由人工在 issue #23 所属会话中裁定，本目录此前没有它，仓库内可验证的只有「谁在何时写下了这条引用」。
- **更新 `README.md`**：文档清单增行；「当前四份文档全部归决策记录」一句随之修订；「尚无设计文档」一句改写，并说明本份没有重蹈那条被整份删除的老路——它的每条不变量都追到某条已确认事实。

## 风险与未覆盖项

**真风险（放行后续跟进）**：

1. **承接表的覆盖率核对没有入库**。本次用的是一次性脚本，**按 `mechanization-claims` 规则 1 一律记为未固化**。更要紧的是它暴露了既有门禁的一个真空洞：`consistency_check.py` 的「不得引用已划线推翻的事实」只在**同一份文件内**生效，而本文档引用的全部是**别的文件**里的事实——现有检查对这种跨文档引用零断言。若某条被引用的事实日后在源文档中被划线推翻，本文档不会有任何反应。**承接见 issue #12**，已在该 issue 下登记该项。
2. **「提醒」这一档的实际效力未定**。提醒可以被点掉，点掉之后是否留痕从未讨论，见待澄清 D5。若不留痕，这一档在事后追查时等于不存在。

**仅观察**：

- 不变量 5（决策表的行是否被前面的行完全吃掉）只声明了「必须能判定」，没定怎么判——条件的包含关系需要人群定义的语义比对。见待澄清 D3。

**本次不覆盖项**：

1. **视觉样式体系不在本次范围**，也不在本目录。按 README「可判定的边界」，配色、字体、构件形态、界面布局属禁止侧。它的落点**未定**，见待澄清 D4。本轮产出的界面设计存在于一份设计画布中，不在仓库内。
2. **不新增、不修改任何领域语义**。四份既有文档内容一字未动。
3. 活动与投放项的状态机未补，见待澄清 D1。
4. 「决策表」「演练」的英文名未补，见待澄清 D2。
5. **业务回归用例**：根 `AGENTS.md`「业务回归用例」一节的「当前状态：尚未建立」在本轮**未变动**——本次是文档变更，不触及 `gmp-core`。`experimentation` 那部分已由 PR #27 部分解除，其余仍未建立。
