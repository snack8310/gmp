# 按任务类型收窄自修复轮次上限，并为载体专属失效增加停止条件

关联：issue #20（另含人工裁定并入的载体清单扩充，原 issue #25 已关闭并折叠至本分支）

## 背景

issue #17（把 `docs/domain/business-scenarios.md` 的场景状态标记从 `待确认` 改为 `已确认`，一次纯文档变更）经历了五轮评估器审查。`AGENTS.md`「分级执行规则」给小任务的自修复额度在第三轮用尽，其后靠人工授权才继续。

关键事实是那些阻断问题的分布——**它们全部落在送审载体上**：

| 轮次 | 阻断问题 |
|---|---|
| 第一轮 | 送审载体书写计数，且任务卡自称已遵守该禁令 |
| 第二轮 | 送审提交含范围外构建产物，变更证据「改动范围核对」自评与实测相反 |
| 第三轮 | 上一轮的范围调整只登记进变更证据，任务卡四处未回写 |
| 第四轮 | 载体声称某项「由 issue #18 承接」而该项不在其范围内；任务卡一处落点清单漏项 |

**产物侧（`docs/domain/` 的两份文档）自第一轮起未被攻破**，第五轮 `PASS`。

由此暴露现行规则的两个缺口。其一，轮次上限不分任务类型：文档治理类任务的产物就是文本，评估器可逐字取证，产物侧缺陷通常一轮内收敛，用与代码任务相同的额度不匹配。其二，没有任何条款识别「产物已对、每轮都只在改措辞与记账」这一形态——而 issue #17 实测：**每一轮修复动作本身又制造了新的载体缺陷**（第二轮的修复引入了未登记的范围外文件，第三轮的修复因脚本中止漏改任务卡，第四轮的修复指向了不承接该项的 issue）。这不是纪律问题，继续手工修措辞不会收敛。

## 关键实现

- **新增一档轮次上限**：文档治理类小任务收窄为 1 轮自修复，与通用小任务的 2 轮、大任务的 3 轮并列。
- **新增一条独立于轮次上限的停止条件**：连续两轮的阻断问题全部落在送审载体、产物侧无阻断问题时，必须停止自修复。两者先到先生效。
- **明确该停止条件的正确动作不是续修，而是转固化**：把载体形态问题转成固化 issue，并按当前产物状态交人工裁决。
- **判定归属写死给评估器**：「阻断问题是否全部落在载体」由评估器在裁决中显式标注。理由写在条款里——归类结果决定主 Agent 自己能否继续，它在此有自利倾向。
- **条款内如实标注两条新规则均未固化**，并写明不可机检的真实原因：「自修复轮次」这个量在仓库内不存在，每轮裁决目前只存在于会话与 PR 正文，没有受版本控制的产物记录轮次与每轮的阻断问题归类，机检无遍历基准。前置条件是评估轮次记录入库，承接见 issue #18。
- **把 commit message 纳入送审载体清单**（人工裁定并入）。来源实证：PR #24 的首个 commit `094ae08` 的 message 写有「Three other items are recorded as not added」，而最终 head `f20aec1` 上该去向表已重构，这句计数不再成立；评估器判定当时不构成违反（commit message 不在列举内）但形态同型。纳入后，`review-package-consistency.md` 的其余规则**逐条判定是否对 commit message 成立**，不整体套用——判为不适用的是「取送审 SHA 并核对」「CI 的 headSha 等于送审 SHA」「外部工具写出后回读确认」「人工确认三态」，各自写明理由。失真句原样保留在历史中，不追溯改写。
- **顺带修正一处计数**：`review-package-consistency.md` 原文「核对三者对同一事实」中的「三者」既是计数、又在载体增加后失真，改为「各载体」；同句被核对事实中的「条目数」一并移除（它本身就是禁令所指的计数）。
- **条款内保留了来源实证**，遵循 `docs/history/README.md`「没有原因的规则会在半年后被当成教条删掉」。

## 风险与未覆盖项

**真风险（仅观察）**：当一个文档治理类小任务的产物侧确有两处独立缺陷时，会在修完第一处后被迫交人工，人工介入频次上升。接受——人工裁决的成本低于一次不收敛的自修复循环。

**真风险（放行后续跟进）**：当主 Agent 把载体缺陷归类为产物缺陷时，「连续两轮」的计数被重置，停止条件失效。已通过把判定归属写给评估器来缓解，但**该归属本身仍无机检**。后续动作：随评估轮次记录入库一并固化，见 issue #18。

**本次不覆盖项**：

1. 两条新规则**均未固化**，停在规则文档层。不可机检的真实原因是无遍历基准（轮次这个量在仓库内不存在），不是「语义判断做不了」。前置条件与 issue #18 的任务卡入库同族，由 #18 承接。
2. 既有门禁对 `AGENTS.md` 的内容零断言——把本次改动完整回退后门禁仍会全绿。实际起作用的验证是全仓枚举与人工核对。
3. 本次未修改大任务的轮次上限，也未评估它是否同样需要按类型细分。
4. 「连续两轮」这个阈值本身没有实证支撑——issue #17 的样本只有一个任务。它是拟定值。

**需要后续动作的事项**：

- 人工裁定：文档治理类小任务的上限定为 1 轮是否合适。
- 人工裁定：「连续两轮」的阈值是否合适。定 1 会让第一次载体问题就中断流程，定 3 则与轮次上限本身重叠。
- 人工裁定：`review-package-consistency.md` 中判为「不适用于 commit message」的各条（「取送审 SHA 并核对」「CI 的 headSha 等于送审 SHA」「外部工具写出后回读确认」「人工确认三态」），其判定是否成立。
- 人工裁定：本任务自身按哪个上限执行。它是文档治理类小任务，若新规则立即对自己生效则只有 1 轮额度。**本次按「新规则自合并后生效，本任务仍按旧规则」处理**，需人工确认这一读法。
- issue #18：评估轮次记录入库，使本次两条规则具备可机检的前置条件。
