# 技术栈表述改为已定 Go，并执行该句自己要求的清单复评

关联：issue #13

## 背景

`AGENTS.md` 项目高风险清单表下的最后一条限定说明原文是「技术栈尚未确定，因此本表只覆盖领域语义与执行语义层面的风险，不含具体技术栈相关风险；技术栈确定后需重新评估是否补充」。技术栈已由人工裁定为 Go，该句前半句与仓库实际状态冲突。

不改的代价有两层。**近处**：路线图下一项是 issue #23（`gmp-core` 第一轮），其硬约束 H1 即 Go。一旦 `go.mod` 落库，评估器可同时引到声明侧原文（`AGENTS.md` 该句）与实现侧路径，取证完整，按取证纪律必须判 `FAIL` —— 已关闭的 PR #14 正是死于这一类「产物与送审真源对不上」。**远处**：该句的后半句是一个**动作项**，只改前半句等于让它永久消失且无人记得；规则真源里出现已知不实之处，其余条目会被一并打折读（同型后果见 [`mechanization-claims`](../memory/mechanization-claims.md) 的「原因」段）。

## 关键实现

- **出处不引已作废产物。** issue #13 正文把裁定出处写为 `docs/history/changes/2026-08-30-domain-identity-and-audience.md`。实测该路径在 `git log --all` 下零结果，文件只存在于**已关闭、从未合并**的 PR #14 分支。改引 **issue #23 的硬约束 H1**（由人工撰写），并按 [`business-scenarios.md`](../../domain/business-scenarios.md)「确认记录」的既有写法标注诚实性边界：能追溯到的是一份 issue 与一次会话，会话不在仓库内。该改引经人工确认。
- **执行了该句自己要求的复评，而不是只改陈述。** 去向表直接写进 `AGENTS.md`（不是只写进本变更证据），并**显式给出遍历基准与判据** ——「`system-boundaries.md` 中成因为技术栈或工程形态、且描述一种不报错的失效的陈述」。给判据是为了让穷举声明可被第三方独立复核：没有判据，读者无法判断表内是否有遗漏。按 [`source-enumeration-fidelity`](../memory/source-enumeration-fidelity.md)，穷举式结论必须以来源侧为遍历基准并落成产物形态。
- **逐项去向不做复合词压缩。** 「内存实现测不出回流延迟、并发、下游是否真幂等、规模」这一句在来源侧是各自独立的分项，去向各不相同（前两者合并进第 17 条，「下游是否真幂等」落第 11 条，「规模」属性能不在本表），故在表内拆成各自独立的行。同理，按判据判定**不适用**的相邻陈述（便利接口、对齐的类型责任、B6 的变更单元、被否决方案的「接口定义会有四份」）也逐条登记，而不是沉默略过。
- **准入条件未被放宽。** issue #13 的未讨论项 3 问的是「技术栈风险是否满足本表『必须靠领域知识才能识别』的准入条件」。本次**回答它，而不是改写它**：技术栈风险分两类 —— GC 停顿、并发原语误用、依赖库选型这类通用工程问题不进表；第 16、17 条进表，是因为识别其后果必须依赖本项目的领域设计（B9 的「未来整块搬走」、回流延迟与并发是本业务的真实失效模式）。表下「必须靠领域知识才能识别」一句因此保持原样。该结论经人工确认。
- **补入第 16、17 条，其余分项写明不补及理由。** 补入的是「变更 `gmp-core` 内部依赖分层 / `experimentation` 零依赖约束」与「变更时间来源与事件投递的提供方式」。第 16、17 条的共同论证：**自动化检查能挡住穿透，挡不住有人有意放宽约束本身**，而后者正是「约束落地优先级」第 1、2 层结构上覆盖不到、只能靠人工卡点的部分。
- **每条判为「应下沉」或「由他处承接」的行，同行给出承接 issue 编号**，按 [`mechanization-claims`](../memory/mechanization-claims.md) 规则 4。
- **不改动任何既有条目的语义**，第 1 至第 15 条一字未动。
- **不落地任何检查。** 本次不新增脚本，`AGENTS.md` 的格式校验仍由 issue #9 承接。文中不出现「已固化」字样，按 `mechanization-claims` 规则 1。

## 风险与未覆盖项

- **真风险（仅观察）**：当……新补的第 16、17 条在 `gmp-core` 落地后每个 PR 都命中时……卡点会退化成橡皮图章。当前判定为不成立，理由是两条的触发面是**变更约束本身**（改分层规则、改时间与投递的提供方式），而不是在既有分层内加代码 —— 例如 issue #23 第一轮会命中（「变更」涵盖「首次引入」），但此后在 `experimentation` 内补一个测试不会命中。该判定是论证，不是证据；样本要等 `gmp-core` 有若干个 PR 之后才有。
- **真风险（放行后续跟进）**：第 16 条所卡的对象中，「穿透」那一半的自动化检查尚不存在，由 issue #23 的 H4 承接；「有意放宽约束本身」那一半没有任何检查能承接，只能靠本条的人工卡点。
- **真风险（放行后续跟进）**：`AGENTS.md` 作为规则真源，**完全不在任何自动化检查的遍历基准内**。这比本次任何一条内容缺陷的影响面都大。由 issue #9 承接。
- **本次不覆盖项**：
  1. `docs/domain/system-boundaries.md` 的「技术栈倾向 Go，但方案与语言无关」在裁定后成为陈旧措辞，与改后的 `AGENTS.md` 直接冲突。按 issue #13 非目标不改，理由改为「范围漂移应拆成新 issue」—— **issue #13 原本给出的理由（「领域文档按约定不得出现技术栈词汇」）本身已被推翻**，见 [`2026-08-30-domain-user-stories.md`](2026-08-30-domain-user-stories.md) 的撤回行与 `docs/domain/README.md`「可判定的边界」（明确允许写「技术选型的倾向与其后果」）。结论不变，理由必须换。**承接 issue 尚未创建。**
