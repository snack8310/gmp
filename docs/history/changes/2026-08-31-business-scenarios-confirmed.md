# 五个业务场景转为已确认，并补裁定出处

关联：issue #17

## 背景

`docs/domain/business-scenarios.md` 的场景此前全部标 `待确认`，定位段写着「全部由主 Agent 拟定，未经业务确认」。业务侧已在会话中确认这些场景各自成立，该陈述不再成立。

不改的代价是：首先，这份文档是根 `AGENTS.md`「业务回归用例」指定的用例基准，落点为 `gmp-core/scenarios/`；基准标着「未经业务确认」，承接 `gmp-core` 的任务无从判断该不该照它建用例，而那正是路线图的下一项。其次，`docs/domain/` 定位为跨 repo 引用的规格真源，真源里的已知不实之处会让其余条目一并被打折读——同型后果记录在 [`mechanization-claims`](../memory/mechanization-claims.md) 的「原因」段。

同时承接 [`2026-08-30-domain-user-stories.md`](2026-08-30-domain-user-stories.md) 风险段留下的后续动作：「为 `已确认` 项补『裁定出处』列，或至少标注确认轮次」。该轮把「`已确认` 标记的真实性无法在仓库内验证」记为自称最关键却完全不可验证的部分；本次确认有明确出处，是补上它成本最低的时机。

## 关键实现

- **只改确认状态与其出处，不改任何领域语义。** 场景正文、「踩到模型的哪里」表、覆盖矩阵、「这五个没覆盖到的」一节均未改动。
- **新增「确认记录」小节**，写明裁定出处、裁定回应的是什么、用户原话、确认范围、拟定方，并显式写出该记录的诚实性边界：它能追溯到的是一次会话，而会话不在仓库内，仓库内可验证的只有「谁在何时写下了这条出处」。
- **确认范围如实收窄**：用户确认的是各场景**成立**，**未**确认「这些就是全部场景」。故「这五个没覆盖到的」一节列出的补充项保持原状。该读法需人工在最终审核时裁定，见下方未覆盖项。
- **同步 `README.md`**：文档清单的状态列，以及「三类文档」一节的分类判据句。后者不含「待确认」字样，属间接陈述——按 [`source-enumeration-fidelity`](../memory/source-enumeration-fidelity.md) 以来源侧为遍历基准（全仓枚举「声明场景确认状态的位置」）才发现，逐字 grep 关键词抓不到。
- **不回改 [`2026-08-30-domain-user-stories.md`](2026-08-30-domain-user-stories.md)**：其「场景全部 `待确认`，未经业务侧确认」在当时为真。变更证据是时点事实记录，本份与它并存。
- **本次未立任何新规则。** 补出处是产物动作，不是约定，详见下方未覆盖项。
- **范围调整（如实登记，非静默）**：
  - **新增 `.gitignore`**，超出任务卡原范围。理由：本轮修复动作自身把本地跑门禁产生的 `.pyc` 带进了送审 commit，`.gitignore` 是该缺陷的最小防复发手段，属对本 PR 引入缺陷的补救而非新需求。挡不住的部分（已入库文件、`git add -f`）由 issue #18 承接。
  - **出处的粒度相对 issue #17 收窄**：issue 写的是「为每个场景补确认出处」，实现是一份共享的「确认记录」。理由：裁定是一次性作出的，逐场景重复同一份出处会让记录看起来像五次独立裁定，反而失真。

## 关键文件

- `docs/domain/business-scenarios.md`：定位段的确认状态陈述改写；新增「确认记录」小节；①～⑤ 各自标题的状态标记由 `待确认` 改为 `已确认`。
- `docs/domain/README.md`：文档清单中该文档的状态列；「三类文档」一节引用旧状态的分类判据句。
- `.gitignore`：新增。忽略本地执行 `test/docs/consistency_check.py` 产生的字节码。

## 风险与未覆盖项

**真风险（仅观察）**：当五个场景与真实业务不符时，基于它们建的回归用例会验证错的东西，且会全绿。本次不处理——该风险由业务确认本身承担，不由本次改动引入。原判断见 [`2026-08-30-domain-user-stories.md`](2026-08-30-domain-user-stories.md) 的同名条目，本次确认使其从「场景未经确认」变为「场景已确认但与真实业务的相符程度仓库内不可验证」。

**真风险（放行后续跟进）**：当后续有人给目录下别处的 `已确认` 项补出处时，会发现只有这一份有出处、格式无先例可循。后续动作：若决定全量补，须另开 issue，并按 [`mechanization-claims`](../memory/mechanization-claims.md) 规则 6 对存量同型产物（活动侧事实清单、受众侧事实清单与故事表、边界侧 B 系列结论）做全量复核。**本次未开该 issue。**

**本次不覆盖项**：

1. `已确认` 标记的真实性仍无法由仓库内产物独立验证。补出处让它可追溯到「哪次裁定、回应的是什么」，但会话本身不在仓库内，这一层未闭合。
2. 目录下其他文档的 `已确认` 项未补出处（issue #17 非目标）。
3. 「`已确认` 项必须给出裁定出处」**未立为规则，亦未固化**。其机检形态与 issue #12 承接的 `docs/domain/` 结构检查同型，宜合并考虑；本次不声称任何新固化。
4. 根 `AGENTS.md`「业务回归用例」的「当前状态：尚未建立」仍为真，本次未改动该节——确认基准不等于建立用例。
5. **既有门禁对本次改动零覆盖**（见验证结果表的「回退变异」一行）。`docs/` 类改动目前没有任何检查能断言其内容正确，只能断言其未破坏既有结构。
6. **`.gitignore` 只挡未入库的产物**，挡不住已跟踪文件与 `git add -f`；第 2 层的自动化检查**未固化**，由 issue #18 承接。
7. **前一轮变更证据里一条仍在生效的判断，其前提已被本次改动证伪，但按不回改规则未动它**：[`2026-08-30-domain-user-stories.md`](2026-08-30-domain-user-stories.md) 的「卡点密度复审」结论「当前密度判定为合理，不收窄」，论证前提之一是「场景全部 `待确认`，尚未进入『做增量功能』阶段」。该前提现已不成立。**这不影响其结论**（代码仍为零行，仍未进入做增量功能阶段），但下次复审卡点密度时必须重新推导，不得直接沿用该行。`consistency_check.py` 的划线事实检查只扫 `docs/domain/`，抓不到 `changes/` 内的此类失效。
8. **任务卡不在版本控制内**（位于会话临时目录），CI 触及不到，因此它被漏改时没有任何机制会发现，其历史也无法在仓库内取证。本轮实证：`.gitignore` 的范围调整先只登记进了本变更证据、任务卡未回写，由评估器判为阻断。「任务卡入库 + 范围声明与实测 diff 的机检」**未固化**，由 issue #18 承接——该项已写入 #18 的范围内，非仅指向。

**需要后续动作的事项**：

- 人工在最终审核时裁定：用户确认的是各场景**成立**（本次采用的读法），还是「这些就是全部场景」？若为后者，「这五个没覆盖到的」一节需另行处理。
- 人工裁定是否为「所有 `已确认` 项补裁定出处」另开 issue。
- issue #18：用门禁挡住构建产物入库、把任务卡纳入版本控制并机检其范围声明与实测 diff，并沉淀评估器判定应新增的抽象记忆。评估器追加了该记忆的主题——「任务卡是送审载体，评估器驱动的修复必须回写任务卡」「任何『本次已遵守规则 X』的自称必须同时给出可核对的实测依据」——并判定其中的范围一致性属第 2 层、应固化为检查而非停在记忆层。另建议给 issue #12 加严一条：载体中出现的 `#N` 承接声明，其被引 issue 须处于 open 且正文含该承接项——#12 现规划的「同行须给出 issue 编号」只校验编号存在，不校验它是否真的承接。**该建议本轮未落地，仅记录。**
