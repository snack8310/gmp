# gmp-core 第五轮：执行侧与批量投放，幂等键贯穿三段

关联：issue #38

## 背景

用户要求「做事件串和执行侧」。**主 Agent 提出拆成两轮并说明理由，用户同意**：三样东西——执行侧、事件与回流、「我们找人」方向——一轮做完是 PR #14 整份作废的规模，而且顺序不可颠倒，事件是从执行产生的。本轮只做执行侧与批量投放方向。

本轮要解决的是事实 48 那条约束，它此前是仓库里最贵的一个洞：

> **幂等键必须贯穿决策 → 执行 → 回执三段，断一节执行状态就永远悬空。**

三段里只有第一段存在。而它的三种失效**全部不报错**：键在重试之间变了，下游把同一次发放当成新的一次；回执带着对不上的键回来被静默丢弃，那次执行永远挂着；下游声称幂等而实际不是，重试两次、用户收到两条。

## 关键实现

**幂等键由输入推导，不是每次生成**

键由「活动 + 投放项 + 分流键 + 本次进入的标识」确定性组合而成，在任何一次投递尝试之前算出一次。**重试复用同一个键因此是结构性的**——不是「记得复用」，而是重试根本没有另一个值可用。

「本次进入的标识」**必填，由触发方给出**：只有触发方知道这是一次新的进入还是一次重试。受众侧事实 4 明写同一个人每满足一次条件就进一次，每次都当作新的处理；在这里猜，要么重复发送要么漏发，两者都静默。

**回执对不上必须报错**

回执带着同一个键回来找它的执行。**键找不到对应执行时拒绝，不静默丢弃**——丢弃正是「执行状态永远悬空」的成因：投递已经出去了，没有任何东西会再说它怎么样了，而且没报过错。

**投递侧是端口，且「幂等」要被证明而不是声明**

投递侧是接口，本轮只给内存实现。领域文档明写「下游幂等是声明不是保证」，并要求接入时有验证手段——`deliverytest` 就是那个手段：一套契约用例，新接一个下游必须跑通「同键调两次只产生一次效果」。另配了一条用例证明该判据**有区分力**：一个忽略键的实现在同一个键上产出两次效果。

**动作区分方向**

推那类（我们调对方）可重试；**拉那类不可**——人已经走了，重试一次没人在等的东西不是更小的错误。方向**无零值**：忘了填的动作会被当成可重试。

**执行记录带两个字段**

投放项与落点（份号）。少任一个就有一边算不出来。落点经 `audience` 新增的值类型传递，`campaign` 不因此反手去够 `experimentation`——分层不变。

**ITT**：重试耗尽的执行**仍带着它的落点入账**。剔掉发失败的人等于偷偷筛了一遍人群，而失败的人往往有共性。

**演练**：走同一条路径，不投递、不落记录，返回的是另一个类型（计划，不是执行）——避免用同一个类型留一个空状态让人误读。

## 风险与未覆盖项

**真风险（仅观察）**：

1. **给一次从未被接收的投递记「已送达」回执，模型当前不拒绝**。这是写 demo 时撞见的：随手取的那条恰好是重试耗尽失败的，却给它记了送达回执，输出读起来是通的。demo 已改为取一条真被接收的，**但模型本身没有加这条规则**——规格对此未表态，加了就是臆造。**登记为待澄清**。
2. **并发未被证明**。批量按顺序逐个处理；内存实现跑不出竞态。执行日志的写入在接口层面做了「同键只记一次」，但那是契约不是实测。

**本次不覆盖项**：

- **事件与回流、触发器**——下一轮。场景 ① ⑤ 随之收口。
- 异步回执的**投递时机与顺序**（乱序、延迟到达）——本轮回执由调用方喂入，时序归调度器，与核心无时钟的裁定一致。
- 真实渠道、真实存储、HTTP、部署形态。
- 频次、退订、免打扰；指标、观测期、显著性。
- 场景 ④ 的执行部分——放量闸门与批量投放本轮均已存在，但两者串起来的场景用例未写。
- **业务回归用例**：`AGENTS.md` 的逐场景清单已同步，场景 ② 从「分组与对照已建立」推进到「分组、对照与触达已建立」；指标仍未建立。

**需要后续动作的事项**：

- 人工裁定：本轮四项自行裁定（幂等键的构成、执行状态取值、回执收哪些信息、批量按顺序）是否认可。
- 人工裁定：从未被接收的投递收到「已送达」回执，该拒绝还是该接受。
- 下一轮：事件与回流，场景 ① ⑤。
