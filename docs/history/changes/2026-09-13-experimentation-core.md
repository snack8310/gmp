# gmp-core 第一轮：experimentation 层、依赖方向门禁与场景断言

关联：issue #23

## 背景

仓库此前零业务代码。`docs/domain/` 的领域语义已经收口，但没有一条能被机器证伪——[`2026-08-31-business-scenarios-confirmed.md`](2026-08-31-business-scenarios-confirmed.md) 的「回退变异」是实测证据：把整轮文档改动完整回退后既有门禁仍然全绿。

本轮的目的不是「写代码」，是把「分桶必须稳定」「放量必须单调」「演练不得染色」这类断言从 `AGENTS.md`「约束落地优先级」的第 3 层（散文）降到第 1、2 层（类型与必跑的测试）。

第一轮切 `experimentation`：它是依赖分层的最底层、零依赖，接口形状已被规格定死，业务场景 ② 的分组与 ④ 的放量单调性两条核心断言都落在它身上。

## 关键实现

**领域模型（`gmp-core/experimentation/`）**

- **分流键不透明**。服务只收一个 `AssignmentKey`，不解释它代表人、设备还是订单。这是「可开放给第三方」的前提，所以没有任何方法对它的内容有意见。
- **接口形状只有 `(分流键, 定义) → 份号`**。**未提供**「按人群分流」的便利接口——规格把它列为「要盯住的」，加了会把本层绑死在本项目里。
- **份号从 1 起**，与领域文档「分流 E 第 2 份」逐字对齐；并落成**独立类型而非整数别名**，使其无法被直接当作切片下标使用。一、二之差跨文档与代码时不报错，这是本仓库反复吃亏的形态，故下沉到类型层。一、零两套下标的换算只在一个私有方法内发生。
- **定义不可变**。字段全部在构造期设定，没有任何修改入口。**必要推论：分流标识跨定义修订稳定，染色按标识归档而非按定义归档**——否则「定义变了、已染色的人不动」这条规格当场失效。该推论的出处是三条规格合起来的唯一自洽读法（「一次分桶是唯一需要成为业务对象的」给出标识；染色表的「定义变了 → 已染色的人不动」要求跨修订；「定义变更等同于破坏性变更」说明修订会发生），已交评估器攻击。
- **必填项在构造期失败，不取默认值**：算法版本、盐、分流标识、切法缺任一即构造失败。Go 的零值会把算法版本静默填成空串，那样的分流看起来完整却无法回放；盐则是因为规格让跨租户隔离依赖「盐里带租户」却从未定过生成口径，本层因此不生成盐。
- **切法的总量由调用方明写，各份权重之和必须等于总量**。不做静默归一化——归一化等于发明一条规格没说过的规则，且调用方永远不会知道自己的配置不完整。「比例和不为整体」因此是一条看得见的拒绝路径。比例不整除不产生舍入。
- **对齐取目标的盐与切法**，调用方配的是「跟哪次分流对齐」而非盐。切法不兼容当场拒绝；自行指定盐当场拒绝。**对齐不可传递**（拒绝对齐到一个本身带对齐的定义）——规格只定义了「对齐到一个已有分流」，链式既无定义也会允许成环，拒绝是唯一不会静默出错的读法，作为保守选择登记。
- **染色可选、首写者胜**。`ColoringStore` 的 `RecordFirst` 在接口层面定义为原子操作并返回当前生效的记录，「同键并发首次分配只能产生一个份号」因此写进了契约，由未来的真实实现承接。染色记录带当时的算法版本，因为回放必须用当时实际跑的算法。
- **「只读问一下」**（`PeekAssign`）算份号但不写记录，供演练使用；已染色的键它报告记录值而非重算。

**依赖方向门禁（`gmp-core/internal/arch/`）**

- 解析 `experimentation` 下每个 Go 文件的 import，命中上层包路径即失败。
- **检查本体放在被检查包之外**：放在包内的话，包被删除时检查跟着消失，删包会表现为一次干净的通过。
- **配了数量下限断言**：被检查目录不存在、或不含任何 Go 文件时判失败，而不是「零个文件、全部通过」。

**契约测试骨架（`gmp-core/experimentation/coloringtest/`）**

Go 接口隐式实现，「这个实现符合契约」编译期查不全。同一组断言写成可复用的套件，本轮跑在内存实现上，未来的真实存储实现调用同一套件而不是自己另写。**只有现在就用内存实现做第一版，这套东西才是免费的。**

**门禁接入（`.github/workflows/gates.yml`）**

原 `shell.yml` 更名为 `gates.yml`（workflow 名本就叫 `gates`，现已不止覆盖 shell），新增 Go 工具链、`gofmt`、`go build`、`go vet`、`go test`。Go 版本取自 `gmp-core/go.mod`，不在 workflow 内另行钉版本，避免门禁用的工具链与模块声明漂移。

## 风险与未覆盖项

**真风险（阻断，已解决）**：依赖方向若只写文档，单仓库下穿透它只需多写一行 import 且不报错。已固化为检查并实测两种变异均被捕获。

**真风险（放行后续跟进）**：

1. **并发未被证明**。内存实现单线程跑不出竞态，本轮的并发用例断言的是接口契约而非真实竞态。**本轮不声称并发已验证**，由未来的真实存储实现承接。
2. **`docs/domain/` 与本实现之间没有漂移检测**。具体路径：有人在 `experimentation` 加一个规格禁止的「按人群分流」便利接口，两边都绿。未固化，须开后续 issue。
3. **回退变异未捕获**。把本轮改动完整回退后门禁仍全绿——因为测试本身也被回退掉了。真正起作用的是上表逐条的定向变异，不是「门禁是绿的」这个事实。

**仅观察**：

- `CONTRIBUTING.md` 写着「远端同样设有保护规则，`--no-verify` 绕过本地钩子后推送依然会被拒绝」，而 `gh api repos/.../branches/main/protection` 实测返回 `Branch not protected`。**该句当前不成立**，禁止直推 `main` 实际上只有本地钩子这一层。本轮不改，登记在此。

**本次不覆盖项**：

- `audience` / `campaign` / `scenarios` 三层；业务场景 ①③⑤ 的端到端表达。
- 真实存储、真实渠道、真实数据源、部署形态。
- 指标口径清单（边界文档 B6）。
- **时间**。本层无时间概念——定时触发交给外部调度器，到点投事件，模型只对事件与状态作出反应。人工裁定，理由与逐场景核对见任务卡。**该裁定使 `system-boundaries.md`「时间的来源……必须是可被替换的依赖」的前半截不再成立**，`AGENTS.md` 高风险清单第 17 条据此而立；本轮非目标含「不修改 `docs/domain/`」，故仅登记，未改文档也未开 issue。
- 回流延迟、规模与性能。
- **业务回归用例**：`AGENTS.md`「业务回归用例」一节的「当前状态：尚未建立」在本轮**部分解除**——业务场景 ② 的分组部分与 ④ 的放量单调性部分已落成会失败的测试，跟着 `experimentation` 走。其余场景与跨层部分仍未建立。
- 验收基准本身可能不完整：业务确认的是五个场景各自成立，**未确认「这就是全部场景」**，`business-scenarios.md` 自列的待补项仍待补。

**需要后续动作的事项**：

- 开 issue 承接 `docs/domain/` 与实现的漂移检测。
- 人工裁定：`CONTRIBUTING.md` 那句关于远端保护规则的表述，是补上保护规则，还是改掉这句话。
