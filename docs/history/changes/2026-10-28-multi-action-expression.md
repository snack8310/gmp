# 决策记录：多动作三种表达（并行 / 串行 / 按回执分支）

关联：Snack/用户会话 2026-10-28（用户确认显式写入产品能力清单）；承接既有事实 11、17、18、52、64、65

## 背景

运营侧需要「权益 + WhatsApp + 短信」等组合触达，以及按回执走不同后续（如 RCS 成功→邮件、失败→短信）。文档虽已有「条件分流 = 人群组 + 投放项」与事实 52（同批人多种触达 = 多个投放项共用人群组），但未把**并行 / 串行 / 按回执分支**写成显式产品能力行，易被误读成「需要编排器」或「一个投放项挂多个动作」。

## 关键实现（仅文档）

- 显式列出三种表达，**均保持一个投放项一个动作**：
  - **并行**：同一人群组挂多个投放项（事实 52）
  - **串行**：后一步人群建在前一步执行回流来源上（事实 17、18）
  - **按回执分支**：成功 / 失败（及动作契约其他结果）回流后各建人群组 + 投放项（事实 18、65）
- **不引入**编排器 / 「串」对象；成功 / 失败语义由动作契约定义（事实 65）
- **不推翻**事实 11、52、64
- 活动侧新增事实 **67**；确认记录一则
- `interaction-invariants` 承接表登记事实 67 为不适用（不另立不变量）；概念与关系补一句交叉引用
- `system-boundaries` 动作归属行补交叉引用事实 67
- 设计总览 HTML 增「多动作三种表达」小节
- **不改** `gmp-core`、不 commit / push

## 风险与未覆盖项

- 真风险：界面若仍暗示「一个投放项可配动作列表」，会与事实 11/52/64/67 冲突——产品文案须对齐本记录。
- 本次不覆盖项：各动作契约字段级成功/失败枚举仍未写（事实 65 只定「由动作定义」）；回流延迟拦住仍靠不变量 6。
- 需要后续动作的事项：若要在运营 UI 上提供「并行 / 串行 / 分支」模板，另开产品设计任务（底层仍映射为多个投放项）。
