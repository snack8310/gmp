# 从来源文本编制清单类文档的枚举保真

## 规则

- 从来源文本（需求原文、业务主线、接口清单）编制清单类文档时，必须以**来源侧**为遍历基准：拆出每个顿号分项、每个并列连词（与 / 或 / 和 / 及）两侧的项，逐项标记落到产物的哪一条。**禁止以产物为基准反向确认「看起来都覆盖了」。**
- 未被任何条目逐字承接的分项，必须显式写出「合并进第 N 条」或「判定不适用，理由 X」，不得沉默略过。
- 覆盖判定必须同时排除两种失败：
  - **丢词**：分项在产物中完全消失。
  - **复合词压缩**：多个分项被合并成一个词，字面残留但语义合并（如「渠道接入协议、连接器抽象」→「渠道连接器协议」）。仅做字面 grep 只能抓前者。
- **探针**：条目的「后果 / 说明」列若只提到该条目枚举项的一部分，即是该条目枚举有缺口的可见痕迹，必须回查来源。
- 本规则同样适用于**描述产物的送审摘要**（PR 正文、变更证据、任务卡）。摘要中**尽量不写「共 N 段 / N 条」这类计数**；确需给出时，N 必须以产物实测为准，不得凭记忆填写。能枚举就枚举，枚举不会随产物增删而失真。

## 原因

issue #7 中，同一类遗漏在同一份文档上连续出现五次：

| 来源 | 被吞掉的部分 | 掩盖它的条目 |
|---|---|---|
| 业务主线 f「各自的抽象模型与统一执行契约」 | 各自的抽象模型 | 只取了后半句的条目 |
| 业务主线 a「名单来源、圈选、快照与生命周期」 | 名单来源 | 其余三项逐字保留的条目 |
| 业务主线 e「分流单元、分桶算法、实验定义与指标口径」 | 实验定义 | 「分流单元」足够邻近 |
| 业务主线 c「渠道接入协议、连接器抽象、发送结果回执」 | 两项被压成一个复合词 | 「连接器」字面在场 |
| 产物自身的表下限定说明 | 第六段未被计入 | 三份送审载体都写了「五段」 |

每次都被一条「看起来相关」的东西在语义上掩盖，三轮评估器审查才逐个挖出。

第四次证明「逐字对照」不足以抓复合词压缩 —— 字面上什么都没少。第五次证明该失效模式会**从产物迁移到描述产物的摘要上**，因此规则必须覆盖摘要，且计数本身就是错误来源。

前三轮实施方均自称「已逐字对照，通过」。**纯态度型规则无效**，必须落成产物形态（分项承接表），才能被审查。
