# 「已固化」是一条可核对的事实陈述，不是修复姿态

> 本文件由 issue #10 复审评估器判定应新增，规则草案出自评估器输出，主 Agent 仅作转录。

## 规则

- 任何文档写下「已固化为自动化检查」或「已由类型约束」时，被引用的检查必须是**仓库内受版本控制、且由 CI 或钩子实际运行**的产物。一次性脚本、scratchpad 工具、评估会话内的取证脚本**一律记为「未固化」**。
- 固化声明必须逐条给出**固化归属表**（规则 → 已固化 / 未固化 + 固化位置 `文件:断言名`）。**禁止整体式的「以下约定均已固化」。** 未固化项必须与已固化项并列出现在同一张表内，不得移到别处或省略。
- 写「仍留在文档层的只有 X」这类**穷举式**表述前，必须逐条比对声明表与检查实现。比对不出来的，改为非穷举表述。
- 评估器要求把约束下沉一层时，若本轮不下沉，正确回应是「**未下沉 + 后续 issue 编号**」，**不是在文档里写下它已下沉**。
- 引入结构性检查脚本时，必须为脚本本身补一组**空断言变异**：把被检查小节改名、把被检查条目整行删除，确认脚本**报错**而不是「断言数变少但全部通过」。**发现驱动的循环必须配一条数量下限断言**，否则被检查对象消失时循环体一次都不执行，脚本仍打印通过。
- 送审载体中**禁止书写由工具产生的计数**（断言数、用例数、条目数），一律改为枚举类别。计数无信息价值，且必然随产物变动而失真。见 [[source-enumeration-fidelity]]。

## 落地层级

- 「声明表的每一行都能在仓库内找到对应断言」可脚本化（解析固化归属表 → 校验引用的文件与断言名存在），应随检查脚本入库任务一并固化。
- 「不写工具计数」可由送审载体的正则检查固化，宜并入 [[review-package-consistency]] 的可脚本化校验范围。
- 「评估器要求下沉时的正确回应」「穷举表述的合法性」属语义判断，只能留在文档层。

**本文件描述的规则目前全部未固化。** 按本文件自身的规则 2，此处如实标注；可机检的部分由 #12 承接。

## 原因

issue #10 的复审中，首轮评估器指出「状态机写法本可前置固化却写成了散文」。实施方的回应是在 `docs/domain/README.md` 里写下「以下约定**已固化为自动化检查**」——而承载这些断言的脚本位于会话临时目录，合并后即不存在，仓库 CI 中没有任何针对该目录的检查。同一次提交的变更证据在另一处又如实写着「检查脚本未入库，对后续提交无回归防护」。

**问题被挪了位置，没有闭合，而挪动的方向恰好是让欠账不可见。** 这比诚实地停在文档层更糟：`docs/domain/` 的定位是跨 repo 引用的规格真源，下游实现方读到「已固化」会认为写法违规会被门禁挡下，实际不会。

同一轮复审中，评估器对该脚本自身做变异，发现四条空断言路径。其中最典型的一条：状态机小节的发现正则是 `^### .*状态机$`，把小节改名为「……的状态与流转」后，该状态机的全部结构断言**静默消失**，脚本照常打印「全部通过」。这与 `shell-ci-gate` 那次发现的空断言同构——**测试自身也会静默失效**，而发现驱动的循环是这类失效最常见的入口。

`shell-script-portability` 早已写过「未固化的部分仍是文档约定，不得声称为已固化」，但它被读成了 shell 专属规则，本轮任务卡因此判其「不适用」。本文件的存在就是为了让这条规则脱离 shell 语境。
