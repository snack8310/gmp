# 「已固化」是一条可核对的事实陈述，不是修复姿态

## 规则

1. 任何文档写下「已固化为自动化检查」或「已由类型约束」时，被引用的检查必须是**仓库内受版本控制、且由 CI 或钩子实际运行**的产物。一次性脚本、临时目录里的工具、评估会话内的取证脚本**一律记为「未固化」**。
2. 固化声明必须逐条给出**固化归属表**。**禁止整体式的「以下约定均已固化」。** 未固化项必须与已固化项并列出现在同一张表内，不得移到别处或省略。表的形态是硬要求：
   - 左列**必须以规则标识为键**（「规则 N」）。判据写死：**把表的键按出现顺序去重后，所得序列必须与规则清单的编号序列完全相等**——不是行数相等。
   - 一条规则拆成多行时，各行**共用同一键**，且必须相邻。
   - **「行数恰好等于规则数」不构成完整性证据**——一条规则占两行、另一条零行，行数照样对得上。必须逐键比对。
   - 被检查文档若没有编号规则清单，**必须先编号**。无编号清单时该比对没有遍历基准，「不编号」会成为规避该形态要求的通道。
   - 判为「可机检 = 是」的行，必须给出固化位置或承接 issue 编号；判为「否」的行，必须写明**为什么不可机检**。只填「否 / 文档层」而不给理由，等于把欠账合法地留在文档层。
3. 写「仍留在文档层的只有 X」这类**穷举式**表述前，必须逐条比对声明侧与检查实现。比对不出来的，改为非穷举表述。
4. 评估器要求把约束下沉一层时，若本轮不下沉，正确回应是「**未下沉 + 后续 issue 编号**」，**不是在文档里写下它已下沉**。
5. 一条检查所依据的规则若被推翻，该检查的历史「通过」结论**必须显式撤回**，不能因为它当时确实跑绿过就留着。规则不成立时，绿灯本身就是假证据。
6. 新立一条**结构性**规则（约束产物形态而非内容的规则）时，必须对仓库内**已存在的同型产物**做一次全量复核，把不合规者显式登记为未覆盖项或后续 issue。**不得只对本次新写的产物负责。**
7. 引入结构性检查脚本时，必须为脚本本身补一组**空断言变异**：把被检查小节改名、把被检查条目整行删除，确认脚本**报错**而不是「断言数变少但全部通过」。**发现驱动的循环必须配一条数量下限断言**——否则被检查对象改名或消失时循环体一次都不执行，脚本照常打印通过。

## 落地层级

**本文件描述的规则目前全部未固化**，按规则 2 如实标注。左列为规则标识，与上方规则清单同序同基数：

| 规则 | 可机检？ | 机检形态 | 固化状态 |
|---|---|---|---|
| 规则 1 | 是 | 声明表引用的检查须在仓库内存在且被 CI 或钩子实际调用 | **未固化**，#12 |
| 规则 2 | 是 | ①正文出现整体式固化声明（「以下约定均已固化」一类）即失败；②归属表的键集合与规则清单**同序同基数**——**表缺失、标题被改写或键集合为空一律判失败**，不得空转通过 | **未固化**，#12 |
| 规则 3 | 否 | 「穷举是否成立」需要语义比对，无结构特征 | 文档层 |
| 规则 4 | 是 | 声称「未固化 / 未下沉 / 由后续 issue 承接」的行须同行给出 `#编号` | **未固化**，#12 |
| 规则 4 | 否 | 该回应是否**诚实**（是否真的没下沉），输入是仓库外的评估对话 | 文档层 |
| 规则 5 | 否 | 判断「某条规则是否已被推翻」需要理解语义 | 文档层 |
| 规则 6 | 是 | 新立结构性规则的 PR，须对同型存量产物全量跑一遍该规则；不合规者须在变更证据中登记 | **未固化**，#12 |
| 规则 7 | 是 | 检查脚本须配空断言变异用例；发现驱动的循环须有数量下限断言 | **未固化**，#12 |

规则 4 拆成两行且共用同一键：可机检的是「有没有写编号」，不可机检的是「这句话是不是真的」。故表的行数不等于规则数——按上述判据，比对的是**去重后的键序列**。

规则 2 第 ② 项的下限断言不是可选项：它的遍历基准是归属表的每一行，而表本身就是被检查对象——没有下限断言时，删掉表或改掉标题即可让检查零行通过，这正是规则 7 禁止的形态。**本文件初稿就踩了这个坑**：当时的表漏掉了规则 2 自己，而行数恰好等于规则数，掩盖了漏项。

## 原因

这类失效的特征是：**它看起来是修复，实际是把欠账挪到看不见的地方。** 两种形态都在本仓库出现过。

**形态一：规则塌了，绿灯还留着。** PR #11 的变更证据（[`2026-08-30-domain-user-stories.md`](../changes/2026-08-30-domain-user-stories.md)「验证结果」表）中，「设计词漂移检查」一行被划掉并如实撤回：该检查依据的是「此类文档不得出现任何技术词汇」，而评估器指出这条规则对 `docs/domain/` 下一份文档也不成立。检查当时确实跑绿过——但**规则不成立时，绿灯是假证据**。

**形态二：把「应该固化」写成「已经固化」。** issue #10 的另一条路径（PR #14，已关闭）中，评估器指出某条写法约束本可前置固化却写成了散文。实施方的回应是在文档里写下「以下约定**已固化为自动化检查**」——而承载这些断言的脚本在会话临时目录，合并后即不存在，CI 里没有任何对应检查；同一 commit 的变更证据在另一处又写着「未入库、无回归防护」。评估器判定：**问题被挪了位置，没有闭合，而挪动的方向恰好是让欠账不可见。** 这比诚实地停在文档层更糟——那份文档定位为跨 repo 引用的真源，下游读到「已固化」会以为写法违规会被门禁挡下。

同一轮里，评估器对那个脚本自身做变异，发现它的状态机检查用 `^### .*状态机$` 发现小节，把小节改名为「……的状态与流转」后，该小节的全部结构断言**静默消失**，脚本照常打印「全部通过」。这与 [[shell-script-portability]] 记录的空断言同构：**测试自身也会静默失效**，而发现驱动的循环是这类失效最常见的入口。

规则 2 关于表形态的细则，来自本文件自己的初稿被评估器判为阻断：那张表的行数恰好等于规则数，看上去一一对应，实际是一条规则占了两行、另一条一行没有——而漏掉的恰好是规则 2 本身。**「行数对得上」是最容易被当成完整性证据的假信号。**

规则 6 来自本文件复审时被抓到的阻断：新立的表形态要求套到仓库内已有的固化归属表上，[[shell-script-portability]] 的归属表当场违反——它漏掉自己的最后一条规则，而表行数恰好等于规则数，漏项被这个假信号掩盖，与本文件初稿逐字同构。**新规则的第一个检验对象应该是存量产物，不是本次新写的产物。**

[[shell-script-portability]] 早已写过「未固化的部分仍是文档约定，不得声称为已固化」，但那份文件的标题、原因段、落地层级表全部是 shell 语境，按主题检索时不会命中，实践中被读成 shell 专属规则。本文件的存在就是为了让这条规则脱离 shell 语境。
