# 送审载体与送审提交的一致性

## 规则

- PR 正文、变更证据、任务卡都是**送审载体**。发起评估器审查前，必须先取真实的送审 SHA（`gh api repos/<owner>/<repo>/pulls/<n> -q .head.sha`），并核对三者对同一事实（条目数、关键措辞、人工确认状态、送审 commit）的陈述彼此一致、且与该 SHA 的产物一致。
- 引用 CI 或命令执行结果作为门禁证据时，必须核对该执行的 `headSha` **等于送审 SHA**。父提交或任意祖先提交的绿灯不得作为送审产物的门禁证据 —— 那就是 `AGENTS.md` 禁止的「上一步没报错」推断，只是换了个更像证据的外观。
- **不要在会随提交变化的文档里引用固定 run id**：任何新提交都会让它指向祖先。门禁证据应引用**自动绑定 head 的载体**（PR 的 checks），或在最终提交后再回填。
- 任何通过外部工具（`gh pr edit` 等）写出的送审载体，**必须回读实际内容确认生效**，不得以命令未报错推断成功。
- 载体之间对同一事实出现相反或不一致陈述时，一律以**仓库内产物**为准并同步修正，禁止只改其中一处。
- 人工确认状态在任一载体中只允许如实三态：`已确认` / `未确认` / `待确认`。**禁止把「用户提出了问题」记为确认。**

## 原因

issue #7 的第二、三、四轮 FAIL 都不是内容错误 —— `AGENTS.md` 的清单内容自第二轮起就没有实质缺陷了。三次阻断分别是：

1. 仓库内容已修好，PR 正文停留在旧版本，且对人工确认状态作出与变更证据**相反**的陈述。
2. PR 正文仍未同步 —— `gh pr edit` 调用因 GraphQL 错误未生效，实施方据自身输出报告成功，未核实实际状态。
3. 门禁证据引用的 CI run 落在**父提交**上，而该行还特意标注了「非由推断得出」。

评估器读到的是送审载体，不是实施方的意图。**载体错了，前面所有工作在审查视角下就是错的** —— 人工据此放行时，批准的是一份不存在的产物。

## 固化建议

「送审 SHA 一致性」与「CI run 的 headSha 等于送审 SHA」均可脚本化校验，已建议并入 issue #9。若落地，issue #7 后三轮 FAIL 中有两轮会被自动挡下，不消耗人的注意力。仅「人工确认状态的语义一致」需留在文档层。
